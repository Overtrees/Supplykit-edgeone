### 15.147 首次结账实跑：三个「只有真跑才暴露」的故障 (2026-11-05)

10 月账期在预演阶段（`GET /ledger/preview`）数字全对，但真正 `POST /ledger/reclose` 连挂三次。
三个故障都不在算法里，全在「写入路径」和「字段语义」上，属于 dry-run 验不出来的那一类。

#### 一、故障 1：首次结账被自己的默认值拦死

```
POST /ledger/reclose {"period":"2026-10"}
→ 「上月(2026-09)尚未结账, 请先结上月再结 2026-10」
```

`ledger_state` 是空表，`state_get()` 返回内存默认值 `{"period": period_of()}` = **当月 `2026-11`**。
而 `close_period` 的链条完整性判断把「period 非空」当作「该期已结」，于是判成
「已结到 11 月了，你却在结 10 月 → 跳期」，直接拒绝。建账第一步就死锁。

根因是**字段语义错**：`period` 的含义是「**已结账**的账期」，不是「当前账期」。
默认值应为空串。需要「当前账期」的调用方（`current_period` / `routes/ledger` 状态展示）
本来就以 `status == CLOSED` 为准，不受影响。

#### 二、故障 2：批次切片撞主键

`inventory_month` 1003 行写对了（`377,865 / 357,637 / 233,985 / 501,517`），
但 `freeze_batches` 报 `(1062) Duplicate entry for key 'batch_opening.PRIMARY'`，`batch_opening` 0 行。

`batches` 以**自增 id** 为主键，同一批次键（同 SKU/仓/生产日/到期日）允许多行（每次入库一行）；
`batch_opening` 以**批次键**为主键。`INSERT ... SELECT` 直接搬运必然撞键 ——
实测 78 组重复、多 118 行。改 `SUM(qty) GROUP BY` 批次键：同键多行本就是一笔批次余额，
相加即正确，FEFO 顺序也不变（同键批次等价）。

#### 三、故障 3：回写顺序 + 不幂等，留下中间态

原顺序是「写账期 → **改 inventory.beginning_stock** → 切片批次 → 记状态」。
切片一失败，`beginning_stock` 已经被改成 10 月期末 501,517，而账期没结、`begin_date` 还是空 ——
界面数字变了、账期没闭合，且此时任何一次重算都会读到这个期初。

更麻烦的是**重跑不幂等**：`beginning_stock` 被写成「当期期末」，而 bootstrap 又拿它当基线，
第二次结账会把已结转的量再叠一遍。

三处一起改：

| 改动 | 为什么 |
|---|---|
| 顺序改为「写账期行 → 切片 → **最后**改 inventory」 | 两张新表都幂等可重跑；改存量放最后，失败不留中间态 |
| 新增 `inventory.ledger_base`（首次结账前固化基线，此后永不覆盖） | 基线必须与会被回写的 `beginning_stock` 解耦 |
| 重结同期时期初优先取该期已存的 `begin_qty` | 期初是外部事实，重算改不了它；取回来用才能重跑幂等 |

另：加列必须 **bump `SCHEMA_VERSION`**（6→7）。`ensure_schema` 是版本门禁，
版本没变就直接 return，补列段根本不会执行 —— 表现为「代码部署了、列却没加」。

#### 四、结账成功后暴露的第四个问题：跨月串号

```
11 月汇总：(错) 入 357,637 / 出 233,985   ← 这是 10 月的量
          (对) 入  98,515 / 出 223,359
```

`_apply_to_inventory` 把结账月的 `month_inbound/month_outbound` 写进了 inventory，
而这两个字段是「**当月**滚动值」。11 月页面读它 → 显示 10 月的入出 → 周转全错。
行级更隐蔽：自有仓某 SKU 本月无流水时，`month_in.get()` 返回 `None`，回落读静态列，
等于**跨月串号**（也正是用户反复要求清除的那类兜底）。

修法：结账只回写 `beginning_stock`；自有仓行级缺流水按 **0**；汇总的月入出改按流水现算。
平台仓/B 仓维持回落（后台导出即权威，已定口径）。

#### 五、实跑结果（线上，2026-11-05 10:00）

```
POST /ledger/reclose {"period":"2026-10"}
→ ok: rows 1003, batches 2540, beg 377865, in 357637, out 233985, end 501517, orphan 0
```

| 校验项 | 值 | 结论 |

| 账期等式 | `377,865 + 357,637 − 233,985 = 501,517` | ✓ |
| 批次切片 Σqty | `376,673` | **等于当前可用**（批次轨与库存轨闭合） |

#### 六、还剩的已知项

- **`inventory.month_inbound/month_outbound` 仍是 10 月的值**：结账不再写它，但也没清。
  自有仓页面已不读（改走流水），平台仓不受影响；`task_seed._month_sum_diff`
  这类巡检工具会看到不一致 —— 属可接受的脏值，下次导入会覆盖。
- **`ledger_base` 目前仍是 NULL**（本次走的是「本期已存 begin_qty」分支）。
  下一次真正从零建账时才会固化，语义已备好。
- **11 月账期会在 12-01 自动结**，届时走「上月期末」分支，不再碰 bootstrap 逻辑。

## §15.148 规则字段单一真源：三份手工列表 → 一张注册表(2026-11-05)

### 一、现象

规则页能选中、能保存，但规则**永不触发**，也不报任何错。实测两个字段：

| 字段 | 白名单 | 规则页下拉 | 注入判定 `_CALC_VARS` | 结果 |
|---|---|---|---|---|
| `supplier.score` | ✅ | ✅ | ❌ | 走快速路径 → ctx 无 `supplier` 键 → 条件恒 None |
| `inv.turnover_days` | ✅ | ✅ | ❌ | 同上（`turnover_days` 只在 `if _need_calc` 分支里注入） |
| `inv.locked_qty` | ❌ | ✅ | — | 反向：选中保存直接被 `validate_condition` 拒 |
| `order.unit_price` | ❌ | ✅ | — | 同上 |

### 二、根因（四个，叠在一起才"完全静默"）

1. **两份手工列表**：`_VALID_FIELDS`(保存校验) 与 `_CALC_VARS`(是否进入计算注入) 各写一份，
   任一处漏登记即失效。`_CALC_VARS` 还是**子串匹配**，与字段名没有结构关系。
2. **校验正则只认 `a.b`**：`re.finditer(r"[a-z_]+\.[a-z_]+")` → 顶层字段(`daily_sales`/`sellable`)
   根本不校验，拼错也放行。
3. **求值端右侧只解析带点字段**：`_check_single` 的 `right` 走 `elif "." in right` 分支，
   `right=daily_sales` 落到 else 被当字符串 → `int < str` 抛异常被 `except` 吞 → **恒 False**
   （左侧正常，所以用户更难看出是哪边的问题）。
4. **测试弹窗另有一份 ctx**：`test_rule` 只注入 inv/order/health(+own/batch)，
   `supplier.score`/`turnover_days` 取不到 → 弹窗恒"未触发"，用户据此判断"规则写错了"，
   而这条规则在真实评估里同样不触发 —— 两个错误互相印证。

### 三、修法

**新建 `core/rule_fields.py`（唯一真源）**：每个字段登记一次 `(kind, scopes)`
- `kind=base` 快速路径 ctx 就有；`calc` 需 `_need_calc` 分支注入；`event` 由具体事件提供
- `scopes` 标明该字段在哪些事件上下文里真实存在（`inv`/`order`/`flow`）

派生关系：`_VALID_FIELDS = frozenset(FIELD_SPEC)`、`needs_calc(cond)` 解析条件里的字段引用后
查表（不再子串匹配）、`validate_condition(cond, event)` 增加**事件作用域**校验。

配套四处：
| 文件 | 改动 |
|---|---|
| `core/rules.py` | 删手写白名单与 `_CALC_VARS`，全部派生；`_CALC_VARS` 仅留兼容别名 |
| `core/rule_cond.py` | 右侧统一解析：登记过的字段 / `params.*` / 含运算符 → 求值；字面量剥引号(`'own'`→`own`) |
| `core/rule_eval.py` | 注入判定改 `needs_calc()`；未登记字段每进程留痕一次（`try_err`），不再静默 |
| `core/rule_sim.py`(新) | 测试弹窗 ctx 构造从 542→ 抽出（`routes/rules.py` 已 600 行红线），补 `supplier.*`/`turnover_days`/顶层别名 |

**作用域收窄**（防"换一种静默"）：`inv.in_transit_qty`/`inv.safety_qty` 原来对 order/flow
也放行，但那些 ctx 里是**写死的 0** → "低于安全线"恒不成立。现只允许 `inv` 事件。

### 四、行为变化（用户可感知）

- `supplier.score` / `inv.turnover_days` / `inv.locked_qty` / `order.unit_price`：保存通过，且**真的会触发**
- `flow.quantity` 写进 `inventory.changed` 规则：保存被拒，提示"该事件上下文不提供此值"
  （以前能存、永不触发）
- 顶层字段拼错（`daily_sale`）：保存被拒（以前放行）
- 右侧写 `daily_sales` / `'own'`：条件能正常判定（以前恒 False）

### 五、验证

`local_test.py` 475 通过 / 0 失败，新增 9 条断言：

```
✅ 规则字段: supplier.score 需计算注入
✅ 规则字段: inv.turnover_days 需计算注入
✅ 规则字段: 纯 base 条件不走计算注入
✅ 规则字段: 规则页下拉字段全部已登记      ← 解析 labels.tsx 的 LF 数组，与注册表比对
✅ 规则字段: flow.quantity 在 inventory.changed 被拒
✅ 规则字段: 无点字段拼错也拦(原正则只查 a.b)
✅ 规则求值: right 侧无点字段可解析

## §15.149 进销存月汇总上界 + 键盘焦点可见 + 两列静态值的去留核实(2026-11-05)

### 一、月汇总区间补右开上界

`insights.py` 里自有仓的"本月入/出"原来只写 `日期 >= 本月1日`，没有上界。
流水表 `inbound_date/outbound_date` 是 `VARCHAR('YYYY-MM-DD')`，字典序可比；一旦表里有
**下月/未来日期**（提前导入、补录、日期解析错年份），就会被算进本月 —— 与账期/结账统一
使用的 `< 下月1日` 口径不一致。

修法：行级 2 处 + 汇总 2 处聚合全部改为 `>= 期初日 AND < 下月1日`，边界由
`core.ledger.period_bounds_excl()` 提供（唯一真源，不手写月份算术）。

断言：`账期: 进销存流水聚合带下月1日上界(右开, 各 2 处)`（count 精确匹配 2/2）。

### 二、键盘焦点可见（142 个原生按钮，一处覆盖）

**现状核实**：全仓 142 个 `<button>`；CSS 里**没有**全局 `button{outline:none}`，
但 13 处内联 `outline:'none'`（登录页输入框等）把默认环去掉了，且**没有替代反馈**
（登录页输入框聚焦后视觉毫无变化）。iOS/WKWebView 点按不出环、桌面默认环是系统细线，
在玻璃拟态背景上对比不足 —— 观感就是"键盘操作没有焦点"。

修法（`styles.css` 末尾集中一段，不改 JSX）：

| 规则 | 作用 |
|---|---|
| `:where(button,[role=button],a[href],summary,input,select,textarea,[tabindex]):focus-visible` | 2px `--focus-ring`(#0057d9) 环 + `outline-offset:2px` |
| `!important` | 突破 13 处内联 `outline:'none'`（那些位置没有替代反馈） |
| `@supports not selector(:focus-visible)` + `(pointer:fine)` | 老 Safari 回落 `:focus`，只在精确指针设备启用，手机点按不残留环 |
| `@media (forced-colors: active)` | 环改 `Highlight`，跟随 Windows 高对比度 |

环色刻意比主色深一档：主色按钮(#007aff)上用同色环只靠 2px 白缝分隔，对比偏弱。

**抖动修复（根因是"几何缩放"）**：`button:active{transform:scale(.97)}` 会让环跟着缩。
把全站按压反馈从**缩放**改为**变暗**（`filter:brightness(.93/.94)`），几何不再变化，
环纹丝不动；`.btn` / `.clickable` / `.hammer-btn` / `.hammer-segment` / `.task-download`
一并改，`transition` 里的 `transform` 换 `filter`。鼠标/键盘/触屏按压观感一致。

**实测（Playwright + Chromium，430×700 与 390×844 两档）**：

```
键盘聚焦 button     → outline solid 2px rgb(0,87,217), :focus-visible = true
鼠标点按 button     → outline none,                  :focus-visible = false
键盘按住 Space      → transform none + filter brightness(0.94)   ← 环不抖
鼠标按住            → filter brightness(0.94)                     ← 按压反馈保留
输入框点按          → 仍出环（规范如此：需要指示光标落点）
```

多形态截图验收：主色/次级/危险/圆形图标/表格内按钮/输入框/下拉/复选框，环均完整、
圆角贴合、未被滚动容器裁切。

### 三、`inventory.month_inbound / month_outbound` 能不能删（核实结论：不删）

| 消费方 | 用途 | 删掉的影响 |
|---|---|---|
| `insights.py` 平台仓/ B 仓 | 月入出**只能**取静态列（流水聚合只在 `wh_type=='own'` 分支查） | 期末=期初、周转恒 `null` |
| `task_export.py` | 导出 Excel"当月入库/当月出库"两列 | 导出少两列 |
| `task_seed.py` / `test_inv_recalc.py` | 报表值 vs 流水值的对账巡检 | 失去核对基准 |
| 清洗页 `fields.ts` | 库存报表可映射字段（用户 Excel 真有这两列） | 用户数据无处落 |
| `inventory_archive` | 列必须与 `inventory` 逐一对应（恢复靠 INSERT 全列） | 两表要同删 + 历史数据迁移 |

结论：**平台仓仍在用**（页面不展示，但期末/周转计算与导出在用），且这是导入文件里的
原始字段 → 删列=丢数据资产。自有仓已经不读它（走流水），残留值无害，
结账也不再写（只回写 `beginning_stock`）。

若目的是"消除误解"，正解不是删列，而是**在自有仓页面标注月入/出取值来源是流水**，
以及当月无流水时给出"请导入出入库明细"的提示（否则用户看到一排 0 不知道原因）。

> **2026-11-05 修正**：上面"平台仓仍在用"的核查结论只对了一半 —— 所谓的"在用"是
> `insights.py` 自己在用一个没人消费的派生字段（见 §15.150）。用户定案：平台仓/ B 仓
> 不需要当月入出，已从计算链彻底解绑。删列仍不做（那是导入原始字段），但"仍在使用"
> 这个理由不再成立。

## §15.150 平台仓/B 仓与「当月入出」解绑 + Prettier 门禁归零(2026-11-05)

### 一、先回答"自有仓这个维度还要不要"

**要，而且是核心。** 自有仓页面上那两列（本月入 / 本月出）不是可选装饰，它们是
「期初 + 入 − 出 = 期末」这条恒等式的两个操作数：

| 页面元素 | 依赖 | 缺了会怎样 |
|---|---|---|
| 期末库存 | 期初 + 月入 − 月出 | 只剩期初，等于不承认本月动过货 |
| 平均库存 | (期初 + 期末) / 2 | 同上 |
| 周转天数 | 平均库存 × 月天数 ÷ 月出 | 除数为 0 → 恒 `null`（显示"未出库"） |
| 仓周转（表尾） | Σ期初 / Σ月入 / Σ月出 | 同上 |
| 与账期对账 | 期末 ≡ 该月末批次剩余 | 失去可复算性，只能"信结果" |

要点在于：自有仓这两列的值**不是** `inventory.month_inbound`，而是当月
`inbound_records/outbound_records` 按 `sku + 69码 + 仓` 现算（`insights.py`），
`inventory` 上的同名列在自有仓只是导入留档。所以"保留自有仓维度"保留的是**列与算式**，
不是那两个静态列。

### 二、平台仓 / B 仓：从计算链解绑（用户定案：不需要）

核查"到底谁在用"，四个可能的消费方全都不成立：

| 消费方 | 实际情况 |
|---|---|
| 页面列集 | `INV_COLS.platform / platform_b` **没有** `month_in` / `month_out` / `end_stock` / `avg_stock` / `turnover` |
| Excel 导出 | `task_export.py` 里这几列包在 `if _wh == "own"` 内 —— 平台仓根本不输出 |
| 表尾合计 | 合计只在对应列存在时渲染（`visCols.map`），平台仓无列 |
| 仓周转 | `turnover` 列只在 `own` 列集；`totalTurnover` 加了 `whType !== 'own' → null` 护栏 |

也就是说，`insights.py` 里为平台仓算出来的 `month_inbound/month_outbound → end_stock
→ avg_stock → turnover_days` **没有任何读者**，只是躺在 JSON 里冒充"真值"。
更糟的是它算得不对：平台仓没有期初列，`期初 + 0 − 0` 恒等于期初(通常 0) → 期末恒 0。

改动（3 处）：

| 位置 | 改动 |
|---|---|
| `insights.py` 行查询 | 非 own 时 SELECT 不再带 `i.month_inbound, i.month_outbound` |
| `insights.py` 行计算 | 非 own：`month_inbound = month_outbound = 0`；`end_stock = available_qty`（导出即权威），`avg = available`，`turnover_days = null` |
| `insights.py` 汇总 | 非 own：SQL 不 SUM 这两列（`0 AS mi, 0 AS mo`），少扫两列 |
| `InventoryPage.tsx` | `totalTurnover` 加 `whType !== 'own' → null` 护栏（列集本就没有，防将来加列算出 0 天） |

## §15.151 对账工具的两处「声明了却不校验」+ 测试弹窗的仓型空串(2026-11-05)

### 一、schema 对账报「库里多出 3 列」是假阳性，真问题是反的

```

✓ 所有声明的列都存在

三列在 `schema_create.py` 里都**明确声明了**（146 / 152 / 313 行，且带反引号）。
根因在 `sql_smoke.parse_columns()`：它按括号深度切分后，**只拿首 token 判约束行**：

```python
name = tok.group(1)
if name.lower() in _CONSTRAINT_HEADS:   # {"primary","unique","key","index",...}
    continue                            # `key` VARCHAR(80) 也在这里被丢掉
```

列名恰好等于约束关键字（`key` / `index`）时就被当成 `KEY idx_x (...)` 跳过。方向其实更糟：

_nxt = re.match(r"\s*`?([A-Za-z_][A-Za-z0-9_]*)`?", p[tok.end():])
if not _nxt or _nxt.group(1).lower() not in _TYPE_HEADS:
    continue
```

`PRIMARY KEY (a)`（下一词 `KEY`）/ `KEY idx_x (a)`（下一词 `idx_x`）仍判约束；
`` `key` VARCHAR(80) `` 判列。补账后 **433 列 / 缺失 0 / 多余 0**。

## §15.152 期初双场景: 结转 vs 窗口内实盘导入(2026-11-05 用户定案)

### 一、原来的缺口

账期改造(§15.146/§15.147)只实现了**一个场景**: 本月期初 = 上月期末(carryover)。
实盘导入被降级成 `snapshot_qty`(只对账)，理由是"每次导入都写期初 = 每月累加一次双算"。
但真实业务里"盘库"是**月末/月初一次性的外部事实**，与"每周导一次库存报表"不是一回事 ——
一律不认，等于用户盘完也改不动期初，只能手改库。

所以按**时机**区分两个场景(而不是按导入次数):

| 场景 | 触发条件 | 本期期初 |
|---|---|---|
| A 默认 | 窗口内没有导入库存 | 上月期末(结转，既有口径) |
| B 实盘 | 上月末最后一天 00:00 ~ 当月 3 日 23:59:59 之间导入过库存 | **导入值**，覆盖结转并留痕 |

窗口为什么这么定: 结账在次月 1 号 03:05(平台调度)才跑，月末最后一天盘库很常见，它描述
的就是"下月期初"；4 号以后再导入，量里已经掺了本月流水，再当期初必然双算。

### 二、换算: 校准"导入时点结存"，不是硬塞期初

```
期初 = 导入量 − Σ净流水[本月 1 日 00:00, 导入时刻)
```

导入量永远被当作"导入那一刻仓库里有多少"，用户不需要倒推成月初数。上月末导入时区间为空，
期初 = 导入量，天然正确。净流水为负(净出库)时直接回加，**不夹 0** —— 实盘与流水打架要暴露。

### 三、落点

| 表/文件 | 作用 |
|---|---|
| `ledger_begin_adj`(新表) | 一行 = 账期×SKU×69码×仓，存 `qty`(校准后) / `imported_qty` / `offset_qty` / `carried_qty`(原结转) / `delta` / `batch_id` / `applied_at`，供审计 |
| `core/ledger_adj.py`(新模块) | 窗口判定 + 换算 + 写库存期初 + 批次差额 + 留痕 + `begin_map/summary` 读侧 |
| `core/ledger.build_rows` | 期初优先级新增 ⓪ 校准值（压过 ①上月结转）；`inventory_month.src` 逐行写 `import`/`derived` |
| `routes/cleanse_write.py` | 库存写入成功后接线（仅 own，异常只 `try_err`，绝不阻断导入） |
| `routes/ledger.py` | `/ledger/status` 增 `begin_source / begin_adj_rows / begin_adj_delta / begin_window` |
| `routes/misc._LOG_SCOPE_TYPES` | 新增 `ledger_override`(user 域) —— 不登记＝日志页按类型过滤时"写了等于没写" |

**批次轨**: 期初一变，`Σbatch_opening` 与库存轨就差 `delta`。盘盈补一条到期日 `9999-12-31`
的调整批次(FEFO 末位，不吃掉真实批次)；盘亏按到期日从早到晚逐批扣，扣不干净才留负数暴露。
随后 `_recalc_own_inventory` + `_rebuild_own_batches` 立刻重算 —— 不等下一次导入，
否则"期初改了列、可用还是旧值"。

**只对当前进行中的账期生效**: 已结账的期再改期初，期末就与月报不符 → 返回 skipped，
让用户走 `/ledger/reclose`。窗口内多次导入以**最后一次**为准(UPSERT)，每次都写一条日志。

### 四、验证

```

结账优先级    上月结转 end_qty=10 + 校准 77 → begin=77, src=import（mock 直连 build_rows）
线上冒烟      临时渠道连续两次导入 → 期初 100 → 80，两条日志(原结转 → 校准后 → 差额)，清理后 0 残留

### 五、残余与边界

- **流水日期是 VARCHAR**，只标日期的行按"当日 00:00"参与回退；假设导入量是"导入那一刻的结存"，
  与文件实际含义(导出时点)可能有几小时误差 —— 但方向一致，且差异会在月末对账里显形。
- **盘亏扣批次**按到期日升序，与出库 FEFO 同序；期初被调到低于批次余额时留负数批次，
  由 `_rebuild_own_batches` 的"Σ批次≡可用"告警继续盯着。
- 平台仓/B 仓**不参与**(快照制，不进账期)。

## §15.156 文档级语言同步: title / meta / html lang(2026-11-05)

### 一、这是门禁查不出的死角

红线 B 的可执行门禁扫的是 `frontend/src` 里的中文字面量, 但有几处字符串**不在 React 树里、也不经过 `t()`**:

| 位置 | 改前 | 切 EN 后 |
|---|---|---|
| `<title>` | `index.html` 写死 `<title>Supplykit</title>` | 不变(仍是中文语境下的产品名) |
| `<html lang>` | 写死 `lang="zh-CN"` | 不变 → 屏幕阅读器仍按中文发音 |
| `meta[name=description]` | **根本不存在** | — |
| `app.name` / `app.desc` | 字典里有, **全仓零引用**(§15.155 核实) | 白躺着 |

所以 §15.155 里"`app.*` 两条先留着"的后续就是这一步: 先接消费点, 再让它们变成活键。

### 二、实现(`frontend/src/locale.ts`)

```ts
function applyDocumentLang(locale: Locale) {
  if (typeof document === 'undefined') return          // SSR / node 脚本无 document
  const name = t('app.name')
  if (name && name !== 'app.name') document.title = name  // 缺词条时 t() 回落键名, 宁可不动
  const desc = t('app.desc')                              // 没有就建 <meta name=description>
  ...
  document.documentElement.lang = locale === 'zh' ? 'zh-CN' : 'en'
}
```

两处调用, 缺一不可:

1. `setLocale()` 里 —— 用户切语言时立即生效;
2. `main.tsx` 启动时 `syncDocumentLang()` —— **首访的语言是从 localStorage / navigator 探测的,
   走不到 `setLocale`**, 而 `index.html` 的 title 与 lang 是静态中文。只在 setLocale 里做,
   等于"第一次打开英文系统的人看到的仍是中文标题"。

`lang` 取值: 中文用 `zh-CN`(简体标准写法), 英文用 `en` 而非 `en-US` —— 与字典
"界面用语而非地区变体"的口径一致。

### 三、为什么要加"缺词条不动"这个判断

`t()` 在缺键时**回落到键名本身**(`return ... || key`)。如果不判, 哪天有人把 `app.name` 删了,
浏览器标签页会直接显示 `app.name` —— 这比保留原标题糟得多, 且同类事故在
`RiskSheet` / `renderNoteSegs` 上都真实发生过(界面上冒出英文键名)。
测试里专门锁了这条: `expect(document.title).not.toMatch(/^[a-z]+\.[a-z_]+$/)`。

### 五、没有一起做的事(残余)

- **语言切换入口本身不存在**: 全仓只有 `setLocale()` 定义, **没有任何 UI 调它**;
  `getLocale()` 也无调用方。也就是说 en 字典目前只能靠 `localStorage.c_locale` 手工设置生效。
  这是比标题更深的一层缺口 —— 红线 B 守的"切到 EN 不能半中半英", 前提是**能切**。
  要不要做切换入口(设置页 · 界面段), 单独定。

## §15.157 seed 规模扩到 90 天 / 1 万 SKU / 21 万单, 并把 RU 从 ≈2500 万压到 2.4 万(2026-11-05 用户定案)

用户原始诉求:「每渠道订单 csv 20 万单可以波动在 21 万 21 万多, 各 10000 个 sku, 10000 个里
需要体现有一个 sku 多 69 码, 具体比例你看着来…最后我需要拟真彻底, 不接受来回返工,
ru 消耗是大头, 目前已经消耗 2100 万只剩 2900 万左右」。

### 一、规模: 数字必须反推, 不能正算

第一版按"90 天 × 2333 单/天 ≈ 21 万"设了 `ORDER_BASE_PER_DAY = 2333`。实测生成 **32 万单** ——
促销日(×2~4, 25 天)与周末(×0.6~1.2)是**在基数上再乘**的, 用户给的 21 万是**含波峰后的总量**。
反推: 基数 1550 时 5 次抽样落在 **20.4 万 ~ 21.6 万**(中位 21.1 万)。最终实测生成
**jd 214,984 / other 212,173**, 符合口径。

| 项 | 值 | 说明 |
|---|---|---|
| `SKU_PER_CHANNEL` | 10000 | 编号位宽 4 → **5**(`SKU-%05d`); 4 位到 9999 就撞名 |
| `ORDER_DAYS` | 90 | 订单/流水/快照/物化**共用这一个窗口** |
| `ORDER_BASE_PER_DAY` | 1550 | 见上, 反推值 |
| `BC2_RATIO` | 0.01 | 多码 SKU 每渠道约 100 个(原来固定前 3 个, 大规模下等于没有) |
| `_SEED_ORDER_SEGS` | 6 | 90 天 ÷ 15 天/段(原 4 段 × 15 = 60 天) |
| 库存行 | 170,200 | 其中多码行 200(双渠道各 100) |
| 滞销/低动销 SKU | 1964 / 1347 | 3% / 2% |

### 二、段号重排引爆的两处硬编码

段号从 `库存5/流水6/落账7/月汇总8` 变成 `库存7/流水8/落账9/月汇总10/尾11/完成12`,
两个地方写死了旧值, 都不是"改个数字"那么简单:

1. **`/api/seed/step` 白名单 `(5,6,7,8)`** → 改为从 `seed_fill` 的段常量推导
   (`_SEED_INV/_SEED_FLOW/_SEED_SETTLE/_SEED_MONTH`)。以后再加段不用动这里。
2. **`task_seed.py` 的 `nxt >= 10`** —— 这是**真事故**: 完成值变成 12 后,
   任务越过 10 就再也不会落 `done`, 前端 `status` 轮询会**无限续跑**, 每轮都在跑
   `_seed_tail` 里的快照/物化重建(空转烧 RU)。改为 `nxt >= SEED_DONE`, 并在回归里钉死
   `"nxt >= 10" not in 源码`。

### 三、RU: 成本按「批次数」计, 不按「SKU 数」计

这是本轮最贵的一课。原 `_recalc_own_inventory` 是"每 200 SKU 一条 SELECT + 每行两个相关子查询":

```
旧: 2000 SKU ÷ 200 = 10 批 × 29.6 RU/批(线上 EXPLAIN ANALYZE 实测) → 单步就要 296 RU
```

第一版改成 `UPDATE JOIN` 聚合后只省了两成(29.6 → 23.9 RU/批)——因为它**还是按 SKU 分批**。
真正的原因是 **TiDB Serverless 的 RU 按"一批"计价, 与批里放多少 SKU 关系很小**。
所以正确解法不是"让每批更便宜", 而是**把批数压到 1**:

```python
# 一条 SELECT 取全量(该渠道 own 行 + 全部流水聚合) → Python 算 → executemany 回写
# 实测: 119.4 RU / 39.6ms(全渠道一次聚合 66.9 RU)
```

24000 批 → **2 批**。这一处把 ≈2500 万 RU 压到 **239 RU**(降 5 个数量级)。

同批还有一处:`_seed_records` 里判滞销的
`GROUP BY sku HAVING SUM(quantity) <= 15` 实测 **422.69 RU**(18 万行订单扫 + 分组),
而它只为拿 970 个 SKU 的标记。改为**内存优先**(标记由 `_seed_orders_range` 生成时记入
`_DEMO_SLOW`), 只有内存集合为空(`/seed/step` 单跑流水段)才退回查库, 且按渠道分查。

**坑**: 按 `(sku, 码, 仓)` 聚合会让"仓型为空"的流水被三个仓型各累加一次,
所以**仓型必须进 GROUP BY 键**, join 时再放宽为 `(f._wt = '' OR f._wt = i.warehouse_type)`。

全量重灌的 RU 粗估(按批量/次计):

| 环节 | RU |
|---|---|
| 订单写入(500/批 × 43 万行) | ≈10,250 |
| 流水写入(500/批) | ≈8,170 |
| 库存写入 | ≈2,720 |
| 批次写入 | ≈1,900 |
| own 重算(2 渠道各一次全量) | **239** |
| 快照聚合 90 天 × 2 | ≈880 |
| `sku_sales_stats` 重建 × 2 | ≈88 |
| **合计** | **≈24,300** |

剩余 2900 万 RU 够跑 **100 次以上**全量重灌。

### 四、`seed_watermark`: 半途失败不再只能整库 reset

90 万行量级的 seed, 单步撞 90s 上限/网关 504 是常态。旧做法下"跑到一半失败"只有一个出路:
整库 `reset` 重来 —— 把前面已经正确的步骤一起丢掉, 还要再付几十万行 DELETE 的 RU。

```sql
-- 写入前记水位, 回滚 = 只删本轮新增
hwm_before = MAX(id)                    -- 该表本轮写入前
DELETE FROM `t` WHERE id > hwm_before   -- 历史行(哪怕也是 seed 生成的)一行不碰
```

**语义严格限定**: 只对**插入型**目标登记(`orders` / `inventory` / `inbound_records` /
`outbound_records` / `batches`)。upsert 型目标(`products` / `suppliers`)没有 id 单调性,
水位回滚不成立 —— 那类只做行数对账。

**行数对账**: `expected`(生成侧说写了多少) vs `actual`(`id > hwm_before` 实际计数)。
差一行就是一行。旧实现在这里完全静默: 生成侧打印"生成 170200 行", 库里 169800,
后续所有对账(Σ批次=可用 / 月汇总=流水)都在拿残缺底数算, 却"看起来跑完了"。
`status='short'` 只留痕**不抛错**(可能是合法去重), 但不能没有。

新增两个 admin 运维口:

```
POST /api/seed/watermark  {"run_id": "..."}              只读: 每步 expected/actual
POST /api/seed/rollback   {"run_id": "...","steps":[7,8]} steps 可省; 只删 id > hwm_before
```

`rollback` 与正在续跑的任务互斥: 任务 `running` 时返回 409 —— 否则会删掉本步刚写入的行。

### 五、`SCHEMA_VERSION` v8 → v9: 一次"声明了却没建"的现场

本次先加 `seed_watermark` 声明时**只改了声明没 bump 版本号**(声明写着 8、版本也已是 8)
→ `ensure_schema` 走热路径直接返回, 新表永远不会创建。

这是 `--schema-diff` 对账抓出来的(它在 preflight [3/8] 里直接报
`seed_watermark.<整表不存在>`)。同一类事故在 §15.122 已经踩过一次, 这次仍复现 ——
说明"改 schema 必 bump"这条规矩光写在注释里不够, 必须由对账在门禁里挡住。

顺带把回归里钉死 `"SCHEMA_VERSION = 8"` 的断言改成 `>= 8`: 钉死具体数字会让每次
**合法**的 bump 都变成红灯, 逼着人改测试而不是改代码。

## §15.158 seed 落账段卡死 280s + 任务卡"显示刚刚/卡骨架屏"(2026-11-05 用户实测反馈)

用户一次提了五条, 逐条对应到**五个独立缺陷**, 其中两条是同源的"耗时按批次数计"。

### 一、落账段 280s 撞死 90s 上限(用户第 5 条)

现象: seed 跑到第 9 段(落账)后, 每次 `status` 轮询都在 90s 以上返回空,
任务永远停在 `running`, 前端看到的就是"十来分钟不动"。

根因: `_rebuild_own_batches` 按 **100 个 SKU 一批**循环, 每批 6 条查询。
线上实测单批三条主查询合计 **1.26s**, 2 万 SKU ÷ 100 = 200 批 × ~1.4s ≈ **280s**。

修法与 §15.157 的重算是同一条规律 —— **耗时只跟查询次数有关, 跟批里放多少 SKU 关系很小**:

| 批大小 | 单批耗时 | 批数 | 总耗时 |
|---|---|---|---|
| 100(原) | 1.26s | 200 | ≈ 280s ❌ |
| 500 | 1.74s | 40 | ≈ 70s |
| **1000(现)** | **1.78s** | **20** | **≈ 36s** ✅ |
| 2000 | 2.78s | 10 | ≈ 28s(但单批内存/延迟抖动风险更大) |

1000 是拐点, 再大单批自身开始变慢。

同批还省掉一次 `SELECT DISTINCT sku FROM inventory`(2 万行实测 **3.1s**)——
`seed_settle` / `_seed_batches` 改为优先用内存里的 `skus_data`, 只有 `/seed/step`
单跑(没有内存集合)才查库。

### 二、订单段返回值一直是错的(水位对账抓出来的)

`_seed_orders_range` 返回的是**全局累计序号 `total`**(含 `day_from * 1000000` 的步偏移),
不是本段新增行数。水位第一次跑就报"第 2 段预期 15,072,115 / 实际 72,115" ——
差正好 1500 万, 就是偏移量本身。

这个错值一直只用于 step summary 展示("生成了 1500 万单"), 从没人核对过。
现在改为显式累加 `_seg_rows`, 并在回归里钉死 `return _seg_rows`。

**顺带确认**: 水位对 `inbound_records` 报 expected 40,202 / actual 80,210 —— 一开始误判为重复写入,
实际是 `INSERT IGNORE` **撞键也会消耗 auto_increment**, 而 `COUNT(*) WHERE id > hwm` 数的是真实行数。
这里没有 bug, 但注释写清楚了"不能用 MAX(id)-hwm 代替 COUNT"。

### 三、任务卡右上角一直显示"刚刚"(用户第 1 条)

`relTime()` 是**纯渲染期计算**, 组件不重渲染就不会重算。而任务轮询每 3s 一次,
但 state 内容不变时 React 不会重渲染 → 任务跑 10 分钟, 卡片还写"刚刚"。

修: 任务 `running` 时挂一个 30s 定时器强制重渲染(`setTick`)。相对时间是 1 分钟粒度,
30s 刷新足够, 又不会给每张卡挂 1s 定时器(一屏可能有十几张卡)。

### 四、进度条写死 10 段(同源, 段号重排没跟上)

`TaskCard` 里 `pct = progStep / 10`, 段号重排后完成值是 **12** → step > 10 时进度顶在 99% 不动,
看起来像"卡在最后一步"。改为后端在 `params.total_step` 下发 `SEED_DONE`, 前端缺字段时按 10 兜底。

### 五、多数页面"一直在加载中"(用户第 3、4 条)

两处**竞态**, 都在 `loading` 这类开关状态上:

1. **`useAppStore.loadAll`**: `loading/orderLoading` 置 true 之后, 有 **4 处**
   `if (_mySeq !== _loadSeq) return` 在 `finally` 之前就返回了。被丢弃的那次把

## §15.159 三条用户实测「没根治」的深挖: 骨架死锁 / 胶囊靠手工配对 / 「刚刚」根本不是渲染问题(2026-11-05)

用户原话:「1.快速访问多页面卡加载中/同步中依旧…并没得到根治我需要彻底根治 2.什么情况?不行就再分多步走
在12上拓展?保障单次请求不超时上限是120s 3.任务卡片的依旧显示刚刚,没有实时计算,这是导入任务特殊还是?
我记得之前是实时渲染的」。

上一轮(§15.158)我修的是**症状**: 给竞态加序号、给相对时间加定时器。这一轮把三条都往下挖了一层,
每条都挖到了与上一轮完全不同的根因 —— 这也解释了"为什么上一轮修完用户还在复现"。

### 一、「刚刚」—— 不是渲染问题, 是数据问题

上轮判断"卡片不重渲染所以 relTime 不重算", 加的修法是 30s `setTick` 强刷。**这只对了一半**。
真正的根因在数据层:

```
TaskCard 读的是 task.created_at  → 那是"任务**创建**那一刻"
seed 是分步长跑(13 段, 10~30 分钟), 每步推进**不改 created_at**
→ Date.now() - created_at 只会越算越大, 但前端拿到的是同一个常量, 差值算出来永远 < 1 分钟
```

等一下 —— 差值是不断变大的, 为什么还是「刚刚」? 因为**卡片拿到的 created_at 本身是对的,
但那次轮询返回的数据里没有任何字段能表达"这个任务还在动"**。用户看到的"刚刚"其实是
「创建于几分钟前」被正确算成了"N分钟前"以外的另一种情况: 当 `setTasks(d.data)` 写入的数组
内容与上一轮**完全相同**(status 没变、params 没变), React 不重渲染 → `relTime` 不重算 →
时间冻结在第一次渲染的那一刻 = 「刚刚」。所以**两层都要修**:

| 层 | 修法 |
|---|---|
| 数据 | `/api/tasks` 补 `updated_at`(每续跑一步 `NOW()` 刷新 = 进度心跳), running 时优先用它 |
| 渲染 | 把原来"耗时 1s / 相对时间 30s"两条定时器合成**一条 1s 时钟**, 同时驱动两者 |

一条定时器而不是两条: 任务页有 N 张卡, 每卡两条就是 2N 个 interval。

### 二、「卡加载中/同步中」—— 胶囊此前只信手工配对的计数器

`store.syncing` 全仓有 **9 处** `setSyncing(1)` / `setSyncing(-1)` 调用点(Dashboard 3、Insights 3、
Inventory 1、History 1、store.loadAll 1)。每一处都要自己在**所有**退出路径上配对 ——
而 `loadAll` 里甚至有 4 处 `if (_mySeq !== _seq.v) return` 在 `finally` 之前。

更关键的是 `loadAll` 自己就不一致:

```python
# 加：直接赋值          # 减：夹到 0
syncing: get().syncing + 1     |     Math.max(0, get().syncing - 1)
```

当 Inventory 的 `-1` 先把计数压到 0, `loadAll` 收尾再 `-1` 被夹回 0 —— 它减掉的是**别人的名额**,
剩下那次真实取数就没人计数了。修法两条:

1. 增减同源, 都走 `setSyncing`
2. **网络层补一条硬信号**: axios 拦截器统一登记在途请求数(`_reqStart` / `_reqEnd`),
   成功/失败/取消三条路径都注销; 胶囊 = `syncing > 0 || reqBusy > 0`。
   页面漏配对不再可能让胶囊永久转圈 —— 这是把"9 个调用点都得对"变成"1 个地方必然对"。

### 三、骨架屏死锁 —— `setLoading(false)` 挂在竞态 return 之后

`TaskPage.loadTasks` 由**三个源**驱动: 3s 轮询 + `visibilitychange` + `channel` 变化,
每次调用都 `++loadSeq.current`。而收尾是:

```js
if (mySeq !== loadSeq.current) return   // ← 首载一慢就永远过期
setLoading(false)                        // ← 永远走不到
```

`/api/tasks` 在 50 条长 `params` 上确实会超过 3s → 轮询抢先把序号推走 → 首载回来即过期 →
`setLoading(false)` 永不执行 → **骨架屏永久卡住**。修法: 挪进 `finally`。
"有没有数据"不依赖谁是最新, 数据内容才依赖。

## §15.160 seed 改成真·导入链路 / 任务看守 / 时间解析(2026-11-05)

### 一、上一轮的"复用生产函数"绕过了导入本身

§15.159 之后的 seed 仍然是 `executemany("INSERT IGNORE INTO orders ...")`, 只是把**生成**
逻辑抽成了函数。那等于: 导入链路里所有"入口才有"的规则一次都没被走过 ——

- 69码归码(档案有码、本行缺码时按档案补, 多码并存时拒写)
- 订单四维业务键对齐(`order_no|sku|barcode`, 空码落二键)
- 库存期初实盘校准(`core.ledger_adj.apply_import`)
- 自有仓可用重算 + 批次 FIFO 重建
- 脏日登记(orders_day_agg 重建) / `analysis_cache.invalidate(domain)`

演示库"看着对", 真实导入却可能错, 而且没人能提前发现。这是 `supplier_code` 那次
(§15.158)同一个教训: **绕过链路的代码不会报错, 只会静默缺一块**。

### 二、做法: 内存行 → CSV → 导入四层

新增 `routes/seed_import.py`, 每个 target 一份规格:

```python
"order": {"table": "orders",
          "cols": [... 中文导出列名 ...],       # 与 fields.ts 的 label 对齐
          "mp": {"订单号": {"target": "order_no", "type": "string"}, ...},
          "keys": ("order_no", "sku"), "agg": "sum", "key3": "barcode",
          "conflict_mode": "sum"}
```

`import_rows(target, channel, rows)` 的四步全部复用线上实现:

```
to_csv            内存行 → 按中文表头顺序输出(缺列写空串, 不跳列)
_parse_table      编码/分隔符嗅探同一函数(与用户上传一致)
_clean_rows       按 mapping 清洗类型/空值(唯一映射真源)
_write_rows       分派写入: 补码 / 键对齐 / 期初校准 / 重算 / 批次 / 脏日 / 缓存
```

**为什么中间要过一遍 CSV 文本**, 而不是内存里换个 dict: 日期是字符串还是 datetime、
数值带不带千分位、空列写不写, 这些问题只有真的序列化/反序列化一次才会暴露。
`to_csv` 负责让 `csv` 模块处理逗号/引号/换行(商品名里全都有)。

落库分配:

| 数据 | target | 切成几份 |
|---|---|---|
| 商品档案 | `product` | 按渠道 |
| 订单 | `order` | 按渠道 × 500 行一组(控制单条 INSERT 体积) |
| 库存快照 | `inventory`(自有仓) / `inventory_b`(平台仓+B仓) | 按渠道 × 仓型 |
| 出入库 | `inbound` / `outbound` | 按渠道 × 类型 |

### 三、`conflict_sql`: 键里含 `deleted_at` 时 upsert 会静默退化

`orders` 的四维键是 `(channel, order_no, sku, barcode)`, 但 `deleted_at` 参与**业务唯一键**
判定时, `ON DUPLICATE KEY UPDATE` 若不显式包含对应子句, TiDB 的处理是"命中冲突但无更新动作"
—— 写成功、数据没变。这比报错难查得多。

`_write_batch` 增 `conflict_sql` 参数: 调用方给完整子句, 优先于按表名推断的三套默认
(`sum_mode` / `inv_upsert` / `ord_upsert`)。seed 用它把"流水/批次已存在就覆盖"写全。

### 四、可用重算不再由 seed 补第二次

落账段原先再调一遍 `_recalc_own_inventory`。现在重算已经是导入链路的职责, seed 再算一遍
意味着**承认链路没生效**, 而那正是要验证的东西。改成只读核对:

```python
_assert_available_balanced(chs)   # 可用 vs 期初 + Σ入 − Σ出, 有差就留痕
```

一条聚合 SQL 出「有差额的行数 + 最大差额」, 不为 0 就写 quality_logs。

### 五、任务看守: 租约期间其它页面 / 反复切页面

后端续跑是**前端轮询驱动**的, 每推进一步服务端持一次 `lease_until` 防并发重写。
三个坑必须同时堵:

| 坑 | 现象 | 改法 |
|---|---|---|
| 驱动只挂在任务页 | 一切走就没人推进, 回来说"跑了十分钟还是刚刚" | 搬到 App 层 `api/taskWatch.ts`, 模块级 `_watches` |
| 两个页面各发一次状态请求 | 服务端只认一个, 另一个白跑并拖高在途计数 | 全局 `_inflight` 串行, 同一时刻只有一个续跑请求 |
| 租约被别人持有时硬撞 | 3s 一次空转, 烧 RU | 无进展指数退避 3s → 15s(封顶) |

单请求超时 **100s**: 必须小于网关 120s 硬上限 —— 请求被掐断而服务端仍在跑时, 租约还兜着,
下次心跳会看到真实状态; 反过来若没有超时, 一个挂住的请求会把整条链拖死。

> **租约本身是 `TTL 30s` + 每 `10s` 一次心跳 + `lease_token` 归属令牌**, 不是固定长租约。
> 固定时长无法同时满足"跑 90s 的本段不被人抢走"和"被杀了不拖住所有人" —— 因为
> 「这个请求还活着」代码自己不掌握, 只有"还在写心跳"才是活着的证据。
> 早期用过 `600s`, 于是「停止一个任务要等十来分钟」: 进程被网关切断后没人去清 `lease_until`,
> 期间所有轮询只能看到 `lease_held`, 台上却没有人在跑。现为 30s TTL, 心跳一停最多 30s 释放。

### 五之二、状态端点必须是纯读 (`probe=1`)

`/api/seed/fill/status`、`/api/cleansing/status`、`/api/cleansing/eval-status` 这三个端点
是**驱动端点**: 每被调用一次就「抢锁 → 推进一步 → 写库」。历史上前端有 6 处都在打它们
(App 层 3 个老轮询 + 清洗轮询 + 任务页 + 各业务页), 再叠加 `taskWatch` 看守 = 同一任务
5~6 个驱动源抢同一把租约。后果是用户能直接看到的:

- 抢不到锁的请求白烧 RU;
- 每个请求都进网络层在途计数 → 用户可见的忙徽标(`加载中 / 同步中`)**恒亮**,
  看起来"什么页面都在加载";
- 任务页与看守互相"以为对方在推进", 进度条不动而租约一直被占。

现在口径固定:

| 调用方 | 用法 |
|---|---|
| `api/taskWatch.ts`(唯一驱动源) | 不带 `probe`, 正常推进 |
| 其它一切"只看进度"的地方 | 必须带 `probe=1`, 纯读快照 |

`probe=1` 分支必须**早于** `mark_driver` / 抢锁 / 超时自愈等任何写操作 `return`,
否则等于没加。另外看守请求在 `client.ts` 里标为 `background`, 它的在途**不计入**
用户可见的忙徽标 —— 否则长任务在跑时, 任何页面都会显示"同步中"。

### 六、骨架后闪空态 / 「刚刚」的第二层成因

**闪空态**: `channel` 变化的 effect 先 `setTasks([])` 再置 `loading`。首个响应回来时若
任务列表真的为空, 骨架消失的同一帧就落进 `EmptyState` —— 用户看到"骨架 → 空 → 数据"
三条连续状态。

根治不是再加一个 `loadedOnce` 标记(那只是把三态拼成四态, 中间态仍能被渲染出去),
而是收敛成**单一状态机**: `phase: 'load' | 'ready'`, 转移单向; 空态与数据在同一次
渲染里二选一, 不存在"非骨架 + 空数组"的中间帧。

**「刚刚」有三层成因**, 前两层修完仍然「刚刚」, 因为第三层是语义错位:

1. 卡片读的是 `created_at`(创建时刻), 分步长跑每步推进不改它 → 差值恒 0;
2. `relTime` 解析: 无时区后缀按 `Z`(UTC) 解析差 8 小时; 已含 `+08:00` 再补 `Z` → `NaN` → 恒「刚刚」;
3. **换成 `updated_at`(进度心跳)反而更错**: 心跳一直在刷新, "距最后活动多久"永远 < 1s。

所以进行中的卡片显示的是**已运行总时长**(`now − created_at`, 由 1s 时钟驱动),
而不是"距最后一次心跳多久"; 已完成/待运行才用「N 分钟前」。

preflight 八步全绿; schema 对账 47 表 / 463 列 / 13 索引 无差异

## §15.161 非真异常连续噪音的根治: 日志通道按「正常态 / 异常态」分流(2026-11-05)

### 一、现象：空库下每分钟一条告警，且告警内容其实什么也没发生

第二集群重建为干净空库后，质量日志仍持续增长。按 source/level/message 分组核对，
主体不是故障，而是**三种正常态被送进了异常通道**：

| 日志 | 频率 | 真实语义 |
|---|---|---|
| `continue-tasks 诊断: rows=0 cutoff=...` (warning/quiet_error) | 每 60s 一条，永不停止 | 中间件周期触发续跑，空库无 running 任务 → `rows=0` 是正常空态 |
| `快照续段降级: time data '' does not match format` (warning) | 每次 dashboard 请求 | 空库 `MAX(ordered_at)=''` → `strptime('')` 必抛异常；无订单 = 无快照可续 |
| `schema v12 就绪` / `迁移完成` / `唯一键建立完成` (warning, 带 `: str: ` 尾巴) | 冷启动一次性 | 建表/迁移**成功**，却把空字符串当 `exc` 传给了异常通道 |

### 二、根因：`try_err` 被当成通用日志函数

`routes/common.py:try_err` 的契约是「静默吞异常留痕」——固定写
`level='warning' / log_type='quiet_error'`，带 traceback、同源 10s 合并计数。
它是 `except` 分支的纪律收口，**不是**「我想记点什么」的通用入口。

一旦诊断摘要、成功信息、正常空态也走它，后果不是「多几行日志」这么简单：
- 质量日志页 / Markdown 导出按 level 汇总「警告 N 条」，N 被正常态持续推高，真异常被淹没；
- 60s 周期 > `try_err` 的 10s 合并窗口，所以 `rows=0` 每条都完整落库，合并计数拦不住；
- 匿名访问部署预览域名必然 401，前端把 401/403 与网络错误/5xx 一起上报成
  `api_http_error/warning` → **每次部署都刷一批**，纯属噪音。

### 三、修法：从链路源头判空 + 通道分离，而不是压日志或降级别

没有改 `try_err` 本体一个字（真异常留痕能力必须原样保留），也没有把 warning 降成
info 来「让数字好看」。分两层：

**① 正常态不进入异常分支（链路判空）**

```
cron.continue_tasks        rows 非空才 log_info 一条摘要；空态零写入
                           (真异常仍由「续跑异常 / 整体异常」两处 try_err 留痕)
dashboard._track_data      _db2='' → 不触发快照续段(没有订单就谈不上追平)
dashboard._snapshot_step   入口判空直接 return，双保险；
                           判空放在 perf_debug 诊断之前 → 空库零写入
```

**② 正常态 / 成功态走独立通道（`log_info`）**

| 维度 | `try_err`（异常） | `log_info`（正常态/成功） |
|---|---|---|
| level / log_type | `warning` / `quiet_error` | `info` / `maint` |
| 内容 | 异常类型 + 消息 + traceback | 一句摘要 |
| 适用 | `except` 分支、降级、需人工介入 | 诊断摘要、迁移/建表成功、空态返回 |
| 失败处理 | 自身异常自吞防递归 | 同 |

`schema_create.py` 三处成功信息、`migrations/runner.py` 的迁移完成改走
`log_info` / `_log_ok`；后者的 `_log`(走 try_err) 仍专用于「失败且见证写入也失败」
等真异常。`log_type` 固定 `maint`（已在 `misc._LOG_SCOPE_TYPES` 白名单内，
字面量可被收口自检扫到，不新增类型）。

**③ 前端：预期鉴权态不是异常**

401 有专门的认证态链路（拦截器派发 `auth:may-expired` → App 调 `/auth/check`
确认后才 `setLoggedIn(false)`，冷实例偶发 401 不误踢）；403 是访客「仅可查看」
的既定行为。新增 `isExpectedAuth(status)` 单一判定，axios / `apiJson` /
`uploadRawBytes` 三处 HTTP 状态上报点统一排除；**`throw` 保留**（业务层仍感知失败），
5xx / 网络错误 / 400·422 照常上报。

**④ 门禁自身：`sql_smoke.report` 不再把诊断崩成 traceback**

前置失败（连接失败 / 覆盖率不足 / 目标库缺表）返回的三元组第三项是空串哨兵，
而 `report()` 无条件 `item["where"]` → 连不上库时崩成 `TypeError`，
把「配额耗尽 / 凭据指向错库」这个明确原因淹没在堆栈里。补 `_detail(item)`：
dict 才取 where/sql，否则留空，门禁能清楚说出为什么红。

### 四、顺带收尾：切集群的本地侧

线上 EdgeOne Production env 已切第二集群，但本地 `.env` 仍是旧集群凭据
（RU 配额已耗尽）→ preflight 的 SQL 冒烟连不上库。将 `.env` 的
`TIDB_USER/PASSWORD/DB` 对齐 `.env.local`（该文件 gitignore，不进仓库、不改线上其它键）。
CI 侧无需改动：`scripts/ci_fetch_env.py` 从 EdgeOne 线上 env 优先拉取，`FB_*` 仅作回落。

## §15.162 本地直连 vs 线上: 把「慢」量清楚, 并作废那个 182.9 秒(2026-11-06)

### 一、触发: 用一个环境相关的绝对秒数, 论证了一个环境无关的代码问题

沙箱直连跑 seed 首窗口, **2.39 万行订单 182.9 秒**, 据此下了「快速通道还不够快」的判断。
这个判断**作废**。

原因很直白: `182.9s ≈ 往返次数 × 221ms`。它描述的是「沙箱到新加坡的公网有多远」,
不是「这段代码写得怎么样」。同一份代码换个位置就换一个数字:

| 环境 | 单次往返 | 同样往返次数的窗口耗时 |
|---|---|---|
| 本沙箱(公网 → alicloud ap-southeast-1) | **221 ms** | 182.9 s |
| 线上(按 §15.120 的 57ms 估) | 57 ms | ≈ 47 s |
| 线上(按 §15.96 原写的 4ms 估) | 4 ms | ≈ 3 s |

后两行**都是估的**, 见第二节。讽刺的是 §15.96 的标题就是「本地跑得慢 ≠ 代码慢」,
而我在同一份文档里违反了它 —— 这次的教训不是"不知道", 是"知道了还照着错的做"。

### 二、今天量到的(50 次 `SELECT 1`, 直接测量, 不是反推)

| 层 | 沙箱实测 |
|---|---|
| DNS 解析 | 67~81 ms |
| TCP 握手(443/4000) | 215~370 ms, 均值 281 |
| **`SELECT 1` 往返(4000)** | **均值 221ms · P50 221 · P90 221 · min 221 · max 222** |
| 500 行 `executemany` | 232 ms |
| **2000 行 `executemany`** | **252 ms** |

`min == max` 说明这不是抖动, 是**固定公网路径延迟**, 与 §15.96 当初的观察一致
(当时 423ms, 今天 221ms —— 路径变了, 性质没变)。

线上侧只有间接观测, **不能当 RTT 用**: `GET /api/health`(含 1 次库查询) TLS 完成
325~399ms、首字节 815~1546ms, 服务端处理落在 491~1222ms 且波动极大 —— 里面混着

### 三、官方文档怎么说(计费侧印证了链路差异)

TiDB Cloud Starter 定价页, Network Egress 的 RU 计量**分两种接入方式**:

| 接入方式 | 网络出口 RU |
|---|---|
| **Public Endpoint** | **1 KiB = 1 RU** |
| **Private Endpoint** | **4 KiB = 1 RU** |

差 4 倍。这不是"快一点", 是两条不同的物理链路。配套三条约束(同页/Starter 限制页):

- egress 在 **gateway 单独计量**, `EXPLAIN ANALYZE` 看不到 —— 公网端点是**过网关**的;
- Public Endpoint 经 **AWS Global Accelerator**, 空闲超时 340s, **不能用 TCP keep-alive 保活**;
- 连接开超 30 分钟可能被服务端掐断, 官方建议连接池 max lifetime 从 5 分钟起。

这也解释了 `WBY_WORKFLOW.md:125` 那句「公网出口 1KiB=1RU、同区内网 4KiB=1RU」的来源 ——
它是官方口径, 不是项目自己的经验值。

### 四、真正可迁移的结论: 行数不是成本, 批次数才是

上面两条实测放在一起: **500 行 232ms, 2000 行 252ms** —— 行数翻 4 倍, 耗时只多 **8.6%**。
因为 221ms 全在往返, 服务端写 2000 行几乎不花时间。

这与两处历史结论是同一条规律的第三次独立验证:

| 出处 | 原话 |
|---|---|
| §15.157 | RU 按「批」计价, 与批里放多少 SKU 关系很小 |
| §15.158 | 耗时只跟查询次数有关, 跟批里放多少 SKU 关系很小 |
| 本节 | 行数 ×4 → 耗时 +8.6% |

所以 seed 提速的正确杠杆自始至终只有一个: **压批次数(往返次数)**。
不是加大批次、不是加缓存、更不是把明细折叠起来眼不见为净。

### 五、边界: 这次校正没有推翻什么

- 快速通道方向仍然对 —— 它把"每批一次的文件级动作"降成"每窗口一次", 压的正是批次数;
- 但**"能省多少秒"只能在线上端口量**, 沙箱给不出这个数;
- 沙箱的用途收窄回一条: 验「算得对不对」(四维、口径、幂等), 不验「跑得快不快」。

## §15.163 「改成导入链路后慢了几十倍」+「任务期间页面加载不出」的根因(2026-11-06)

用户两个问题，一句话各自回答：

> **① 慢**：不是"导入链路本身慢"，是链路里三处 **O(行数) 的查库动作**被放大成了
> "每 500 行全表扫一遍 / 每 2000 行回读一次 / 17 万行写三遍"。
> **② 加载不出**：不是并发竞态，也不是 DB 连接打满 —— 是一个 5.6MB 的响应把
> 共享缓存顶穿 TiDB 单条 6MB 上限，于是**每个请求都重算两遍**，把实例和连接池一起堵死。

下面是量出来的证据与改法。凡是没直接测到的，本节明确标"未测"。

### 一、把"慢"拆开：每一段多贵，是测出来的不是猜的

沙箱直连 TiDB（公网 221ms 往返，见 §15.162），所有数字已扣除/标注往返。

| 动作 | 实测 | 服务端净耗时 | 说明 |
|---|---|---|---|
| 2000 键点查（全不命中） | 0.24 s | ~0.02 s | 纯往返，便宜 |
| 2000 键点查（全命中，取 4 列） | 0.68 s | ~0.46 s | 回表 2000 行，0.23ms/行 |
| INSERT 2000 行 | 0.33 s | ~0.11 s | 写不是瓶颈 |
| INSERT 10000 行 | 1.24 s | ~1.0 s | 0.1ms/行，线性 |
| to_csv + _parse_table + _clean_rows（2000 行订单） | — | **0.035 s** | 纯 CPU，全程 441k 行 ≈ 8 s |

**第一条被证伪的猜想**：不是"CSV 往返把时间吃掉了"。441,913 行订单的 CSV 序列化 + 解析 +
清洗合计只有 ~8 秒，占比 2.6%。§15.160 引入的"真 CSV 往返"设计是对的，不该回退。

**真正的三块开销**，全部是"每批一次 × 批次数"：

#### 1) 69 码多码证据：每 500 个 SKU 全表扫一次

`cleanse_write._fill_barcode_from_products` 里有一条证据查询：

```sql
SELECT sku, COUNT(DISTINCT barcode) FROM `orders`
WHERE sku IN (…500 个…) AND barcode<>'' GROUP BY sku
```

EXPLAIN 实测（线上库）：

| 表 | 计划 | 规模 |
|---|---|---|
| orders | **IndexFullScan** `uq_orders_biz(channel,order_no,sku,barcode)` | 扫 **441,373** 条索引项 |
| batches | **TableFullScan** | 扫 **180,579** 行 |
| inventory | IndexRangeScan（`uq_inventory_biz` 的最左就是 sku） | 正常 |

原因很直白：orders 的唯一键把 `sku` 放在**第三位**，`sku IN (...)` 用不上最左前缀。
而这条查询在订单导入里 **每个窗口的每个 500 行批次**都要发 3 条（inventory/orders/batches），
一个窗口 1 万 SKU = 20 批 × 3 = 60 条，6 个窗口 = **360 次全表扫**。

**改法（语义等价）**：这条证据只服务于两个分支 —— "档案缺码"和"本行缺码"。
档案有码、本行也有码时，结论算出来根本没人读。于是：

```python
_no_code = {r["sku"] for r in cleaned if not r["barcode"].strip()}
_need    = [s for s in _skus if (not _amap.get(s)) or (s in _no_code)]
_probe   = [s for s in _need if s not in _probed]     # 只查"会被读到"的
```

实测（同一批真实档案）：全码批次 **4 条查询 → 1 条**（只剩档案查询）；
含缺码行的批次仍是 4 条，且判定结果逐行不变（`效期管理=yes/多码=是` → 留空，与改前一致）。
配套补了覆盖索引 `(sku, barcode)`（orders / batches），把剩下那部分从全表扫压成 500 个索引区间。

#### 2) 订单四维键预读：每条 2000 行都要回读一次库

`_align_order_keys` 每批发一条 `order_no IN (2000)` 的回读。这条本身是对的（防"同一笔订单
因为码变了分裂成两行"），但它是 **O(批次数)** 的固定成本：441k 行 / 2000 = 221 次。
命中 0.46s、不命中 0.02s —— 首次灌库时表是空的，所以它几乎全是"白查"。

**没动它**。原因：`prev` 同时承担三件事（补码、空码升级、旧日期重建 agg），
任何"跳过"的写法都要在三种场景下重新证明等价，收益却只有首次灌库这一条路径上的几十秒。
先把 ①③ 做完再量，不够再动（§15.162 的教训：不要用推理代替测量）。

#### 3) 月汇总：同一批 17 万行被写了三遍

原实现 = `UPDATE inventory SET month_*=0 WHERE channel IN (jd,other)`（全表清零）
\+ 入库 `UPDATE ... JOIN` + 出库 `UPDATE ... JOIN`。线上该段 **325 s**（含两次 504 重试）。

改法：一条语句 LEFT JOIN 两张聚合表，两列一起写，且

```sql
WHERE i.channel=%s
  AND (i.month_inbound<>COALESCE(fi.q,0) OR i.month_outbound<>COALESCE(fo.q,0))
```

"没流水的行要归 0"没丢 —— LEFT JOIN 出 NULL，`COALESCE(...,0)` 就是 0，老值非 0 照样写回。
只是现在只为"真的变了"的行付费。**已在线上库空跑验证：jd 0 行 / other 0 行，各 0.7~0.9 s**（数据本就正确）。

### 二、把"加载不出"拆开：一条 5.6MB 的响应拖垮了整个实例

先给结论，再给证据：**不是竞态，也不是 TiDB 连接被打满，是队头阻塞。**

#### 证据 1：连一条 `SELECT` 都超时，说明卡在排队而不是算不动

`quality_logs`（11:42 那一分钟，用户正在切页面）：

```
严重慢请求: GET /dashboard/aux 15.6s / 19.0s
timeout of 45000ms exceeded /api/orders?page=1&page_size=30&…
timeout of 45000ms exceeded /api/tasks?channel=jd&limit=8
timeout of 90000ms exceeded /api/insights/replenishment?…
Network Error /api/dashboard/stock-risk?…
```

`/api/tasks` 是 `sync_tasks` 上一条 `ORDER BY id DESC LIMIT 8`，毫秒级；
`/api/orders` 是 `idx_orders_ch_id` 上的 30 行分页。它们超时，只能是**前面有东西占着**。

#### 证据 2：库侧连接只有 12 条 Sleep

```
SELECT COUNT(*) FROM information_schema.processlist → 13（含自己）
command: Sleep 12 条，最长空闲 421s
```

TiDB 没被打满，`DB_POOL_LIMIT=10` 也没被饿死。问题在**每个请求要占着连接好几秒**。

#### 证据 3：aux 自己就 5.6MB，且缓存永远写不进去

```
GET /api/dashboard/aux → 5,648,116 B / 9.56 s
  ownHealth   5,998,436 B   items: 13,615   ← 全部明细
  alerts         35,883 B   (100 条)
  stockOverview  26,820 B   (100 条)
```

写共享缓存时：

```
cache_error: cache_get 降级直算[dash_aux|jd|bbcc]:
  (8025, 'entry too large, the max entry size is 6291456, the size of data is 6835645')
```

**这一条把三件事串起来了**：

1. `own_health(channel, full=1)` 返回**全部** 13,615 条（7,143 积压 + 5,256 效期 + 1,216 缺口）；
2. 6.8MB > TiDB 单条事务 6MB 上限 → `cache_put` 抛错；
3. 抛错被 `cache_get` 的 `except` 接住 → 删 key → 记 `cache_error` → **`return builder()`**，
   也就是**再算一遍**。于是每个请求 = 2 ×（own_health 的 9 条 SQL + 1.3 万条 Python 组装）≈ 9.5s。

再叠加"seed 每个窗口 `invalidate("all")`"——缓存永远是冷的。多个页面同时进来，
每个都在算 5.6MB，同一实例上其它接口（含 `/tasks`）只能排队 → 45s 超时 → 用户看到"加载不出"。

#### 为什么不是"并发/竞态"

- 竞态那部分在 §15.161 前已经收口：`probe=1` 纯读、租约心跳、`_LAST_CONT` 限频，日志里
  没有一条"抢锁/双写"痕迹；
- 真正串行化的是**连接与实例**：`DB_POOL_LIMIT=10` + `_acquire()` 阻塞等 20s，
  10 条连接被 10 个"重算中的看板请求"占满后，第 11 个请求连 SQL 都发不出去；
- 而重算本身是被上一条（缓存写不进）逼出来的 —— 因果链是
  **明细塞进聚合响应 → 缓存失效 → 每请求重算 → 连接被长时间占用 → 队列堵死**，
  不是两个请求抢同一份数据。

## §15.164 §15.163 遗留两项的排查结果(2026-11-06 下午)

### 一、`_align_order_keys` 每批回读：实测只占 4%，不改

先把成本量准（线上 44 万行，按 `(channel, order_no)` 索引前缀，2000 个键/批）：

| 场景 | 沙箱实测 | 扣掉两次往返(0.45s)净耗时 | 线上折算(往返 57ms) |
|---|---|---|---|
| **命中**，取 4 列（现状） | 0.649 s | **0.199 s** | ≈ 0.26 s |
| **命中**，取 3 列（去掉 `ordered_at`） | 0.244 s | **0.000 s** | ≈ 0.06 s |
| **不命中**，取 4 列 | 0.232 s | 0.000 s | ≈ 0.06 s |

关键在第三行：**首次灌库根本不会命中**（seed 的 `order_no` 全局唯一、递增），
所以那 221 次预读几乎全是"白查"——221 × 57ms ≈ **13s**，占 303s 订单段的 **4.2%**。

第二行看起来很美（去掉 `ordered_at` 就走 `uq_orders_biz` 覆盖索引、零回表，
命中场景 0.26s → 0.06s，重复灌库能省 44s），但 `ordered_at` 是"旧日期重建"的唯一来源：
upsert 可能把一行挪到新的业务日期，**旧日期的物化 agg 必须一起重建**，否则旧日期留着
这份数据 → 双计。两段式（先查 3 列、命中后再补查日期）是 2 次往返 + 回表 = 0.31s，
比现在的 1 次 0.26s 更慢。

> **结论：不动。** 它既不是"慢几十倍"的原因（4.2%），改它又要拿正确性换 0.2s/批。
> 真要动，得先给 `orders` 加一个 `(channel, order_no, sku, barcode, ordered_at)` 的宽覆盖索引
> —— 但那等于把 `uq_orders_biz` 再存一遍，写入侧要为每次导入多维护一份索引，不划算。

### 二、`_build_aux` 冷算 6~9s：拆成四路并行，并把白传的列砍掉

先纠正 §15.163 的一句含糊话("ownHealth 占大头")——**用块级计时量出来的实际占比**是：

```
own_health 单算(热)      3.55 s    ← 4 条大查询 + 5.6 万行组装
_build_aux 整包(热)      8.5~9.6 s  ← 其余 5s 在 alerts/库存概览/低库存判定
```

也就是说 ownHealth 占 **~40%**，不是"绝大部分"。剩下 60% 是另外三段。

#### 为什么是这四段并行

`_build_aux` 里的四段**彼此没有任何数据依赖**，只是按代码顺序排下来串行：

| 段 | 内容 | 查询数 |
|---|---|---|
| 告警组 | 低库存 200 条 + 其他告警 300 条 + 分组计数 + 仓库名回填 | 3~4 |
| 库存概览 | 缺货计数 / 缺货清单 100 条 / BC 合计缺货 | 3 |
| 低库存判定 | `get_sales_digest` + 补货配置 + 9,895 行库存逐行算动态安全线 | 3~5 |
| 自有仓健康 | 4 条大查询(10,100 + 10,000 + 20,093 + 15,496 行) | 6~8 |

改成 `ThreadPoolExecutor(max_workers=4)`（与 `_build_summary_agg` 的并行池同一套写法——
线程在 EdgeOne 运行时**已经验证可用**，不是新引入的能力）。峰值 4 条连接 < `DB_POOL_LIMIT=10`，
不挤占同实例上的其它请求。每块内部 `try/except` 独立降级，一块失败只退化成自己的空结构。

#### 顺带砍掉"取了但没人读"的列

`dashboard_own_health` 里有两条查询在传**从未被读的列**：

| 查询 | 原取列 | 实取 | 白传量 |
|---|---|---|---|
| `products` | `sku, product_name, barcode, supplier_code, expiry_managed` | 前两项 + `expiry_managed` | 10,000 行 × 2 列 |
| `batches` | `… exp_date, qty` | `… exp_date` | 15,496 行 × 1 列 |

`pmap` 只读 `product_name` / `expiry_managed`，`_pick_batch` 只读 `batch_id/barcode/warehouse/exp_date`。

#### 实测

| | 沙箱（往返 221ms） | **线上（supplykit.top，已部署实测）** |
|---|---|---|
| 改前整包 | 10.60 s | 6~9 s（§15.163 记录） |
| 改后整包·冷算 | **8.52 s** | **3.11 s**（清缓存后首请求） |
| 改后整包·命中 | — | 1.53~2.44 s |

响应体 62,351 B，`ownHealth` 仍是 9 条 / total 13,615、`alerts` 100 条、计数 120，
与改前一致；工作区另存了新旧输出的逐字段 diff（67,644 B 时点）——**无差异**。

> **必须一起看的基线**：同一时段 `/health`（219 B、几乎不查库）实测 **0.86~1.51 s**。
> 也就是说线上一次请求里约 **1 s 是 EdgeOne 函数冷启动 + 边缘路由**，与业务无关。
> aux 命中缓存的 1.5~2.4 s 里，扣掉这 1 s，**数据侧只剩 0.5~1.4 s**。
> 用户说的"切页面加载不出"，有相当一部分是这个基线，不是查询慢 —— 这一点
> §15.163 当时没量基线，容易把两件事混成一件。

> **诚实说明**：沙箱这一版只降到 8.5s（-20%），不是数量级。因为剩下的成本是
> **6.5 万行的传输 + Python 组装**，不是往返次数——先前的假设"串行往返是大头"是错的，
> 这次量出来才看清。要把 6~9s 压到 1s 级，只能把三类判定下沉成一条 SQL
> （CTE + 窗口函数 Top-N），但那会把 `pick_ds` / `rolling_predict` 这两条**单一真源**
> 复制成第二份，口径漂移不会报错、只会在某个页面悄悄偏掉。**这是口径决策，不是性能决策**，
> 留给定案后再做。

### 15.127 安全三件事的"能不能根治": 分别给出终态, 而不是一句"待人工"(2026-11-03)

> 起因: 用户把 `security.md` 里三条"已知未覆盖"摘出来问 —— `X-Auth-Token` 是被迫的、cron 弱校验、
> git 历史 blob 扫描靠人工复查, **能不能彻底解决**。
> 结论先说: 三条**性质完全不同**, 混在一起谈就会得到"都要人工"这种没用的答案。
> 本节把它们分清: 一条可自动化(历史)、一条是平台终态(认证头)、一条只能治"危害"不能治"鉴权"(cron)。

#### 一、先分类: 三种"根治不了"不一样

| 问题 | 真实约束 | 能根治什么 | 不能根治什么 |
|---|---|---|---|
| 认证头 `X-Auth-Token` | 网关改写 `Authorization` | 消除不确定性(删回退) | 让标准头可用 —— 应用层改不了网关 |
| cron 弱校验 | 平台 schedules 无 header 能力 | **危害**(重复执行/RU/骚扰) | **鉴权**(物理上无处放凭据) |
| git 历史扫描 | 无(此前判断错了) | 全部 —— 脚本 + CI 定时 | 无 |
| 平台侧密钥存储 | 平台托管 | 最小化 + 轮换 + 不外泄 | 平台日志是否泄露值 |

**教训**: 被列为"需人工复查"的项, 先问一句"规模到底多大"。历史扫描当初写"受 refs 异常限制",
实测 164 个 blob 扫描 3.4 秒 —— **"太大了只能人工"经常是没量过的托词**。

#### 二、git 历史扫描: 从"建议人工 `git log -S`"到 CI 每次跑

`scripts/audit_secrets.py` 新增 `scan_history()`, 三个面:

1. **commit message** —— 密码进提交信息是真实发生过的(2026-10-17 新集群密码), amend 只改当前树;
2. **全部历史 blob** —— 按 sha 去重, 跳二进制/超大文件, 跑 HIGH+MED 模式;
3. **reflog 脱分支提交** —— `reflog` 有但 `rev-list --all` 没有的(amend/reset 残留)。

配套 CI(`.github/workflows/preflight.yml` 新增 `secrets` job): `fetch-depth: 0` + 浅克隆直接报 error
+ **每周一 01:00 UTC 定时重跑**。这条定时很关键 —— 密钥审计是"会随时间腐化"的检查(依赖轮换/平台变更),
只在有人推代码时才看, 等于没做。

**实测结论(2026-11-03)**:

| 面 | 范围 | 结果 |
|---|---|---|
| 本地历史 | 51 提交 / 424 blob / 脱分支 0 | 无命中 |
| 远端可达历史 | 120 提交(最早 2026-10-30) message | 无命中 |
| 当前树 | `git ls-tree -r HEAD` 敏感文件名 | 无 |

> 本地是**浅克隆**(`.git/shallow` 存在), `github.com:443` 不可达 → 无法 `--unshallow`。
> 所以"完整历史"由 CI 保证, 本地扫描只算快速预检, 脚本会显式打印告警。

#### 三、写审计脚本时踩的坑: 报告本身会泄密

初版跑出来直接把两种情况的原值打到了终端(下面按现在的脱敏规则还原成示意, 不写真实片段):

```
✗ .env:9 [MED] JWT 密钥: JWT_SECRET=xxxx***(实际长度)
✗ .edgeone/auth.json:3 [HIGH] GitHub PAT: "GITHUB_TOKEN": "xxxx***(实际长度)"
```

写这一节时还踩了第二次: 我最初把上面两行**原样**贴进了本文, 下一次 `audit_secrets.py`
立刻把 `docs/DEVELOPMENT.md` 自己报成"硬编码密钥 2 处" —— 公开仓库里的文档当然也算源码。
这个自查正好证明脚本有用(它扫的是整个工作区, 不是白名单), 也说明"脱敏"要脱到底:
**连举例都不能用真实片段**, 否则文档本身就是泄露源。

**这比不扫更糟** —— 把泄露面从 git 搬到了 CI 日志/终端历史/对话记录。三处修正:

1. `SKIP_DIRS` 加 `.edgeone/`; `_walk()` 跳过 `.env*`(模板除外) —— 它们是**密钥本体**,
   该不该存在由"是否入库"来管([2] 段), 不是"硬编码"([1] 段);
2. `_redact()` 脱敏: 命中值只留前 4 位 + 位数;
3. `_looks_placeholder()` 抑制误报: 空值(`JWT_SECRET=`)、变量拼接(`'Auth-Token: ' + AT`)、
   `os.environ.get(...)` 这类取值语句都不算硬编码。

**通用原则**: 安全工具的**输出**和安全工具本身同等重要。凡是要打日志/打终端的疑似密钥,
一律先脱敏 —— 包括报错信息里的 DSN、请求头、堆栈参数。

#### 四、cron: 换问题 —— 从"谁在调"到"现在该不该跑"

平台约束是硬的(schedules schema 无 headers / payload 不插值 / `edgeone.json` 公开),
所以**鉴权做不了**。但攻击者真正想要的是"让它执行", 那就守执行:

第四个锁是本次新增的 **时间窗守卫** `_off_window(task)`:

```python
_SH_TZ = timezone(timedelta(hours=8))     # 容器在新加坡, 不能依赖 TZ
_WINDOWS = {"archive": (0, 30, 4, 0), ...}  # (起时,起分,止时,止分) CST
def _off_window(task):
    w = _WINDOWS.get(task)
    if not w:
        return None                        # 未登记 → 放行(ping/continue_tasks/agg-sweep)
    now = datetime.now(_SH_TZ)
    cur = now.hour * 60 + now.minute
    return None if w[0]*60+w[1] <= cur <= w[2]*60+w[3] else {"skipped": True, "reason": "窗口外"}
```

9 个重任务接入(snapshot/freshness/archive/cleanup_logs/daily_rules/recycle/push_alerts/reconcile/ledger_close);
窗口外**一行 SQL 都不发**(直接 return, 零 RU)。

**窗口边界不是拍脑袋, 是查出来的**。查 `pipeline_runs` 最近 40 条:

```
archive       17:04:03 UTC = 01:04:03 CST   (配置 01:05)
cleanup_logs  19:04:02 UTC = 03:04:02 CST   (配置 03:05)
freshness     19:09:00 UTC = 03:09:00 CST   (配置 03:10)
snapshot      19:34:01 UTC = 03:34:01 CST   (配置 03:35)
daily_rules   20:04:01 UTC = 04:04:01 CST   (配置 04:05)
```

**六个任务一致地早 57~60 秒** —— 平台按分钟取整 + 排队。所以窗口两端各留 ≥1.5 小时,
既不会被 1 分钟偏差误杀, 也不会把大半天都算"窗口内"。

**两个不能设窗的**(容易被后人"补齐"时误伤, 已写进注释):
`ping`(保活, 全天无害)、`continue_tasks`(**被 `index.py` 请求驱动直接调用**, 设窗会连带打死续跑)。

**回归覆盖**(新增 5 条): 窗口表覆盖 8 个任务 / archive 边界值 / ping+continue 放行 /
当前时刻判定与区间一致 / **8 个任务都真接了守卫**(扫源码断言, 防"加了任务忘接窗"的静默失效)。

#### 五、`X-Auth-Token`: 定案为终态, 并给出重估条件

删掉 Bearer 回退这件事要写清理由, 否则后人会觉得"兼容一下更友好":
**回退会让"是否 401"取决于该请求是否被网关改写 → 变成随机现象**, 排障成本远高于兼容收益。

同时给出 30 秒验证法(`docs/decisions/0001`): 用 Bearer 打一次 summary,
401 = 网关仍在改写(维持现状); 200 = 平台变了, 可以评估切回。**没有验证方法的"终态"就是懒惰。**

#### 六、平台侧密钥: 承认不可控, 只做三件能做的

最小化(env 只放 12 个必需项, 审计脚本 [4] 段自动列出) / 不外泄(禁 `env ls`) / 轮换(5 步,
含"改完必须重新部署 —— env 是部署时快照"这一最易漏的点)。轮换步骤写进 `docs/security.md` C 节。

#### 七、CI 才暴露的那个 bug: 浅克隆测不出完整历史

本地扫 424 个 blob 全绿, 推到 CI 后 `secrets` job 直接崩:

```
UnicodeDecodeError: 'utf-8' codec can't decode byte 0x82 in position 98
  File "scripts/audit_secrets.py", line 219, in scan_history
    text = _git("cat-file", "-p", sha).stdout
```

`subprocess.run(text=True)` 默认严格 utf-8 解码, 而 `cat-file -p` 会吐**二进制 blob**
(图片/字体/压缩包)。本地历史干净(只有文本), 所以一次都没触发; CI 是完整历史, 第一个二进制
blob 就炸。修法: `_git()` 统一 `errors="replace"` —— 替换字符不影响匹配(密钥都是 ASCII)。

**这条值得记的不是修法, 是"本地通过 ≠ 完整历史通过"**: 凡是**只在 CI 才有完整输入**的检查
(历史扫描 / 全量数据 / 跨分支依赖), 本地绿灯只能算预检, 必须看 CI 结果才算数。
也说明把审计放进 CI 是对的选择 —— 放本地的话, 这个 bug 会一直潜伏到某天有人完整 clone。

否则"记录泄露"本身变成新的泄露。这条已写进 `docs/security.md` 与 SKILL 第 9 节。

### 15.128 规则变更链路上的三个「看起来做了、其实没做」(2026-11-03, D4/D5/D8 根治)

11-02 的架构审计列了 9 个断点(D1~D9)。S0~S2 把 D1/D2/D3/D6/D7/D9 都落了地, D4/D5/D8 却从
《改动优先级》的 21 条里消失了 —— 既没做, 也没写"为什么不做"。这不是排期问题, 是**合并去重时丢了**。
本次按"影响面 → 可观测 → 状态机"的顺序补齐, 并顺手把对账扩到四维。

#### 一、D4: 改一条规则 ≠ 跑一整套每日任务

原实现: `create_rule` / `update_rule` / `restore` / 批量操作, 全都调 `_schedule_rule_eval()`,
而它无条件执行 `run_daily_rules()` —— 那个函数是**完整的每日任务**:

| 步骤 | 成本 | 与"改了一条规则"的关系 |
|---|---|---|
| 孤儿清理 3 条全表 UPDATE | 扫全表 alerts | 只有第 1 条有关 |
| 旧 SKU 级清理 / 无需求兜底 | 全表 + 3 个 NOT EXISTS 子查询 | 迁移性清理, 一次即可 |
| 全渠道 × 10 万行库存评估 | 最贵的一步 | 只需**本渠道 × 本 alert_type** |
| 批次四维对账(全表 HAVING) | 扫 inventory × batches | 无关 |
| 健康快照 + risk_summary | 每渠道 2 次聚合 | 按天唯一, 每日一次就够 |

用户改个错别字, 要付上面全部代价; 而且**改完还不知道跑没跑完**。

根治分三层, 缺一层就还是"小修小补":

**① 影响面判定(要不要评)** —— `_changed_materially(d, old)` 比较**规范化后**的值:

| 变更字段 | 是否影响告警集合 | 处理 |
|---|---|---|
| `condition` / `params` | 是(命中条件变了) | 重算 |
| `is_active` / `channel` / `mode` / `event` / `alert_type` | 是(参与范围变了) | 重算 |
| `name` / `alert_title` / `alert_desc` / `severity` | 否(只影响展示) | `_sync_rule_text()` 一条 UPDATE 同步存量告警 |

JSON 比较必须先 `json.loads` 再 `dumps(sort_keys=True)` —— 否则用户"点开又保存"(键序/空格变化)
会被误判成实质变更, 等于没优化。

**② 评估范围(评多少)** —— `run_daily_rules(channels, deep, alert_types)` 三参数:
- `channels` 收窄渠道, `alert_types` 收窄到受影响规则, `deep=False` 跳过 3 条全表 UPDATE、
  批次对账、健康快照。
- `evaluate_stock_skus(only_ats=...)` 在**规则加载之后、评估之前**过滤三组规则(日/库存/订单)。
- **安全性靠既有设计保证**: "未命中即关闭"只针对 `_evaluated_ats`(本次实际评估过的 alert_type),
  被过滤掉的规则不在集合里 → 绝不会因为"没评它"而把它的告警批量关掉。这一条不成立的话,
  收窄范围就是灾难, 所以回归里专门盯了它。

**③ 执行与等待(什么时候算完)** —— 见 D5。

**实测对比**(线上 `pipeline_runs` / `eval_tasks`, 2026-11-03):

| 场景 | 耗时 | 说明 |
|---|---|---|
| 每日全量 jd | **4119ms** | 2:51 那次, 全规则 + 全渠道循环 |
| 每日全量 other | **4206ms** | 同一轮, 两渠道合计 ≈ 8.3s |
| 浅档(单规则 d8_probe, jd) | **420ms** | 含 10 万行库存扫描; 约为全量的 1/10 |
| 文案类保存 | **~0 评估** | 只发一条 `UPDATE alerts SET title/description/severity` |

注意 8.3s 还只是"评估"本身 —— 原来的保存路径还要叠加 3 条全表 UPDATE、批次对账与健康快照,
而这三块的代价都不在 `rule_eval` 的计时里。

#### 二、D5: 从"猜 N 秒"到"任务可查询"

原实现用 `eval_pending` 单行脏标记。标记只能回答"要不要跑", 回答不了:

- 跑了没有? 跑了多久? 影响多少行? 失败了吗?
- 前端保存后该等谁? 只能 `setTimeout(2000)` 猜 —— 猜短了看到旧数据, 猜长了白等。

新建 `eval_tasks`(id / scope / status / rows_out / duration_ms / error / 三个时间戳):

```
保存规则 → INSERT eval_tasks(scope={"channels":["jd"],"ats":["low_stock"],"deep":false})
        → 返回 eval_task_id
后台线程 → UPDATE status='running' WHERE status='pending'   ← 抢占, 多实例只有一个成功
        → run_daily_rules(**scope) → status='done' / 'error'
前端     → GET /api/rules/eval-status?task_id=N 轮询 → done 才 dispatch('rules-changed')
```

三个细节:

1. **合并**: 同 scope 且仍 pending/running 的任务直接复用 id。用户连点三次保存只评一次,
   前端轮询的也是同一个任务 —— 不会出现"三个任务排队、每个都扫 10 万行"。
2. **不阻塞**: 线程用 `_WORKER_ON` 保证同时只有一个; 退出前再查一次 pending, 防止
   "刚退出又来了新任务"导致任务躺到下次保存。
3. **兜底**: 轮询 20s 未完成 → 前端不再等, 但看板 `aux.evaluating=true` 会显示"规则重算中"
   并每 4s 自动重拉(最多 6 次)。**两个机制都要有** —— 只有轮询, 用户切页就断了;
   只有 evaluating, 用户要盯着看板等。

`aux.evaluating` 必须在**缓存之外**读: 进了 60s 缓存就会出现"评估完了还显示重算中",
或者"开始评估了还显示已完成"。

#### 三、D8: 11 个关闭入口 → 一个状态机

原状态: 11 处 `UPDATE alerts SET status='inactive'`, 各写各的 WHERE。三个后果:

1. **答不了"这条为什么没了"** —— 没有 `closed_reason`/`closed_at`。
2. **关了又开 = 插新行** —— 写入侧是"查 active 去重, 没有就 INSERT"。告警被关后再次命中,
   插入全新行 → 同一格库存在表里反复增殖, **抖动频次永远数不出来**。
3. **维度键散落** —— 去重键在 `core/rules.py` 写一遍、关闭条件在各路由再写一遍, 少一维就误关
   (典型: 按 SKU 关掉所有仓, 而实际只有 B 仓恢复)。

新建 `core/alert_lifecycle.py`, 把三件事钉成单一真源:

```python
ALERT_DIM = ("alert_type", "related_sku", "warehouse", "channel", "barcode")
```

**为什么是这 5 维**: 前 4 维与库存/批次的四维对账同构(渠道 + SKU + 69码 + 仓), 第 5 维
`alert_type` 是"问题种类"。`warehouse_type` 刻意**不进**身份 —— bc 合计行与 own 明细行
可能同 SKU 同仓名, 但仓型是判定产物, 不是身份。

| 能力 | 实现 | 解决什么 |
|---|---|---|
| `close(cond, params, reason)` | 统一 `SET status, closed_reason, closed_at` | 11 处入口全部改调; reason 是稳定枚举(13 个) |
| `close_by_ids(ids, reason)` | 评估未命中场景(命中集已在内存) | 免去再拼维度条件 |
| `open_or_reopen(dim, fields)` | 同维度取最近一行: active→只刷展示; 已关→**重开**(`reopen_count+1`); 无→插入 | 抖动不再增殖, 且次数可数 |

写入侧两处(`_action_create_alert` 单条、`evaluate_many` 批量)都改了。批量路径的取舍:
**只预载近 7 天已关闭维度**。原因: 全量拉历史关闭行会把结果集拉大; 7 天外的重开按新行插入,
语义上可接受(那条告警已经"冷"了)。这不是妥协, 是给"抖动"下了定义 —— 抖动是短周期现象。

**回归门禁**: 全库扫描, 任何 `UPDATE alerts ... status='inactive'` 不带 `closed_reason` 即失败。
这条断言比人工 review 可靠: 新增关闭入口的人不一定会读这个模块的 docstring。

#### 四、四维保障: 对账从 2 段扩到 4 段

用户要求"保障数据四维"。原 `run_reconcile` 只有日销总量 + GMV 两段, 都是**汇总级**:
总量相等但个别维度错位时发现不了。

| 段 | 断言 | 能发现什么 |
|---|---|---|
| ① 日销 | Σ快照 order_count == Σ订单 quantity | 整体漏算/重复 |
| ② GMV | agg.gmv/cnt == 源表重算 | 金额口径漂移(10-29 那次 +72% 的类型) |
| ③ **告警四维** | active 低库存/补货告警的 (渠道,SKU,69码,仓) 必须存在于 inventory | 孤儿告警(关闭链路漏了一条) |
| ④ **快照抽样** | 近 7 天量最大的 50 个 (渠道,SKU,69码) 逐个比对 | 总量相等但个别 SKU 错位 |

③ 用一次 LEFT JOIN 扫完(零 N+1), ④ 用两个聚合子查询 + LEFT JOIN(有
`idx_snapshot_ch_date_full` 与 `idx_orders_ch_ordered_at` 支撑)。两段都进
`cron/reconcile` 的每日档, 差异写 error 日志进质量页。

#### 五、踩坑: 浅档路径两次 NameError —— 本地测不到的"块跳过"缺陷

`evaluate_stock_skus` 里有一段"计算变量注入", 包在 `if _need_calc:` 里。每日全量时它总为真
(内置断货/健康规则引用了 `inv.adj_dos` 等计算变量), 所以**从来没有被执行过"跳过"分支**。
`only_ats` 过滤后, 探针规则不引用任何计算变量 → 整块跳过 → 但块内初始化的
`_exp_map` / `_prod_sup` 在下面 ctx 构造时是**无条件 get** 的:

```
线上探针第 1 次: local variable '_exp_map' referenced before assignment (390ms)
修完第 2 次:     local variable '_prod_sup' referenced before assignment (429ms)
第 3 次:         done (420ms)
```

两次是同一个根因的两个实例。教训不是"再补一个变量", 而是:

1. **改动"可能被跳过"的分支时, 要用 AST 或脚本把该块内 `Store` 的名字与块外 `Load` 求交集**,
   而不是撞一个补一个(我第一次只补了 `_exp_map`, 第二次才被 `_prod_sup` 打脸)。
2. **本地 mock 测试覆盖不到这种路径** —— `local_test` 的 fake_query 让 `rows` 为空直接 return,
   走不到 ctx 构造。所以门禁改成源码顺序断言: 四个映射的 `= {}` 必须出现在 `if _need_calc:` 之前。
3. **线上探针比"部署 Success"有用**: 三次探针把"路由/表/任务/评估"整条链跑通,
   每次失败都精确到变量名。探针规则 `is_active=0` + 条件恒假(`available_qty < -1`),
   不产生任何告警, 用完即删。

#### 六、踩坑: `%` 格式化把占位符吃了

`close()` 初版写成:

```python
sql = "... WHERE status='active' AND (%s)" % cond   # cond 自身含 %s
```

`cond` 里有 2 个 `%s`, 加上 SET 侧的 2 个 → 格式串共 4 个占位符, 只给了 1 个参数 →
`TypeError: not enough arguments for format string`。动态用例当场抓到。

教训: **拼 SQL 时, "模板"和"参数"必须分开** —— 要么全部用 `+` 拼接, 要么参数化到底;
用 `%` 把一个含占位符的片段"塞进"另一个模板, 等于让两层占位符互相干扰。
`open_or_reopen` 的 UPDATE 也踩了同一个坑(SET 片段含 `%s`), 一并改成 `+` 拼接。

#### 七、回归

363 → **378**(+15): D4 四条(三参数/浅档跳过/only_ats/文案不评估)、D5 四条(表结构/接口/缓存外读/前端轮询)、
D8 六条(维度键/统一写 reason/重开不新增/全库无裸关/参数顺序/重开走 UPDATE),
外加"浅档映射先初始化"一条(线上 390ms 报错的复现门禁)。
其中"全库无裸关"是**扫描型断言**, 新增第 12 个关闭入口时会立刻变红。

### 15.129 全局提示的四条通道、两个断点与一个操作态(2026-11-03)

D4/D5/D8 做完后, "保存规则 → 看板告警变"这条链在**服务端**闭环了, 但**客户端**还有两个断点:
一个让提示从来没显示过, 一个让联动必然漏。本节把提示体系从"各页手写"收敛成"一个出口 + 一个操作态"。

#### 一、先数清楚有几条通道

| 通道 | 实现 | 作用域 | 表达什么 |
|---|---|---|---|
| Toast | `components/Toast.tsx` | 当前页(切页即清) | 操作回执(成功/失败/撤销) |
| header 胶囊 | `syncing` + `syncOld` | **跨页常驻** | 前端正在取数(同步中/加载中) |
| 任务卡 | `TaskPage` → `/api/tasks` | 仅任务页 | 后端长任务进度(清洗/导出/种子/重置) |
| 事件总线 | `rules-changed` / `insights-refresh` / `orders-changed` / `seed-done` / `custom-fields-changed` | 已挂载页面 | 触发重拉(不携带数据) |

四条通道各管一段, 没有任何一条能回答"后端还在算, 但我已经离开那个页面了"。

#### 二、断点一: App 顶层调用 `useToast()` 拿到的是 no-op

`ToastProvider` 挂在 App 的 **return 里**(`App.tsx:890`), 而 App 自己、以及它顶层的全局任务轮询
都在 Provider **外面**。`Toast` 模块的默认值就是全套 no-op(注释写着"Provider 外调用不崩") ——
于是这十处调用**全是空操作**:

```
种子数据填充完成 / 数据清洗完成 / 数据重置完成 / 导出完成
种子填充失败 / 数据清洗失败 / 导出失败 ...
```

用户看不到失败, 只能自己去任务卡里猜。这不是"提示样式"问题, 是**通道断了**。

修法: `api/notify.ts` 做一个极薄的注册表, Provider 挂载时 `bindNotify({success,error,...})`,
卸载时置 null; 任何模块(含 App 顶层、mutate、store)都走 `notify.*`。组件内继续用 `useToast()`
(它还能拿到 duration:0 / action 撤销这些高级能力), 两者底层是同一个 `add()`。

#### 三、断点二: "提示 + 清缓存 + 发事件"三件套靠手写, 必然漏

审计出的三处漏法各不相同, 但根因一样 —— 三件事分散在三个地方, 谁写谁忘:

| 位置 | 原来的行为 | 后果 |
|---|---|---|
| 规则**撤销删除** | 只 `load(globalChannel)` | 告警回来了, 看板不知道; 等 30s 静默刷新或切页重挂 |
| 采购**下单/取消** | 只弹 toast | `purchase_need` 告警已关, 看板计数滞后; 缓存也没清 |
| 采购**到仓日期** | 裸 `api.put().catch(loadOrdered)` | 超储/在库天数口径变了, 其它页无感知 |

修法: `api/mutate.ts` 一个入口, 把四件事一次声明完:

```ts
await mutate({
  label: '保存规则',
  run: () => fetch(url, {...}),          // 实际请求
  success: r => (r.tid ? '已保存，正在重算告警' : '已保存'),
  events: ['rules-changed'],             // 联动契约: 哪些页面会变
  invalidate: '*',                       // 裸 fetch 的缓存失效('*'=全清)
  op: r => (r.tid ? { id: 'rules:'+r.tid, kind: 'rules', taskId: r.tid, ... } : null),
  opPersist: true,                       // 由 OpsWatcher 按后端状态移除
})
```

`events` 不是可选装饰 —— 它是"改了数据要告诉谁"的唯一声明处。关键页(规则/采购)已全部接入,
裸写的收尾请求(撤销窗口结束后的 permanent-delete)必须显式标 `// no-link: 理由`, 回归里有断言。

#### 四、操作态: `ops` 不能塞进 `syncing`

最省事的做法是给 `syncing` 加一, 让胶囊显示"规则重算中"。**不能这么做**, 三个理由:

1. **`syncing` 有 20s 强制归零兜底**(`App.tsx:160`) —— 那是防徽标永久卡死的, 大库评估一旦超过 20s,
   胶囊会**提前显示完成**;
2. `syncing` 只是计数, 说不出"在算什么、算多久、哪个渠道";
3. 生命周期不同: 取数是秒级, 计算/导入是分钟级, 混在一起后二者都无法单独判断。

所以新增 `ops: AppOp[]`(`kind: rules | ingest | write`), 与 `syncing` 并列:

```
规则保存 → HTTP 200 只代表"已受理" → ops.add(taskId)
        → OpPill 立刻显示「规则重算中」(任意页面可见)
        → App 层 OpsWatcher 每 2.5s 查 /api/rules/eval-status
        → done/expired → opDone + dispatch('rules-changed')
        → error       → opDone + 明确报错(不再静默)
```

三个设计点:

- **挂在 App 层而不是规则页**: 用户保存后切页, 规则页卸载, 页面内轮询就没了 —— 胶囊会永远停在
  "重算中"。这不是假设, 是 §15.128 的 `waitEvalDone` 的真实缺陷(现在已删除, 由 OpsWatcher 接管)。
- **刷新可恢复**: ops 落 `c_ops`, 刷新后继续轮询; 15 分钟陈旧的自动淘汰, 防"永远处理中"。
- **胶囊优先级**: `ops` 非空时显示操作态, 否则回落 `syncing`。两者叠加会让用户以为"一直在加载"。

补上的还有导入类任务: 清洗/种子/重置/导出原本只有任务卡能看到, 现在也进 `ops`(kind=ingest),
提交后在任意页面都能看到"数据清洗中 · jd"。

#### 五、新链路时序

```
点保存 → mutate()
       ├─ fetch 200 + eval_task_id
       ├─ clearCache('*')
       ├─ dispatch('rules-changed')  → 看板 load(aux.evaluating=true, 页内显示"重算中")
       ├─ toast「已保存，正在重算告警」
       └─ ops.add(规则重算)
后台完成 → OpsWatcher 查到 done
       ├─ ops.remove        → 胶囊消失
       └─ dispatch('rules-changed') → 看板再拉(拿到新告警, 重算中文案消失)
```

失败路径不再沉默: HTTP 失败 → mutate 统一报错; 评估失败 → OpsWatcher 报
"规则重算失败，告警可能未更新（详情见质量页日志）"。

#### 六、回归

378 → **388**(+10): 操作态与取数态分离 / 后端状态驱动移除 / 胶囊优先级 / 刷新恢复与陈旧淘汰 /
mutate 四件套 / 规则三条写路径 / 采购三条写路径 / 撤销补事件 / 顶层改 notify / 裸写显式豁免。

**顺手修了"不跑的测试"**: 前端 `vitest` 有 22 个用例, 但 preflight/CI **从来没执行过它**,
于是攒下 12 个长期失败还无人知晓 ——

| 失败 | 数量 | 根因 | 处理 |
|---|---|---|---|
| Toast 三例全部 5s 超时 | 3 | `vi.useFakeTimers()` 下 `userEvent` 内部 delay 被冻结, 永远 resolve 不了 | 改 `fireEvent`(同步派发, 与假定时器无冲突) |
| 列定义断言数字过时 | 9 | 业务加列(商品 12→15 / 订单 9→11 / BBCC 18→20 …), 测试没跟上 | 只锁"当前契约", **不改变任何用户可见行为**; `insDefVisTrad` 不含 `safety` 的差异已注释留待产品确认 |

`preflight.sh` 增加 `[7/7] vitest`, CI `frontend` job 增加 `npm test`。**不跑的测试等于没有** ——
这次的两个断点(no-op 提示、漏发事件)都没有被任何测试发现, 正是因为它不在门禁里。

#### 七、边界

- `ops` 是**前端观察到的**操作态, 不是任务队列。多端同时操作时, 另一台设备的 op 不会出现在本机
  (但看板的 `aux.evaluating` 仍然正确, 因为它读的是库里的 `eval_tasks`)。
- 胶囊里的"隐藏"只从列表移除, 不影响后端任务 —— 文案已注明, 避免用户以为取消了任务。
- 事件总线仍然是"触发重拉"而非"推送数据", 页面未挂载时事件会丢; 兜底是 mount 重拉 + 30s 静默 +
  `visibilitychange`。这条没有改, 因为改成持久化事件队列的复杂度远高于收益。

### 15.130 S3-4 真实 SQL 冒烟: 让测试第一次"问过数据库" (2026-11-03)

审计报告把 S3-4 写成"测试策略: 真实 SQL 冒烟", 理由只有一句 —— 205 个用例全 mock 掉 db
返回固定行, **表名/列名/GROUP BY 一个都测不出**。这次落地, 并且在第一次运行就抓到 3 个真缺陷
(其中 2 个是"上线以来从未生效"的功能)。

#### 一、为什么 mock 永远抓不到这类错

`fake_query` 是**按 SQL 片段做模式匹配**的:

```python
if "FROM inventory WHERE" in sql or "FROM inventory i" in sql:
    return [dict(x) for x in _FAKE_INV]
```

它匹配的是"我**期望**代码写出的 SQL", 不是"数据库**能执行**的 SQL"。所以:

| 代码里的错 | mock 的反应 | 测试结论 |
|---|---|---|
| `WHERE qty=%s`(列不存在) | 片段仍匹配 → 返回假行 | ✅ 通过 |
| `COALESCE((SELECT ...)), 0)`(多一个括号) | 片段仍匹配 → 返回假行 | ✅ 通过 |
| `GROUP BY` 少一列 | 片段仍匹配 → 返回假行 | ✅ 通过 |

更隐蔽的是**被 `try/except` 吞掉的那类**: 查询抛 1054 → except 记一条日志 → 按 0 降级 →
业务继续跑。测试连异常都看不到, 线上也"不报错", 只是**数字一直是 0**。

#### 二、方案: EXPLAIN, 不是"连库跑一遍"

三条路对比, 选了代价最小、副作用为零的那条:

| 方式 | 副作用 | 能否验 DML | 成本 |
|---|---|---|---|
| 直接执行 | 读数据(RU)、慢、可能写 | 能 | 高 |
| 事务 + ROLLBACK | DML 可回滚, **DDL 隐式提交不可回滚** | 能 | 中 |
| **`EXPLAIN <stmt>`** | **零**: 只做名称解析 + 计划, 不读行、不加锁、不执行 | 能(TiDB 支持 `EXPLAIN INSERT/UPDATE/DELETE`) | 每条约 30~80ms |

动手前先实测了四件事(2026-11-03, 生产库):

| 探针 | 结果 |
|---|---|
| `EXPLAIN SELECT sku, no_such_col FROM inventory` | 1054 Unknown column ✓ |
| `EXPLAIN SELECT * FROM no_such_table` | 1146 Table doesn't exist ✓ |
| `EXPLAIN SELECT sku, channel, SUM(x) FROM inventory GROUP BY sku` | 1055 ONLY_FULL_GROUP_BY ✓ |
| `EXPLAIN DELETE FROM inventory` 前后 `COUNT(*)` | 均 17006, **未删任何行** ✓ |

所以可以对着生产库跑, 不需要测试库、不需要造数据、不需要回滚。

#### 三、怎么拿到 SQL: 包在"第一次绑定"处

`routes/*.py` 全是 `from db import query` —— 名字在 **import 那一刻**绑定。这意味着:

- 在 `local_test.py` 首次 import 路由**之前**包住 4 个 mock, 就能覆盖所有已 import 模块的调用;
- 之后再改 `db.query` 对已 import 的模块**无效**(Python 名字绑定语义, 不是偷懒)。

因此只在 6 个点加了 `_A(...)`: 4 个主注入 + `fake_agg_query`(紧接着 import dashboard) +
`fake_query` 重绑(紧接着 import tasks)。后面那些 `_db.execute = lambda ...` 是测试自己的替身
(用于截获 SQL 做断言), 不改变已 import 模块内的绑定 —— 不逐处包, 省 12 处噪音。

**代价**: 包装必须一直在。若有人删掉 `_A`, 收集数会变 0 而 `--sql-smoke` 仍报"0 失败"。
所以有两道护栏:

1. `_MIN_SQL = 200`(基线 388): 收集数腰斩直接判失败, 不静默变绿;
2. 回归里 4 条静态断言: 6 个注入点都带 `_A()` / 冒烟带覆盖率下限 / 两处已修缺陷不得复发。

#### 四、第一次运行抓到的 3 个真缺陷

**① `core/rule_eval.py` 采购在途恒 0(1054, 被 try 吞)**

```sql
SELECT sku, SUM(IFNULL(qty,0)-IFNULL(received_qty,0)) FROM purchase_orders ...
```

`purchase_orders` 的真实列是 `id/sku/store/product_name/suggested_qty/actual_qty/arrival_date/status/channel/created_at`
—— **没有 `qty`/`received_qty`**。每次评估都 1054, 被 `except` 记成"按 0 降级", 于是
`own.po_transit` 恒 0、`can_ship` 少算。

**这条尤其值得记: 同一个错 2026-11-02 已在 `dashboard_own_health.py` 修过一次**
(那里还留了 `"FROM purchase_orders" not in src` 的断言), 但 `rule_eval.py` 漏了 —— 又一次
"修一处漏一处"。修法与 own_health 同源: 采购在途 = 库存导入的 `in_transit_qty`, 导入值即权威,
再推一遍就是双计。所以 `po_transit` 与 `transit` 同源, `can_ship = available + transit`(只加一次)。

> 线上 11 条规则**没有一条**引用 `own.po_transit`/`own.transit`, 所以这次语义修正对现网判定零影响。

**② `routes/cron.py:478` 批次对账多一个右括号(1064)**

```sql
COALESCE((SELECT SUM(b.qty) FROM batches b WHERE ... AND COALESCE(b.barcode,'')=COALESCE(i.barcode,''))), 0) AS bq
                                                                                                    ↑ 多这一个
```

后果比①更重: **D7 的四段对账里, 第④段(告警↔库存四维)之外的"批次四维对账"上线以来一次都没跑成过**
—— 每次每日任务走到这里 1064, 被 `except` 记成"批次对账降级"。日志里只有一行警告, 没人追。

**③ 3 处把 `str` 当 params 传(诊断日志从未落库)**

```python
_ed("INSERT ... VALUES(...,%s,...)",
    ("detect 收到 file: %s" % (bool(file),)))     # ← 少了外层括号里的逗号
```

`"..." % (...)` 求值成**字符串**, pymysql 会把它逐字符当参数序列 → `not all arguments converted`
→ 被 `except: pass` 吞掉。涉及 `routes/cleansing.py`(detect 收文件)、
`routes/dashboard_maintain.py`(快照续段 ×2)。它们都是 2026-10 为定位问题临时加的诊断,
**加了却没生效过**。改为 `(msg,)`。

#### 五、DDL 管不着, 用 schema 对账补

388 条唯一 SQL 里 125 条是 `create×50 / alter×53 / show×19 / drop×3` —— EXPLAIN 不支持,
但"声明了却没建"是同一类事故(`SCHEMA_VERSION` 漏 bump、DDL 写错列名)。于是加 `--schema-diff`:

```
解析 schema_create._TABLES 的 CREATE TABLE → 提取列名(按括号深度切分, 跳过约束行)
+ _COLUMN_ADDS 的补列声明
vs information_schema.columns / statistics
```

| 判定 | 含义 |
|---|---|
| 代码有、库无 | **✗ 失败**(迁移没跑 / 列名写错) |
| 库有、代码无 | ⚠ 提示(历史遗留列不影响新代码执行) |

首次结果: 41 表 / 391 列 / 13 索引, 全部存在; 库里有 3 列未声明
(`replenishment_config.key` 等, 属历史遗留, 不判错)。

#### 六、实测与接入

| 指标 | 值 |
|---|---|
| 唯一 SQL | **388 条**, 覆盖 **31 个后端模块** |
| EXPLAIN 通过 | 263 条, **0 失败 / 0 告警** |
| 跳过 | 125 条(DDL/SHOW, 由 schema 对账覆盖) |
| 单次耗时 | 约 65s(392 用例 + 263 次 EXPLAIN + 对账), 其中回归本身 ~2s |

接入方式:

```
preflight [3/7]  有 TIDB 凭据 → python3 local_test.py --sql-smoke(同一个进程, 复用收集结果)
                 无凭据     → 显式打印"⚠ 真实 SQL 冒烟未执行(表名/列名未验证)"
CI backend job   secrets.TIDB_* 注入 → 跑; 未配置 → ::warning 显式标注"本轮没有验证表名/列名"
                 另有 python3 sql_smoke.py --self-test(19 条正负例, 不需要库)
```

**"没有凭据就跳过"必须打印出来**: 静默跳过的门禁和没有门禁是一回事 —— 这正是 15.129 里
"vitest 22 个用例从没被执行过"的同型问题。

#### 七、零误报设计

门禁只有"报出来的都是真错"才有人看。三条规则:

1. **只有名称解析类错误码判失败**: 1054/1146/1051/1052/1055/1064/1109/1247/1210。
   其余(1366 截断、超时、权限)记 ⚠ 并原样打印, 由人判断。
2. **参数个数对不上先重试**: 用 `NULL` 填充所有 `%s/%d` 再跑一次, 通过则记 ⚠ 不记失败
   —— mock 的参数形状与真实调用未必一致, 不该让它变成红。
3. **报错必须给调用点**: `traceback` 取第一个非 `sql_smoke`/`local_test` 的栈帧,
   输出 `core/rule_eval.py:349`。只报"Unknown column"而不说改哪个文件, 等于没报。

自检锁住这些能力(`--self-test`, 19 条): `explain_sql` 的分类、错误码分级、`%s` 填充、
列名解析(DECIMAL 里的逗号不能切断)。

#### 八、CI 踩坑: 260 条 1146 不是 260 个缺陷

第一次推上去 CI 直接红: `✓203 / ✗60`, 全是 1146 表不存在(连 `channels`/`schema_state` 都没有)。
本地同样代码 263 条全过 —— 差在**连的库不同**。

根因两层:

1. workflow 的 `env` 漏了 `TIDB_DB`(只传了 HOST/PORT/USER/PASSWORD), 代码回落到默认 `supplykit`,
   而 CI 集群里那个库是空的;
2. 更值得记的是**诊断体验**: 60 条同构报错等于没有信息量, 人只会看到"一片红"。

于是加了"库指纹"检查(先问"这是不是本项目的库", 再谈逐条诊断):

```
连接后 → SELECT DATABASE() + information_schema 里查 inventory/orders/rules 三张核心表
不足 3 张 → 只报一条: 目标库 `xxx` 缺核心表 0/3 —— 凭据指向的可能不是本项目的库, 或迁移未跑
            并跳过 schema 对账(在错库上对账没有意义)
```

> **通用教训: 批量同构错误先怀疑环境, 不要逐条读。** 60 条 `Unknown column` 各不相同才是代码问题;
> 60 条 `Table doesn't exist` 集中在一批基础表上, 几乎一定是连错了库。

顺带修掉一个信息损失: 失败原因原来只打中文描述(如"表不存在"), 丢掉了数据库原始消息(含库名)。
现在 `fatal` 一律附原始消息, 否则永远查不出"连的是哪个库"。

#### 九、边界

- **只覆盖 mock 走到的分支**。388 条是"现有用例能触发的 SQL", 不是"代码里所有 SQL"。
  某个 `except` 分支里的查询若从未被测试触发, 仍然验不到 —— 但这类查询通常也不会在生产触发。
- **EXPLAIN 验的是"能不能执行", 不是"执行得快不快"**。执行计划质量(全表扫/笛卡尔积)
  不在本门禁范围, 归 `ru_diag.sh`。
- **不验数据正确性**。`WHERE` 写错但语法合法(如 `channel='jdd'`)仍会通过 —— 那是业务断言的
  职责, 不是 SQL 冒烟的。
- **EXPLAIN 有微小 RU 消耗**(只编译不读行), 263 条量级可忽略; 但不要把它塞进高频循环。
- 无凭据时默认**打印"未执行"但不判失败**(本地无网不该红); 需要强制时设 `SQL_SMOKE_REQUIRED=1`。

### 15.131 CI 的数据库凭据: 从「补传一个变量」到「不再维护第二份」(2026-11-03)

#### 一、上一轮的修法是错的方向

15.130 里 CI 首跑 60 条 `1146`, 我加了库指纹、又补传 `TIDB_DB`。当时看似修好了, 但只是
把**这一处**差异填平:

```
GitHub Secrets  ─┐
                 ├── 两份独立副本, 谁也不知道对方改过
EdgeOne 项目环境 ─┘
```

改密码、换实例、加库名 —— 任何一次变动都会让两边分叉, 而下一次分叉只会在**又一次 CI 首跑**
时才暴露。这和"手写提示三件套必然漏一处"(`15.129`)是同一类问题: 靠人记得同步的东西,
迟早不同步。

#### 二、改成单一真相源

CI 不再持有 TIDB 凭据, 改为**启动时现取**:

```
GitHub Secrets: EDGEONE_PAGES_API_TOKEN  (唯一)
        │
        ▼
scripts/ci_fetch_env.py ──► DescribePagesProjectEnvs(ProjectId)
        │                        只取 Production 档的 6 个连接键
        ▼
   $GITHUB_ENV  →  后续 step 直接用 $TIDB_HOST
```

线上用什么库, CI 就验什么库。轮换密码只改 EdgeOne 一处, 下一次 CI 自动跟随。
顺带把 secrets 数量从 5 个降到 1 个 —— 少一个可泄露、可过期、可填错的值。

#### 三、三个实现上的坑(都不是"写代码"层面的)

**1. `>> $GITHUB_ENV` 会吃掉 workflow 命令。**
最自然的写法是 `python3 ci_fetch_env.py >> $GITHUB_ENV`, 但脚本要输出 `::add-mask::` 和
`::warning::` 才能生效, 而这两个必须**出现在 stdout 被 runner 解析**。重定向后它们被写进
环境文件, 结果是: 掩码失效(密码明文进日志) + 环境文件里多出两行非法变量。
→ 脚本自己打开 `$GITHUB_ENV` 追加, stdout 留给 workflow 命令。

**2. 掩码粒度决定日志还有没有用。**
第一版把 6 个值全登记为掩码, 于是 `4000`、`supplykit`、`true` 也成了敏感词 —— 日志里
`host=*** db=***`, 连"连的是哪个库"都看不见。而这恰好是上次排查**唯一缺的线索**
(`15.130` 第八节花了整节讲这件事)。→ 只掩 `TIDB_PASSWORD`。host/user 是连接目标不是口令。

**3. 只取 Production 档。**
`EnvVars` 每条带 `Env: ["Production","Preview"]`。Preview 可能是另一套库或另一套密码,
CI 要验的是线上那套, 混用等于把"预发能过、线上不能过"变成"CI 绿但线上挂"。

#### 四、降级路径(不能因为拿不到凭据就让门禁红)

| 情况 | 行为 |
|---|---|
| 正常 | `凭据来源=edgeone`, 跑 `--sql-smoke` |
| token 失效 / fork PR 读不到 secret | `::warning::` + 回落旧 secrets, 仍尝试跑冒烟 |
| 两者都没有 | `::warning::` + `CI_ENV_SOURCE=none`, 只跑回归, 明确写"本轮未验证表名/列名" |

理由: 回归 392 条**不依赖数据库**, 缺凭据只该让冒烟跳过。把环境问题变成门禁红, 结果是
大家习惯性忽略红色 —— 比不跑更糟。

#### 五、校验只能靠"下一次 CI"

GitHub Secrets **只写不可读**。所以 `scripts/sync_ci_secret.py` 只能确保"已写入",
无法回读比对。真正的验证是 CI 日志里那一行:

```
── 数据库连接来源: edgeone ──
   host=gateway01... db=supplykit user=3Numc6***
```

出现 `来源: secrets` 就说明 token 没生效, 正在用一份可能过期的副本。

#### 六、边界

- **public 仓库里放平台 token 的代价**: 一旦该 secret 泄露, 攻击面等于"能读项目环境变量"
  (含 JWT_SECRET/CRON_SECRET)。相比原本的 5 个 TIDB 值, 面变大了 —— 取舍是"少一处漂移"
  换"多一分集中风险"。若将来在意, 可改为只给 CI 一个专用的只读 token。
- **不覆盖 Preview 档差异**: 若某天需要验证预发库, 应另起一个 job 显式取 `Preview`, 不要
  让同一个 job 两档混用。
- 原有 `TIDB_*` secrets **暂不删除**: 它们是回落路径, 等 `来源=edgeone` 稳定跑若干次后再清理。

#### 七、这次改动自己又踩了两个坑(都值一条经验)

**1. `.edgeone/` 在 .gitignore 第 23 行, CI 里根本没有 `project.json`。**
第一版脚本从 `.edgeone/project.json` 读 ProjectId, 本地测得好好的, 到了 CI 就是
`无 ProjectId → 回落 secrets → 又是那 60 条 1146` —— 而日志看起来"脚本跑成功了"
(step 是绿的), 因为降级路径设计成不失败。教训: **降级路径会让失败变安静**,
它的日志必须显式写出"我现在用的是次优方案, 原因是 X"(这一版已改成 `::warning::` 带原因)。
修法: ProjectId 不是秘密(还得有 token 才能调), 直接写进 workflow 的 env。

**2. `print("CI_ENV_SOURCE=...")` 不会进环境。**
脚本写 `$GITHUB_ENV` 用的是文件追加, 而 `CI_ENV_SOURCE` 这一行顺手用了 print。
下一个 step 里 `echo "凭据来源=$CI_ENV_SOURCE"` 打出空值, 日志成了 `凭据来源= →`。
同一个文件里两种输出通道混着用, 就会漏一个。

#### 八、结果

| | 改前 | 改后 |
|---|---|---|
| GitHub Secrets 里的数据库凭据 | 5 个, 各自独立 | 0 个(回落用, 待清理) |
| 凭据来源 | 人工同步, 会漂移 | 运行时取自 EdgeOne Production 档 |
| CI 实际连的库 | 另一个集群的空库 → 60 条 1146 | 线上同库 → 263 条 EXPLAIN 全过, schema 对账 41 表/391 列/13 索引全在 |
| 轮换密码要改几处 | 2 处(GitHub + EdgeOne) | 1 处 |

#### 九、收尾清理(同日下午)

| secret | 处理 | 理由 |
|---|---|---|
| `CRON_SECRET` | **已删** | 仓库里唯一的工作流 `preflight.yml` 从不引用它; 定时任务跑在 EdgeOne, 用的是项目环境变量里那一份 |
| `JWT_SECRET` | **已删** | 同上。GitHub 里这份既不会被读到, 又是完整能力的签名密钥副本 |
| `TIDB_SSL` | **从未存在** | 上一版 workflow 里写了 `FB_SSL: ${{ secrets.TIDB_SSL }}`, 一直是空串。`db.py` / `sql_smoke.py` 对缺省值就是开 TLS(`os.environ.get("TIDB_SSL","true")`), 留空与显式 `true` 等价 → 直接删掉这个映射项, 免得后人以为它有用 |
| `TIDB_*` ×4 | **保留** | 降级路径: 新 token 失效/fork PR 时仍能跑冒烟 |

> 一条通用判据: **secret 的"存在"本身就是成本** —— 多一份就可能过期、可能填错、可能被误认为生效。
> 判断该不该留, 不看"以后会不会用", 只看"现在有没有代码读它"。没有读取点的 secret 一律删,
> 需要时再加回来比留着烂在那儿便宜。

### 15.132 S3-1 巨型页面拆分: 前两页(2026-11-03)

#### 一、拆的依据不是"行数", 是"依赖形状"

行数只说明文件大, 不说明能不能拆。真正的判据是**一块 JSX 依赖多少个外层变量**:

| 块 | 依赖变量 | 结论 |
|---|---|---|
| 看板 6 个弹窗 | 各 4~12 个 | 天然边界: 全是 createPortal 挂 body, 无 DOM 位置耦合 |
| 规则页 4 个参数面板 | 各 10~18 个 | 可拆但受控(状态留页面), 因为各自有独立的 saving/saveErr |
| 规则页主列表 | **43 个** | 拆它得先抽 `useRuleEditor()`, 不是搬运, 是重构 —— 本轮不动 |

> 用 AST 脚本算自由变量(排除 style 键名、JSX 标签名、块内声明), 比人眼数可靠:
> 第一次手写只挑出 6 个, 脚本给出 12 个, 少的 6 个正是 tsc 后来报的漏传。

#### 二、结果

| 页面 | 前 | 后 | 外提内容 |
|---|---|---|---|

| RulesPage | 3407 | 2769 | `rules/shared.ts` + `rules/*Panel.tsx` × 4 |

#### 三、验证: 不比"看起来一样", 比渲染树

单测覆盖不到页面(只有 utils/configs/Toast/mutate), 靠人眼看截图等于没验证。做法是
**两版面对同一后端、同一 token、同一时刻, 比「层级|标签|class」序列**:

| 位置 | 节点数 | 结果 |
|---|---|---|
| 看板主视图 | 232 | 逐节点一致 |
| 低库存 / 采购补货 / 其他告警 弹窗 | 1284 / 1090 / 1000 | 逐节点一致 |

四个踩坑(都浪费过一次运行):

1. **线上与本地不同源** → 起 Python 反向代理把 `/api` 转到线上, 绕开"后端没有 CORS"。
2. **代理只转发了 `Authorization`** → 前端用的是 `X-Auth-Token`(网关改写了 Authorization)。
   于是每个请求 401, 页面停在登录页, 而代理日志显示 200。**转发请求头就要全转**, 不要挑。
3. **首启欢迎页挡路** → `localStorage.c_welcome_seen`; 点文本太脆(受 i18n 和包裹层影响)。
4. **一边还在骨架屏就开比** → 差异一堆, 全是加载状态。判据改成"等 `GMV` 文本出现"。

#### 四、拆分本身踩的两个坑

- **"找第一个 `)}`"定位块尾会被嵌套骗到**: ProcSheet 块内有 `)}`, 结果只搬了 113 行
  (文件语法残缺), tsc 报"JSX fragment has no corresponding closing tag"。改用 TS AST
  给的精确区间。
- **删死代码不能按行号猜**: 删 `_whTag` 时用的"从 i 往下找第一个 `}`", 把组件尾部和
  整个文件结尾一起切掉了(3014 → 914 行)。恢复办法是 `git checkout` 重跑生成脚本 ——
  这也说明拆分脚本必须**幂等**(每次从 git 原版出发), 而不是在中间状态上打补丁。

#### 五、一处误判自查: 规则页 4 个参数面板**并非**没有入口

拆分时看到桌面 `RulesPage` 的 tab 读 `store.hammerRulesTab`, 而 `setHammerRulesTab`
只出现在 `components/hammer/HammerRules.tsx`, 就写下"桌面无入口, 4 个面板不可达"。
**这个结论是错的**, 已实测推翻:

- `HammerRules` 是锤子菜单组件, `App.tsx` 在 `page === 'rules'` 时渲染它, **没有
  isMobile 分支** —— 桌面与移动是同一份组件、同一个 `.hammer-icon-btn` 入口。
- 1440×900 实测: 点锤子按钮 → 面板 240×200, 4 个分段(规则/补货/采购/滞销); 点
  「补货」后主页面渲染 C 仓/B 仓/活动系数, 规则列表消失。390×844 同流程面板
  240×200、文本与交互完全一致(仅 x 坐标随右侧对齐), 线上 prod 同样通过。
- 误判根源: 只沿"谁写这个 store 字段"做静态追踪, 没查"这个组件在哪些布局下被挂载"。
  **字段只有一个写入点, 不等于入口只有一个; 组件的挂载点才是入口。**

结论: 四个面板一直可达, 不需要补导航条, 也不需要在桌面上另造一套 tab —— 那反而
会和锤子菜单形成两个真相源。今后要动这块, 先按上面两步实测, 别从 grep 结果推结论。

## §15.200 每日评估改接力：七天 100% timeout 的根治

### 一、现场

`pipeline_runs` 里 `daily_rules` 11-10~11-16 每天 04:04 一条，状态**全 `timeout`**：

```
status=timeout  started_at=04:04  finished_at=10:59  duration≈25000s
error = 挂起超时: running 超过 10 分钟(实例被冻结/掐断, 收尾语句未执行)
```

`maintenance_log.details` 长期停在 `#run#170200|166420|45505475#<token>`（没落指纹），
20 分钟后被看板兜底判成"持有者被冻结"抢走，再跑再冻。

**不是算错**：`run_daily_rules(deep=True)` 在一次请求里做完孤儿清理 + 两条全表 UPDATE +
全渠道 9 万行评估 + 批次对账 + 健康快照。单渠道实测 83~117s，**超过 Makers 请求生命周期**。

### 二、设计（复用，不新建）

用户明确要求"用目前已有机制"。于是：

| 需要 | 复用什么 | 为什么不新建 |
|---|---|---|
| 推进游标 | `sync_tasks`(task_type='rule_eval') | 导出/导入/seed 都在这张表，`continue_tasks` 已经在扫它 |
| 防双跑 | `core.task_lease` | 令牌 + 心跳 + 45s TTL，四个驱动端点共用同一套 |
| 推进源 | `continue_tasks`（60s 请求驱动 + 平台调度 + `/health` 保活） | 已有三个独立触发源 |
| 分片单位 | SKU 游标 + `evaluate_stock_skus(skus=)` | 增量入口本来就"只关本批 SKU 的告警" |
| 对外状态 | `eval_tasks` 一行 | 看板横幅 `aux.evaluating` 读的就是它，零改动 |

四阶段：`prep` → `eval`（SKU 游标分片，每片 4000）→ `post`（批次对账 + 健康快照）→ `kick`。
`deep=False` 直接跳到 `kick`，跳过 `post`。

### 三、三个必须一起改的地方

只改 `run_daily_rules` 是不够的——三处"完成信号"如果还按老语义写，接力等于没接：

| 位置 | 原来的问题 | 现在 |
|---|---|---|
| `cron_daily_rules` | `claim → 同步跑 → settle_rules(ok=True)`：请求一返回就宣告"今天评估完了" | `claim → 建任务推首片 → 不 settle` |
| `dashboard._daily_rules_guard` | daemon 线程跑满 100s，实例冻结就断在半截 | 只推首片（8s 预算），立刻返回 |
| `rules._drain_eval_tasks` | 跑完把 `eval_tasks` 置 `done` | 只排队；`done` 由接力任务收尾（否则横幅提前消失） |

**为什么"不 settle"是关键**：`claim_rules` 的三态占位是"今天该不该评"的唯一真源。
请求返回即 settle = 库里写着"已按当前库存评估完成"，而评估还有 90% 没跑。
那正是线上最误导的信号。

反过来，占位的超时判据是 `created_at < NOW()-20min`（`_RUN_STALE_MIN`），
接力任务跑 20 分钟就会到点被抢 → 再建一个任务重跑全量。所以每片推进时
`touch_claim(token)` 刷一次 `created_at`，等价于心跳。

### 四、为什么不改评估算法一个字

`evaluate_stock_skus(channel, skus=[...])` 的关闭逻辑里已经带：

```python
_only = {str(x) for x in skus} if skus else None   # 增量评估只关本批 SKU(防误关)
...
if _only is None and len(_close) >= 30 and ...:    # 批量误关护栏只对全量生效
```

也就是说：**按批评估本来就只关本批的告警**，且不吃"单轮关闭≥80% 视为数据异常"那道闸。
这是既有实现（2026-10-29 增量入口）的性质，不是为接力新加的。

**为什么不按行 id 切片**：`evaluate_stock_skus` 按 SKU 取该 SKU 的全部仓行，
BC 盘的单元是"平台 + B 合计"——同一 SKU 的多仓行落进不同片，会把单元聚合切开。
所以游标必须是 SKU。分片大小 4000 < `metrics._SCOPE_MAX`(5000)，保证 ctx 加载仍走
scope 下推（超了会退化成"全渠道一次"，那正是 19.3s 那个坑）。

| `SELECT DISTINCT sku ... AND sku > %s ORDER BY sku LIMIT 4000` | `IndexRangeScan + StreamAgg + Limit`，**无 temporary / filesort**（走 `uq_inventory_biz` 的 sku 前缀） |

## §15.201 导出全量：2000 行的"全量"与建任务时的全量试跑

### 一、两个独立缺陷

**① 补货导出只有 2000 行。** `_build_export_rows` 裸调 `get_replenishment_suggestions(page=0)`，
该接口无分页时按 `UNPAGED_CAP["repl"]=2000` 截断（防网关 413）。接口 `total=10000`，
下载的 xlsx 却是 2000 行。

**② 建任务请求里真跑了一遍导出。** `create_export` 用

```python
if _build_export_rows(exp_type, mode, channel, wh_type) is None:
    return fail("未知导出类型")
```

判断"类型认不认识"—— 等于把整份导出真跑一遍只为判空。补货 = 物化全量 + 5 万行组装，
建任务本该是毫秒级（INSERT 一行）。

### 二、改法

列表型导出（补货/采购/滞销）改**分页接力**：

- 每片 `_EXPORT_PAGE=2000` 行，片内 CSV；
- 第 0 片带表头 + BOM，后续片不带；
- `done` 判据 = "本页不满" 或 "已取到 total"；
- 建任务改类型白名单 `exp_type not in _EXPORT_NAMES`。

**为什么分片必须 CSV**：`export_download` 的合并是 `merged += bytes`，而 xlsx 是 zip ——
拼两个 zip 出来的是坏文件。原来只有订单导出走 CSV 分片，补货是单片 xlsx，所以没暴露。
补货改 CSV 分片后，5 万行也不会把单个 part 推到 413 线。

### 三、顺带修好一个一直在的中段 BOM

```python
# 旧: 每一片都保证一个 BOM
merged += _b if _b.startswith(BOM) else BOM + _b
```

3 片就有 2 个 BOM 落在文件中段 → Excel 里一行 `ï»¿订单号,...` 的乱码。
订单导出 5 万行（3 片）时必现。

```python
# 新: 只有第一片有; 后续片剥掉自带的(旧任务的历史分片都带 BOM, 剥掉正好兼容)
if not merged:
    merged = _b if _b.startswith(_bom) else _bom + _b
else:
    merged += _b[3:] if _b.startswith(_bom) else _b
```

## §15.203 物化 fp 缺「代码口径」这一维：BC 计数为什么不闭环

### 一、现象：改完了、部署了、还是 0

§15.202 把看板的 BC 分组计数收敛到 `routes.alerts.wh_map()` 单一真源，部署
`a94044f` → `dp24txlvjkin` Success/Prod=yes。线上复验：

```
/alerts/counts         by_warehouse = {b:0, c:0, own:8235, bc:554, unknown:619}
/dashboard/aux         by_warehouse = {b:0, c:0, own:8235, bc:0,   unknown:619}
                                                                  ↑ 还是 0
```

### 二、先排除"没部署成功"

同一版的 6 条删除判据（不存在的 id 必须 `ok:false`）**线上全过** —— 这些是这一批新写的
代码，能过说明代码确实在线上。所以不是发布问题。

### 三、根因：fp 的两维都感知不到"代码变了"

```python
# core/dash_store.py
def fp_now(family, channel, mode=None, scope=""):
    base = _US.fp_of(_deps(family), channel, mode)   # ← 域计数器
    return md5("%s|%s|%s" % (base, family, scope))

# core/unit_store.py（改前）
raw = "|".join("%s=%d" % (d, vals.get(d, 0)) for d in domains)   # 数据域计数
raw += "|g=%s|m=%s" % (_g, _m)                                    # 粒度 + 模式
```

而 `_deps("dash_aux")` = `{orders, inventory, products, suppliers, rules, config}` ——
**"仓型映射"不在里面，也永远不可能在里面**：它是**代码**，不是数据域。

于是链条是：

1. 改了 `wh_map`（代码）→ 输出口径变了
2. 没人写数据 → `data_version_dom` 一个都不涨
3. `fp_now` 返回与旧物化一模一样的 fp
4. `dash_store.serve` 判定"fp 命中 = 这是最新答案" → **直接返回旧物化，连后台重建都不起**
5. 要等下一次导入/评估撞上域计数，才"自愈"

`serve` 的 SWR 逻辑本身没错 —— 它信任 fp。错在 fp 不完整：**它只描述"数据变没变"，
不描述"算它的代码变没变"**。

### 四、这是全族的缺口，不是 BC 一例

四家物化都经同一个 `_US.fp_of`：

| 消费方 | 会受影响的代码改动 |
|---|---|
| `unit_store`（判定/断货） | 分档公式、状态文案、四舍五入口径 |
| `dash_store`（summary/aux/risk） | 卡片组装口径、仓型映射、聚合维度 |
| `list_store`（补货/采购/滞销） | 排序 tie-breaker、筛选条件、字段口径 |
| `own_store`（自有仓健康） | 权重、阈值 |

所以修一次要修在 `_fp_of` 里，而不是给 `dash_aux` 单独打补丁（红线 2）。

### 五、改法：给 fp 加第三维

```python
_FP_VER = 2   # 1 = 2026-11-07 初版(隐式, 不在 raw 里); 2 = 2026-11-16 纳入代码口径维

raw = "|".join("%s=%d" % (d, vals.get(d, 0)) for d in domains)
raw += "|g=%s|m=%s" % (_g, _m)
raw += "|c=%d" % _FP_VER          # ← 新增
```

为什么选这个而不是别的：

| 备选 | 为什么不用 |
|---|---|
| 加 TTL 兜底 | 两套判据并存（正是 §15.163 花大力气删掉的东西），且 TTL 内仍然返旧值 |
| 手动 rebuild 接口 | 依赖人记得点，等于没修；且"人记得"不可证伪 |
| 把映射塞进 `schema` 域 | 语义污染：`schema` 域的含义是"表结构变了"，混进业务口径后无法判断该不该 bump |
| 每次部署自动 bump | 会因无关改动（改注释）触发全量重建；且部署与口径变更不是一一对应 |

`_FP_VER` 是唯一需要**人工维护**的一维，所以必须把纪律写进红线（第 22 条），
并在 `local_test` 里加断言守住"这个常量存在且在 raw 里" + "有 +1 的说明"。

### 六、配套：四家的冷态行为不对称

改完 `_FP_VER` 立刻暴露第二个问题：**失配之后谁来重建？**

| 读模型 | fp 失配时 | 自愈 |
|---|---|---|
| `list_store.serve` | 返上一版 + `submit_background` | ✅ |
| `own_store.serve` | 返上一版 + `submit_rebuild` | ✅ |
| `dash_store.serve` | 返上一版 + `submit_background` | ✅ |
| `unit_store.tally_of` | **`return None`**（调用方退回现算） | ❌ |

`tally_of` 是纯读原语，它的调用方（dashboard 的 summary / 库存卡片）拿到 `None` 后只是
回退 `metrics` 现算 —— **正确但慢**，而且没有任何一方会去把新 gen 建出来。重建的唯一入口
是写入路径的失效钩子。

于是"部署完但还没人导入"这段时间，看板会一直走现算（3.8s/次）。这是我这一批**自己引入**
的慢窗口（原来自愈不了但也没这么快），必须一起补。

补法选在 `continue_tasks`（既有后台保洁通道，60s 一轮）：

```python
def _bootstrap_materialized(done):
    if not _throttle("mat-bootstrap", 600):   # 10 分钟一次
        return
    from core import unit_store as _US
    _US.ensure_async()                        # 内部判 fresh + 单飞 + 30s 冷却
    done["bootstrap"] = 1
```

为什么不自己判 fp：`ensure_async()` 已经封好了"按 `head.fp` 判 fresh + 同 `(channel,mode)`
单飞 + cooldown"，再写一遍就是第二套判据（红线 2）。

为什么不违反红线 19（读路径禁止触发失效）：它 **bump 不了任何域计数、打不了任何墓碑**，
只是把"已经该建但没人建"的 gen 建出来，而且跑在后台通道不是请求路径。

## §15.204 规则评估为什么显示成「数据清洗导入」

### 一、先回答字面问题：没有做过任何导入

用户看到任务卡写着「数据清洗导入」，问是不是我导了数据。查库：

```
today  cleansing 任务数 = 0
近三天 cleansing 任务数 = 0
今日任务分布: export × 10, rule_eval × 1
```

当天唯一那张"导入"卡是 `ev_1794804393_6117`, **`task_type = rule_eval`** ——
是 §15.200 新建的每日评估接力任务。一行数据都没导入, 是**显示层把它叫成了导入**。

### 二、根因：兜底方向错了

`pages/TaskPage.tsx` 的类型推导原本是：

```tsx
const type =
  task.task_type === 'export' ? 'export'
  : task.task_type === 'seed' ? 'seed'
  : task.task_type === 'reset' || id.startsWith('reset_') ? 'reset'
  : task.task_type === 'cleansing_eval' ? 'cleansing_eval'
  : 'cleansing'          // ← 兜底
```

`rule_eval` 是新类型, 不在白名单 → 走兜底 → `TYPE_LABEL['cleansing']` →
`task.type_cleansing` = **「数据清洗导入」**。

这个兜底在早期是对的(当时只有一种长任务), 但它有个致命性质:
**任何新类型都会被冒充成导入, 而且是静默的**。谎报成另一种任务比"不认识"更糟 ——
用户会去查"我什么时候导入了数据", 排查方向直接跑偏。

### 三、同一个坑已经踩过两次, 这是第三次

`core/eval_kick.py:15` 留着上一次的事故记录:

> `taskWatch` 的 `kind` 判定 —— `cleansing_eval` 落到 `'cleansing'` 分支, 打的是
> `/cleansing/status?task_id=<x>_eval` …… **看守看得见它、却永远推不动它**

那次修在了 `api/taskWatch.ts`(改成精确路由 + 认不出返回 null), 但**没修 TaskPage**——
两处各自白名单、各自兜底, 修一处不修另一处。这次 `rule_eval` 同时踩了第三处:

| 位置 | 职责 | `rule_eval` 的处理 | 后果 |
|---|---|---|---|
| `routes/tasks.py:131` | 列任务 | 全量 SELECT, 不过滤 | ✅ 正常列出 |
| `api/taskWatch._kindOf` | 决定用哪个端点推进 | 返回 `null` → 不接管 | ✅ 安全(**不会**误判成 error) |
| `pages/TaskPage` 渲染 | 决定怎么显示 | 兜底 `'cleansing'` | ❌ **显示成导入** |
| `pages/TaskPage` toast | 完成提示 | 兜底原始 task_type | ❌ 弹 `rule_eval` 英文原文 |
| `components/tasks/TaskCard` | 评估进度条 | 只认 `cleansing_eval` | ✅ 见 §六 |

顺带发现一处**长期死分支**: toast 判断的是 `task_type === 'clean'`, 而实际值是
`'cleansing'` → 该分支永远不命中 → 所有导入任务的完成提示显示的都是英文 `cleansing`。
这是同一个"多份白名单"病的症状。

### 四、改法：抽纯模块 + 兜底只许 unknown

**没有**在 TaskPage 里打个补丁, 而是把类型推导提成 `components/tasks/taskType.ts`
(纯函数/无 React 依赖):

```ts
export function taskTypeOf(task: TaskLike): TaskType {
  if (tt === 'cleansing') return 'cleansing'
  ...
  if (tt === 'rule_eval') return 'rule_eval'
  if (tt === 'reset' || id.startsWith('reset_')) return 'reset'
  return 'unknown'          // ← 认不出就是「任务」, 不冒充
}
```

三条纪律写进文件头:

1. **兜底只能是 `unknown`**。新增类型忘登记 → 显示「任务」。
2. **`cleansing` 显式登记**, 不再靠兜底 —— 兜底能兜住它, 正是这个 bug 的来源。
3. **本模块是展示层唯一真源**, 渲染与完成提示共用。图标留在页面(`TYPE_ICON`),
   文案键(`TYPE_LABEL_KEY` / `WHAT_LABEL_KEY`)在模块里, 便于单测。

`rule_eval` 与 `cleansing_eval` **共用标题**「评估联动」—— 对用户是同一件事(规则评估),
只是触发方式不同(每日全量 vs 导入后增量)。区分放在副标题: `task.eval_full` = 「全量评估」。

### 五、单测与变异验证

新增 `src/tests/taskType.test.ts`(7 条)。写完做了**两次变异**, 因为第一次就发现断言分工有问题:

| 变异 | 结果 | 说明 |
|---|---|---|
| 兜底 `unknown` → `cleansing` | 只有第 3 条红 | 第 1 条(rule_eval)因显式分支先命中而**仍然绿** |
| 删掉 `if (tt === 'rule_eval')` 分支 | 只有第 1 条红 | 第 3 条绿 |

两条各守一半, 缺一不可 —— 只写第 1 条就挡不住"兜底再写错", 只写第 3 条就挡不住
"rule_eval 分支被删"。这个分工已写进测试注释, 防止后人以为一条就够。

### 六、为什么没给 rule_eval 加评估进度条

## §15.205 379 秒是哪来的 + 两个「说谎但不报错」的缺口

### 一、用户三问，先把结论摆出来

| 问 | 答案 |
|---|---|
| 379 秒的评估是哪个场景？ | **手动/看板兜底的全量 deep**，不是定时任务 |
| 进度怎么保障（没加 3s 加速）？ | 靠 `continue_tasks` 接力，不靠前端看守 |
| 四维数据怎么保障？ | `_post_channel` 每渠道评完就跑批次对账，**只告警不自动修** |

### 二、为什么能断定不是定时

`_WINDOWS["daily_rules"] = (3, 30, 6, 0)` —— 定时只允许 03:30~06:00 CST 内触发。
而任务 `ev_1794804393_6117` 创建于 **12:46:33**，窗口外，平台调度不会在这个点调。

真实触发链：

```
我跑 relay_verify.py --only eval（第一步清当天 maintenance_log 占位）
        ↓
用户/脚本打开看板 → _daily_rules_guard() 判「今天没评过」
        ↓
run_daily_rules() → 建 eval_tasks id=30001
   scope = {"channels":["jd","other"],"ats":[],"deep":true}
        ↓
同请求内推首片（budget 8s），剩下交给 continue_tasks
```

`deep=true` 决定了它比日常重：`prep → eval → post（四维对账+健康快照）→ kick`；
而保存规则触发的那条是 `prep → eval → kick`，**没有 post**。

### 三、进度为什么不需要前端 3s 看守

三道入口都会调到同一个续跑：

| 入口 | 调用 |
|---|---|
| 任意 HTTP 请求 | `index.py` 中间件起 daemon 线程 |
| `/health` 5 分钟 ping | 平台探活顺带推进 |
| 平台 cron | 定时撞一次 |

续跑自身有节流和预算：`_throttle("continue-tasks", 30)` + `SELECT ... status='running' LIMIT 20`
+ `step(tid, budget=40.0)`。实测 6 轮 / 384.7s ≈ **64 秒一轮**（30s 限频 + 40s 预算 + 间隙）。

所以 3s 加速只影响**任务卡上进度数字的刷新延迟**，一点都不影响完成时间。上一版文档把它写成
「不加看守就慢」是错的，已在 `PERF.md` 更正。

### 四、缺口一：`eval_tasks` 留 `pending` 僵尸，横幅永久挂

`enqueue()` 原本只写 scope：

```python
execute_id("INSERT INTO eval_tasks(scope) VALUES(%s)", [...])
```

落库靠表默认值 → `status='pending'` + `started_at=NULL`。而 `eval_live_cond()` 是

```python
"(status='pending' OR (status='running' AND started_at > NOW() - 10min))"
```

**pending 无条件算「在跑」**。这条路以前没人走（建任务的是 `_drain_eval_tasks`，
它抢到立刻改 running），§15.200 把 `run_daily_rules` 改成「建任务+推首片」之后，
`enqueue` 的行**不经队列**，于是 pending 一直挂着 → 看板「规则重算中」永不消失。
§15.158 当时堵过同类问题，但只堵了 `running`，pending 是它没覆盖的第二条路。

三处修：

1. `enqueue` 改成 `INSERT INTO eval_tasks(scope, status, started_at) VALUES(%s,'running',NOW())`
   —— 这行本来就不排队，建完同请求内推首片，`pending` 是错误状态。
2. 新增 `rule_eval_task.abandon(task_id)`：`continue_tasks` 判 30 分钟超时时调它，
   补收 `eval_tasks` + `_settle(p, ok=False)` 回滚占位。补的是**进程直接消失**那条路
   （实例被冻结时 `step` 的 except 根本不执行）。
3. `close_stale_runs` 增加 `status='pending' AND created_at < NOW()-10min` 收尾。

**`rules.py` 里那两处 `INSERT INTO eval_tasks(scope)` 是有意不动的**：那条路真的在排队
（写 pending，等 `_drain_eval_tasks` 原子抢占改 running），pending 语义正确。区分标准是
「建完是否同请求内推进」—— 推的写 running，等的写 pending。抄错一处就会两头出错。

### 五、缺口二：`source` / `driver` 埋点恒为假值

`enqueue(..., source="cron")` 有默认值，而唯一调用点没传 → **所有任务** `params.source='cron'`。
我自己排查 379 秒时就被它误导过一轮：看到 `cron` 就去翻调度窗口，白翻。

`step(..., driver="frontend" if _created else "backend")` 同理，任务卡显示「前端轮询」，
实际是后端接力。

改法：`run_daily_rules(channels, deep, alert_types, source="cron")`，三个真实调用方各传各的：

| 调用方 | source |
|---|---|
| `routes/cron.py`（平台调度） | `cron` |
| `routes/dashboard.py:_daily_rules_guard` | `dashboard` |
| `routes/rules.py:_drain_eval_tasks` | `rule_save` |

`driver` 统一 `backend`。

### 六、四维对账只告警不修，是有意设计

`_post_channel` 在某渠道 SKU 全评完后跑：`inventory LEFT JOIN batches` 按
`sku + 69码 + 仓 + 仓型` 聚合，只算自有仓（`SELF_WAREHOUSE_TYPES`），
判据 `|可用 − Σ批次| > 1`，命中写 `quality_logs(warning)`，**不自动改数**。

不自动修的理由：对账只能证明"这两个数不一致"，无法证明哪个对。自动修会把上游导入的
错误固化成"已校准"，比不修更危险（§15.199 定案）。

### 七、门禁

- `preflight` **8/8**、回归 **864/0**、`relay_selftest` **40/40**、`test_audit` **82/0**
- `relay_selftest` 新增 4 条：enqueue 写 running、`abandon` 存在、超时分支调它、pending 被收
- 变异验证：去掉 `abandon` 调用 / 还原 `INSERT` 写法，对应断言立刻变红

### 八、本轮文件

- `cloud-functions/api/core/rule_eval_task.py`（enqueue 状态 + `abandon`）
- `cloud-functions/api/core/maintenance.py`（`close_stale_runs` 收 pending）
- `cloud-functions/api/routes/cron.py`（超时调 `abandon` + `source` 透传 + driver 固定）

## §15.206 日销口径收敛成一套（四家同名同值）

### 一、用户定案

原话：「公式太杂了漂移严重。消费方底料不变，现在需要做个统一收敛。」
三条决策：**① 全用 cut ② 3σ 保留 `max(3σ, 1.5×非零均值)` ③ 采购两窗口是设计**。

底料 `sku_sales_stats` 一个字段没动 —— 收敛只发生在「消费方怎么读」这一层。

### 二、收敛前 vs 收敛后

| 消费方 | 收敛前 | 收敛后 |
|---|---|---|
| 补货 bbcc / traditional | `rolling_predict(cut 三列) × season × act` | **不变** |
| 进销存 platform / own | `rolling_predict(raw 三列)` | 改读 cut |
| 看板断货/库存/健康 | `rolling_predict(raw 三列)` | 改读 cut |
| 告警 / 规则引擎 | `ds28` **单值** | 改读 cut 三列融合 |
| 采购 | 手写三档 `ds14/ds28`（raw） | `rolling_predict_2w(cut 14/28)` |

收敛前同一 SKU 的 `daily_sales` 最多差 39%（SKU-08291-J：进销存 4.35 / 补货 2.64），
差别不是「谁算错了」，而是**喂进去的列不同**。收敛后四家同名同值，只剩采购窗口数不同。

### 三、改法：两个入口 + 一次层级判定

**入口只留两个**，都在 `biz/sales.py`：

```python
rolling_predict(s7, s14, s28)      # 3 窗口，9 档权重表（原有，语义不动）
rolling_predict_2w(s14, s28)       # 2 窗口，3 档（.55/.45 | .20/.80 | .35/.65）
```

`rolling_predict_2w` 的权重是从 `purchase_calc.py` 手写分支里**原样搬出来**的，
所以采购结果逐位不变 —— 收敛公式，不改数值。

**`Series.fused()` 的关键是层级只判一次**：

```python
def _level(self, sku, barcode, dim):   # ①该维该码 ②该维SKU合计 ③无
def fused(self, sku, barcode, dim):    # 判一次层级 → 三列同源取值 → 融合
```

不这么做的后果是能真实发生的：`value("ds7")` 命中码行、`value("ds14")` 因为码行缺列
降到合计行 —— 融合值就成了「7 天来自码、14 天来自 SKU」的混搭，趋势判定跟着疯。
原来的单列 `ds28` 只有一个值，天然不存在这个问题；改成三列就必须把层级钉死。

`metrics.load()` 默认 `fields=("ds7_cut","ds14_cut","ds28_cut")`，
`judge_units` / `tally` 的 metric 默认由 `"ds28"` 改为 `"fused"`。

### 四、降级路径必须同口径，否则「物化挂了」就换一套数

四处「物化表为空就现场直算」的兜底，全部同步成削峰 + shrink：

| 位置 | 改法 |
|---|---|
| `biz/sales.get_sales_digest` | `calc_sales_multi({k: smooth_promo_spikes(v)}, sparse="shrink")` |
| `dashboard_stock_risk` | 抽本地 `_cutm()`，4 个来源（by_sku / daily_c / by_sku_bc / by_sku_wh）统一走它 |
| `purchase_calc` | 同上，14/28 两窗口 + `rolling_predict_2w` |
| `insights` | 只改取值列，直算路径本来就调 `_rebuild` 同源函数 |

这类兜底最容易漏：它只在物化表空的时候执行，正常测试永远走不到，
一旦触发就是「同一页面刷新两次数字不一样」。

### 五、对账（上线前必须看的东西）

**日销值**（jd `__C__` 合计行，n=9998）：

| 对比 | 中位 | p10 | p90 | 降超 20% 占比 |
|---|---|---|---|---|
| cut 融合 vs raw 融合 | **−23.9%** | −63.2% | 0.0% | 54% |

**告警判定迁移**（旧 `ds28` → 新 cut 融合，周期 6 天判 DOS）：

| 渠道 | 参与判定 | 新增告警 | 消失告警 |
|---|---|---|---|
| jd | — | 4（0.8%） | 75（0.8%） |
| other | — | 1（0.9%） | 90（0.9%） |

**采购建议量**：随日销同步下降约 **20%**。

### 六、代价：间歇性需求 SKU 会漏报（附归因拆解）

`SKU-06001-J`：告警用的值 3.536 → **0.99**，可撑天数 4.5 → 16.1 天，告警消失。
底料实测 `nnz7=0 / nnz14=1 / nnz28=6`，`ds7/14/28 = 0 / 0.929 / 3.536`，
`ds14_cut = 0.310`（`nnz=1` → shrink ×1/3），`ds28_cut = 3.536`（`nnz=6` → 不 shrink）。

**必须拆开看，否则会把锅全甩给 cut**（我第一版就写错了）：

| 环节 | 值 | 贡献 |
|---|---|---|
| 旧口径（只取 `ds28`） | 3.536 | — |
| 三窗口融合（档位 −1/−1，权重 `.40/.35/.25`） | 1.209 | **−65.8%** |
| 再叠 `shrink`（14 天 `nnz=1`） | 0.9925 | −17.9% |

**主因是三窗口趋势加权本身**：`nnz7=0`、`nnz14=1` 意味着近窗几乎没有销量，
而档位 (−1,−1) 给 7/14 天合计 75% 的权重 —— 值必然被拉到近窗水平。
这是趋势加权对**间歇性需求（intermittent demand）**的固有偏差，不是 cut 引入的。
`shrink` 只在 `nnz<3` 时生效、系数 `nnz/3`，这里额外贡献 18%。

也就是说：**即使回退到 raw，这个 SKU 的告警值也只有 1.209（−66%）**，照样不报警。

处置方向不是「再拆一套日销」（拆回去就等于白做），而是二选一：

1. **接受**：稀疏 SKU 证据不足，本就该少报；靠人工复核兜。
2. **融合层加稀疏保护**：`nnz7=0 且 nnz14<3` 时抬高 28 天权重（或退化为 `ds28` 单值）。
   这是新机制，要单独定方案、单独对账。

**现有规则参数治不了这个**（见 §15.207）：`accel_ratio` 依赖「今天有销量」，稀疏 SKU
当天无量就不触发；`buffer_*` / `lit` 是全局阈值，一调所有 SKU 一起变。

### 七、防漂移：一条静态扫描断言

```python

```

为什么需要它：`series` 只装了 cut 三列，任何人写回 `series.value("ds28", ...)` 都会
**静默取到默认值 0** —— 不抛异常、不报错，只让告警集体沉默。这种错线上表现为
「一切正常，就是没告警」，比崩溃难查一百倍。

变异验证：往 `insights.py` 插一行 `series.value("ds28", ...)`，断言立刻变红，删除后复绿。

## §15.207 规则引擎能调什么 + 采购页文案的真相

用户追问两件事：「采购页那两列什么文案？」「调阈值是在调参数？现有规则引擎里有这些？」

### 一、先认两个错

**错一：采购页没有「近14天/近28天日均」这个文案。**

我上一轮说「文案没改，用户可能以为算错」，是我凭印象编的。实际是：

```tsx
// components/hammer/configs.ts
{ id: 'daily_sales', label: 'daily_sales' }
// locale.zh.ts:597
'col.daily_sales': '日销(融合/14/28)'
// locale.en.ts:598
'col.daily_sales': 'Daily sales (blend/14/28)'
```

它不是两列，是**一列**：主值 = 融合值，小字 = `↑ 4.3/2.9`（14 天 / 28 天）。
列头写「融合/14/28」，本来就在描述这三个数的结构 —— 换成 cut 之后结构没变，
**文案依然准确，不需要改**。真正的问题只是「数值变小了但页面没解释口径」，

**错二：稀疏 SKU 漏报的主因不是 `shrink`。**

（拆解见 §15.206 第六节）。已订正 CHANGELOG / ARCHITECTURE / 本文三处。

### 二、规则引擎里确实能调，路径是这样

参数不是写死在代码里，也不是另有一个「系统配置」页 —— 它就是 **stockout 那条内置规则的 `params`**：

```
规则页 → 断货预警(stockout) → 参数区
   ↓ 存 rules.params (JSON)
   ↓ 读 _rule_params("stockout", channel)
      rules.params  →  config  →  代码默认值   （三级兜底）
   ↓

```

「停用/删除=回默认」。

### 三、stockout 的可调参数全集（前端已暴露 11 个）

| 参数 | 中文标签 | 默认 | 作用 |
|---|---|---|---|
| `lit` | 补货周期天数 | 3 | **红灯**判据：`adj_dos ≤ lit` |
| `otif_min` | OTIF 置信下限 | 0.6 | 在途打折下限（`suppliers.score/5` 夹在 [0.6,1.0]） |
| `ss_z` | 动态 SS Z值 | 1.65 | 安全库存 `SS = z×σ×√(L/T)` |
| `sigma_days` | σ 样本窗口 | 60 | 标准差取多少天 |
| `accel_ratio` | 加速倍率阈值 | 1.3 | 当日小时流速超过日均多少倍算「加速」 |
| `accel_min_qty` | 加速样本量 | 10 | 触发加速的最小单量（防小数抖动） |
| `buffer_orange` | 橙灯缓冲上限 | 1.2 | `buffer ≤ 1.2` 且逼近周期 → 橙 |
| `buffer_yellow` | 黄灯缓冲上限 | 1.0 | `buffer ≤ 1.0` → 黄 |
| `orange_slack_days` | 橙灯天数余量 | 1 | 橙灯要求 `adj_dos ≤ lit + 1` |
| `include_avail_zero` | 已断纳入红灯 | 1 | 0 = 已断的交健康卡，不进断货卡 |
| `log` | 记录日志 | 0 | 调试用 |

`buffer` 的实际含义是**水位比**，不是天数：

```python
buffer = avail / max(max(safety_line(ds, lit), ss_dyn(sku, lit)), 1)
```

可用量 ÷ 目标水位（安全线与动态 SS 取大）。`buffer ≤ 1.0` = 已经低于目标水位。

### 四、为什么这些参数治不了稀疏 SKU 漏报

| 参数 | 能不能治 | 原因 |
|---|---|---|
| `accel_ratio` / `accel_min_qty` | ❌ | 加速靠「当天小时流速」，稀疏 SKU 当天没销量 → 永不触发 |
| `buffer_orange` / `buffer_yellow` | ⚠️ 全局 | 调高确实更容易判橙黄，但**所有 SKU 一起变** |
| `lit` | ⚠️ 全局 | 红灯判据直接吃它，同理全局 |
| `ss_z` / `sigma_days` | ⚠️ 间接 | 只影响水位（buffer 分母），不直接解救 `adj_dos` |
| `include_avail_zero` | ❌ | 只决定「已断的进不进卡」，与日销无关 |

**根因在于日销值本身**（1.209 的三窗口融合值），任何在「阈值侧」做的调整都是
用全局灵敏度换局部正确性 —— 调完会发现别的 SKU 冒出一堆假告警。

真要治，只能动融合层（稀疏保护），或接受（稀疏 SKU 本就证据不足）。

### 五、结论

**「调阈值」这个建议我上一轮给得太轻率。** 准确说法是：

> 参数确实在规则引擎里、确实可调、且改完即时生效（无代码、无部署）。
> 但它们治不了稀疏 SKU 漏报 —— 那需要融合层的稀疏保护，属新机制。

## §15.209 趋势长基准：只换「60」的值，不动渲染

### 一、用户指令（原话）

我把补货页第三档箭头改成「14 vs 28」，那是动了渲染语义 —— 本轮改回来。

### 二、改回来的是什么，换掉的是什么

补货页日销列原本渲染三个数 + 三档箭头，第三档是「28 vs 长基准」：

```
7 ↑ 14 ↑ 28        ← 箭头①7→14  箭头②14→28  箭头③28→长基准(不显示数字, 只用于判定)
```

| | 长基准字段 | 值 | 前端判据 | 结果 |
|---|---|---|---|---|
| 原 | `daily_sales_60` | `rolling_predict(7/14/28)` 融合值 | `28 > v*1.15` | 75.1% 朝上 / 2.7% 朝下 |
| 现 | `daily_sales_56`（`_60` 退役，见九） | `ds56_cut` 近 56 天 cut 日均 | 同上（未改） | 59.0% 上 / 14.9% 平 / 24.5% 下 |

前端 diff **6 行增 6 行删**，全部在同一个三元表达式里（`daily_sales_14/28` → `daily_sales_28/60`），
样式对象、图标组件、列宽、表头词条、i18n 键一个字符没动。

### 三、为什么原先那个值是错的

`daily_sales_60` 里装的是 `rolling_predict`（7/14/28 三窗口融合值），两处不在理：

1. **不是 60 天**。它是融合值，权重表把所有短期趋势都吸收进去了；
2. **结构上恒低于 ds28**。实测 `ds28/fused` 中位 **2.00** —— 拿它当分母，`28 > v*1.15`
   对 75% 的 SKU 成立、只有 2.7% 判「下滑」。箭头读的是权重表，不是需求变化。

§15.208 当时的处置是「改用 14 vs 28」，方向是对的（两侧同口径），但它把这一档**变成了
另一个窗口对比**，而不是用户要的「28 对长基准」。本轮按指令回到 28 vs 长基准，并修根：
把长基准换成真值。

### 四、为什么是 56 天，不是 60 天

- **28 = 4 周，56 = 8 周，恰好 2 倍**：两窗口的星期构成完全对称，比值里不会混进
  「这 28 天含几个周六」的伪影。60 天是 8 周 + 4 天，两端错开 4 个星期位。
- 削峰窗口必须与取数窗口**配对**：`smooth_promo_spikes` 的 `max_win` 原写死 28，
  直接拿它算 56 天窗口，29~56 天前的促销尖峰会原样留在窗口里抬高基准
  → 全体商品显示「下滑」。新抽的 `cut_series(daily, win)` 把 `max_win=win /
  hist_days=win+32` 绑在一起：28 天窗口的取值与收敛前**逐位一致**（单测 ① 反证过）。

## §15.210 四维验证暴露的五项根治（新鲜度 / 采购粒度 / 降级削峰 / 季节系数 / 加列回填）

### 一、用户指令与实测结论

做完上一轮的四维验证（实时性/准确性/完整性/可靠性）后，用户提了四点：

1. 数据新鲜度功能有问题 —— 数据停更几天了，前端 UI/UX 没有任何提示；
2. 采购底料不都应该按补货口径「SKU + 69 码组合优先」？还有遗漏？
3. P1 的活性门控不动（`0.04` 这种极端稀疏没有补的必要）；
4. 执行根治剩余项，红线依旧。

逐条核过：**第 1、2 条都是真缺陷**，第 3 条按用户定案关闭（已写进 `CONTEXT.md` P8-5）。

### 二、缺陷 1：新鲜度为什么「停更 7 天也不提示」

功能是 **2026-10-29 上线**的（`data_freshness` 表 + 导入时 UPSERT + 看板胶囊圆点 + 列表页
标题圆点，见 `changelog-2026-08~10.md`「五、数据新鲜度」）。代码注释也写着 2026-10-29，
用户记的「10 月底」正确。

实测现场（2026-11-16 16:46）：

| 源 | `last_import_at` | `last_biz_date` | 库里真实最大业务日期 | 旧 `days` | 旧 `level` |
|---|---|---|---|---|---|
| order (jd) | 2026-11-09 13:16 | 2026-11-12 | `MAX(ordered_at)` = 11-09 22:59 | **7** | **0（正常）** |
| inventory (jd) | 2026-11-09 13:16 | （空） | 无业务日期列 | 7 | **0** |

两个缺陷叠在一起，正好把「最常见的那种停更」藏掉了：

**① 阈值一刀切 `≤7 天 = 正常`。** 日更数据停 7 天，恰好落在阈值内 → `level=0` → 前端
`StaleDot` / `StaleDotInline` 直接 `return null`（它们只在 `level>0` 时渲染）。用户看到的
是"什么都没有"，连一个灰点都没有。

**② 判据只认 `last_import_at`（操作时间），且记账值本身是假的。** 写入端取的是
「**这批文件里**的最大业务日期」—— 被清洗跳过、去重丢弃、`deleted_at` 非空的行不进库，
记它等于谎报"数据已经到那天"。实测 `order.last_biz_date=11-12`，库里真实
`MAX(ordered_at)=11-09`，差 3 天。

> 这两条组合起来的后果比单看更糟：即使有人在 11-16 导了一份 9 月的旧文件，
> `last_import_at` 也会变成"今天" → 判新鲜；而真正该看的是业务日期。

**改法（三处，都不动前端渲染）**

1. **判据**：`days = max(业务日期差, 导入时间差)`。内容旧就是旧，不问谁导的。
   业务日期天然滞后的源（回款账期、档案、库存无业务日期列）走白名单
   `_FRESH_IMPORT_ONLY`，只认导入时间。
2. **阈值分档**：按该源真实更新节奏定档，不再一刀切 ——

   | 源 | 转橙 | 转红 | 依据 |
   |---|---|---|---|
   | 订单 / 库存 / 平台库存 / B仓库存 | 2 天 | 4 天 | 日更；当天/昨天正常（不制造狼来了） |
   | 出入库流水 | 8 天 | 31 天 | 随业务发生，一周没动静正常 |
   | GMV 回款 | 31 天 | 61 天 | 按月导入，月中差 15 天是常态 |
   | 商品 / 供应商档案 | 15 天 | 61 天 | 极少变 |

3. **记账下沉**：`common.record_freshness(channel, target, rows)` 成为唯一写入点，
   `last_biz_date` 取**库里真实 MAX(业务日期)**；两个旧调用点（`cleansing` 的 done 分支、
   `cleanse_write` 的旧 finalize）都改成调它，删掉各自的 INSERT。
   成本：一次全表扫（`orders` 没有 `(channel, ordered_at)` 索引），一天几次可接受 ——
   **读路径绝不能这么查**（首屏 4 个页面都会调新鲜度）。
4. **缺失源可见**：原来只返回**有记录**的源，jd 9 类只有 3 类、other 只有 3 类，
   另外几类在弹层里连一行都没有。现在补齐为 `days=null / level=0 / missing=true`
   —— 不报红（新渠道不该一上线就红），但**看得见**。

改完实测：`jd` / `other` 的 `staleLevel` 都从 **0 → 2**，四个看板指标全部转红，
弹层里能看到「平台库存 / B仓库存 / 商品档案 / 供应商」四类缺记录。

### 三、缺陷 2：采购 14/28 与主值粒度不一致

用户问「采购底料不都是按补货口径 SKU + 69 码组合优先？还有遗漏？」—— **是遗漏**。

补货侧一直是 `_rd(sku, wh, bc)`：有 69 码读该码行，没有则降级读合计行。采购的主值
（`daily_sales`）和 56 列都走 `_ds_src`（码行），**唯独 `daily_sales_14` / `daily_sales_28`
从 `s14m/s28m` 取 —— 那是 SKU 合计行**。于是同一行里：

- 主值 = 按码 14/28 融合；
- 两个小字 = 整 SKU 的 14/28；
- 第三个箭头（28 vs 56）= 按码。

实测 97 个多码 SKU 里 **120 行**三个值来自两个粒度，其中 **57 行箭头方向反了**
（如 SKU-00082-J 展示 `0.7 / 0.2`「上升」，同码真值 `0.2 / 0.2`「持平」）。

改法：`_src14 / _src28 / _src56` 三列全部从**同一个 `_ds_src`** 取，无码时一起降到合计行。

```python
if _ds_src:
    _src14 = float(_ds_src.get("ds14_cut") or 0)
    _src28 = float(_ds_src.get("ds28_cut") or 0)
    _base_ds = round(rolling_predict_2w(_src14, _src28), 1)
    _src56 = float(_ds_src.get("ds56_cut") or 0)
else:
    _src14, _src28, _src56 = s14m.get(sku, 0), s28m.get(sku, 0), s56m.get(sku, 0)
    _base_ds = fused.get(sku, 0)
```

对拍（jd，9442 行）：`by_bc=9440 / fallback=2`，`daily_sales_14/28/56` **0 差异**。

### 四、缺陷 3：降级直算的削峰基线恒空

`get_sales_digest`（看板）与 `dashboard_stock_risk`（断货卡）的降级分支都是：

```python
by_sku, _, _ = load_daily_sales_grouped(28, channel)          # 只取 28 天
... smooth_promo_spikes(v) ...                                # 基线要 28~60 天
```

`smooth_promo_spikes` 的基线取 `range(max_win, hist_days)` = 28~60 天 —— 数据只取了
28 天，基线列表**恒空** → 函数在 `if not hist_nz: return daily` 直接返回原序列。
**不抛异常、不写日志、不降级**，只是削峰这一整道处理静默消失了。

实测影响：11.1% 的 SKU 日销偏高，最大 **2.06 倍**（促销尖峰整根算进日均）。

改法：两处都改成「取 90 天 + `cut_series(28)`」，与物化重建 `_rebuild_sku_sales_stats(channel, 90)`
完全同法。并加静态扫描：全仓任何消费方**直接**调 `smooth_promo_spikes` 即失败，
只允许经 `cut_series` 入口（`max_win=` 那一行是 `cut_series` 自己）。

### 五、缺陷 4：季节系数两套读法

| | 补货 `_season_factor` | 采购（内联） |
|---|---|---|
| 查什么 | 只查**本渠道**行 | 一次读「本渠道 + `channel=''`」塞进 dict |
| 缺行时 | 直接 1.0，**不认全局默认** | 全局行覆盖本渠道行 |
| 覆盖顺序 | — | 由 MySQL 返回序决定（不可控） |

结果：只要存在全局 `season_config_*` 行，**本渠道设的季节系数会被全局值盖掉**，
同一天同一 SKU，补货与采购用两个系数算两个需求。

改法：`core.metrics.season_factor(channel, mode, cfg=None)` —— 读 `channel_cfg`
（渠道行覆盖全局，语义唯一），解析规则（仅 `enabled` 生效、多档取最高）只写一次。
补货的 `_season_factor` 退化成一行委托；采购删掉内联解析。
季节保存点补了 `invalidate_cfg(channel)`（`channel_cfg` 有 60s 进程内缓存，不失效就要等一分钟）。

当前 `jd` 的 `season_config_bbcc` 三条全 `enabled:false` → 系数 1.0，两套读法**现值相同**，
所以这条改动对现网数字零影响 —— 它是为"启用季节系数那天"买的保险。

### 六、结构性问题：物化加列不回填

这不是某一列的 bug，是**只要再加一列就会重演**的机制缺陷：

`schema_create._COLUMN_ADDS` 只负责把列加上去，存量行新列恒 0；读侧
`float(r.get(col) or 0)` 把 0 当成"真的没有"。于是 other 渠道 **82,264 行**
`ds56_cut=0` 而 `ds28_cut>0`，趋势箭头恒判「上升」—— 页面看起来完全正常。

改法：`get_sku_sales_stats` 入口加**列级哨兵**：

```sql
SELECT 1 FROM sku_sales_stats WHERE channel=%s AND ds28_cut>0 AND ds56_cut=0 LIMIT 1
```

- 每渠道每进程最多查一次（`_STATS_COL_GUARD` 状态机 `checking/ok/rebuild/fail`）；
- 命中则起 **daemon 线程**重建（12.6 万行 / 187s，**绝不能放请求路径**）；
- 重建后复跑哨兵，清干净才置 `ok` 并 `invalidate("orders")`（红线 19：无产出不失效）；
- 失败置 `fail`，冷却 600s 再试（红线 15 不靠盲重试）。

同时把 other 渠道**手工重建一次**：`127,555 行 → 126,295 行`，
`ds28>0 且 ds56=0` 从 **82,264 → 0**，耗时 187.5s。

> 行数下降 1,260、`ds28>0` 从 82,264 → 79,189 是**时间窗效应**，不是丢数据：
> 数据停更在 11-09，近 28 天窗口从「10-12~11-09」滑到「10-19~11-16」，尾部 7 天全 0，
> 分母多了 7 个零日 → 一部分极小的 ds28 被摊薄成 0。这正是「新鲜度」功能存在的理由。

### 十、顺手修：`type=purchase` 的导出落进了补货分支

验证导出表头时发现的：`_build_export_rows` 的分支写的是

```python
if exp_type in ("replen", "purchase"):     # ← purchase 被并进补货
```

于是 `POST /api/exports?type=purchase` 返回的是**补货数据 + 补货表头**
（`B缺口 / C仓周转 / B建议补`），采购该有的 `建议采购量 / 箱规 / 实购` 一个都没有，
且全程 200 不报错。前端洞察页实际传的是 `purchase_suggestions`（正确分支），所以页面上
"采购导出"是对的 —— 但任何脚本/第三方按直觉传 `purchase` 就会拿到错的表。

改成别名：

```python
if exp_type == "purchase":
    exp_type = "purchase_suggestions"
if exp_type == "replen":
    ...
```

验证（线上，部署后）：`type=purchase` 表头含 `日销56`、不含 `日销60`；补货表 27 列齐全。

### 15.148 规则评估被踢出事件链路 + 三处「显示层」缺陷(2026-11-06)

用户原话锚点:
> 「规则评估需要改为按事件触发（也就是清洗页导入数据就会自动联动，而且我没记错一直都按这个口径，
> 现在是否被动过/失效？）不要等每日兜底或者手工，另外这个手工只服务于运维。」

结论: **用户的记忆是对的, 是被动过 —— 而且是两处独立断点叠加。**

#### 一、断点 1: 看守把 `cleansing_eval` 当成 `cleansing`, 打错端点

`frontend/src/api/taskWatch.ts` 原来只有二元归类:

```ts
const kind: 'seed' | 'cleansing' = task_type === 'seed' ? 'seed' : 'cleansing'
```

于是 `cleansing_eval` 落进 `'cleansing'` 分支, 请求
`/api/cleansing/status?task_id=<导入id>_eval`, 而该端点开头就是
`SELECT ... FROM sync_tasks WHERE task_id=%s` 并只认 `task_type='cleansing'` 的语义 ——
`_eval` 行虽然存在, 但走的是导入分支的解析流程, 立刻 `{ok:false, error:"任务不存在"}`。
更糟的是 `_drive()` 的 `catch` 把它当成**网络抖动**处理: 不报错、不 unwatch,
只累加 `stalls` 触发退避 —— 所以这个失败**永远不会出现在任何日志或 UI 上**,
表面上"看守正在推", 实际一次都没推进。

修复: 三值 `WatchKind = 'seed' | 'cleansing' | 'cleansing_eval'` +
`_kindOf()` 单一判定点 + `_url()` 三路分流(评估走 `/cleansing/eval-status`)。

#### 二、断点 2: 建了任务就撒手, 没有任何"导入完即触发"的驱动

导入 done 分支(`cleansing.py`)建好 `_eval` 任务、写好 `sku_list` 后直接 `return`。
此时只有三条路径可能推进它, **没有一条是"导入完立刻跑"**:

| 路径 | 真实行为 |
|---|---|
| 前端看守 | 只在任务页/App 首次挂载 `adoptRunning(/tasks?limit=8)` 才接管; 用户导完切走或关页 → 无人推 |
| `continue_tasks` 兜底 | 中间件 60s / `/health` 保活 / 平台 05:05 cron 才跑, 且只处理 `status='running' LIMIT 20` |
| 手工「立即运行」 | `POST /rules/evaluate` 全量重算 —— 用户明确: **这只服务于运维** |

线上实证(2026-11-06 13:1x 采样 `alerts?type=low_stock&limit=400`): 低库存告警的
`created_at` 不是导入时刻, 而是散落在 `12:58` / `13:06` / `13:13` 几个**互不相邻**的批次
(109 / 290 / 400 条), 每批都对应"有人碰了一次兜底"。这就是"只能等兜底"的物证。

修复: 新增 `core/eval_kick.py`(红线 A: 122 行文件 / 单函数 24 与 48 行),
导入 done 后 `kick_eval_task(task_id)` 起一个 daemon 线程**本地把分片跑完**。
线程内直接调 `cleansing_eval_status(...)` —— 与看守/兜底**同一条代码路径**,
所以幂等/租约/分片/降级行为完全一致, 不存在"两套评估逻辑漂移"。

降级设计(线程可能被 Makers 冻结, 不能把它当唯一保证):
- 线程跑完 → 任务 `done`, 前端下次进场直接看到结果, 不需要它参与;
- 线程被冻 → 任务仍 `running`, 兜底/看守/手工照旧接上(**零回归**)。

即: 事件驱动是**主路径**, 兜底退化为真正的"保底"而不是"唯一路径"。
`_MAX_SEGMENTS=60` 片上限: 超出部分不丢(任务仍 running), 只保证一个超大导入
不会把实例钉在这条线程上。

#### 三、`inv.exp.*_icon` 缺词条: 中文界面的效期状态列显示英文

`statusLabels.expiryStatusLabel(code, withIcon=true)` 取的是 `t(key + '_icon')`:

```ts
return withIcon ? t(key + '_icon') : t(key)
```

而字典里当时**只有 `inv.exp.warn_icon`**, `ok` / `no` / `expired` 三个都没有。
`t()` 缺词条时回落到**键名本身**(`locale.ts:21`), 于是中文界面「效期状态」列
直接把 `inv.exp.ok` / `inv.exp.expired` 印出来 —— 看起来像"i18n 键值没处理好",
实际是**词条缺了 3 个**, 不是映射写错。

修复: zh/en 各补 `inv.exp.ok_icon` / `inv.exp.no_icon` / `inv.exp.expired_icon`。
门禁里它们显示为"死键不算死"是因为引用是动态拼接(`key + '_icon'`) ——
`i18n_audit.py` 的"动态前缀产键函数 3/3 就位"已覆盖这一类。

#### 四、自有仓健康卡效期明细「乱码」= JS 硬切 40 字断了句

`OwnHealthCard.tsx` 原为:

```tsx
{x.description ? ' · ' + String(x.description).slice(0, 40) : ''}
```

后端 `description` 是中文自由文本:

```
批次 #125008 已过期 15 天(到期 2026-10-22), 自有可用 208 件待报损/急调   ← 52 字
```

切在 40 正好断在 `(到期 2026-10-22), 自有可用` 之后 —— 半句、无标点收尾,
用户读起来就是乱码。而且这一格本身已经有 `text-overflow: ellipsis`,
**真正的省略号由 CSS 负责**, JS 再切一刀纯属多余且有害:
① 断句位置不可知; ② 与弹窗(`OwnHealthSheet` 显示全文)口径不一致。

修复: `clipDesc()` 只在**标点/空格处**断(`[,,;;、。！？ ]`), 断点后补 `…`;
找不到合适断点时**不截**, 交回 CSS ellipsis(按渲染宽度算, 不破坏字形)。

#### 五、前端本地过滤冗余: 不是"多算一次", 是页码错位

用户明确要求不接受"保留无害"。`InsightsPage` 的 `filterBySearch` 对
补货/采购/滞销三张表**都又过滤了一遍**, 而后端早已支持 `&search=` 与
`page/page_size`。实际危害:

- **页码错位**: 后端按"已筛结果"切页, 本地二次过滤把第 2 页筛成几条 →
  用户看到"总数 300 / 实际只出来 12 条";
- **口径漂移**: 前端各表各写一份匹配字段(滞销漏了 `barcode`), 同一关键字
  在不同卡里结果不一致。

修复: 删掉 `filterBySearch`, 三张表一律直接用后端结果。

### 15.149 全维度审计报告落地: 逐条核对后修 11 项(2026-11-06 下午)

用户要求: **「读完这份审计报告结合提出的优先级, 去读取相关完整代码, 是否存在该问题再动, 不要误伤」**。
所以下面每条都标了"核验结论" —— 有两条审计的判断**不成立/做不到**, 按实际改法落地。

#### P0-1 任务看守误杀 —— 存在, 且比审计写的更严重(双向)

核验: `cleansing_status` 的 `except` 分支确实是
`execute("UPDATE sync_tasks SET status='error' ...")`(cleansing.py:771)。
`adoptRunning` 不过滤 task_type, 把 `/api/tasks` 全量 running 任务交给看守,
而 `_kindOf` 当时把 `export` 也归进 `'cleansing'` → 打 `/cleansing/status?task_id=<export_id>`
→ params 无 fname → 读不到 `clean_<id>` → 抛"源文件不存在" → **标 error**。

**审计没看到的一面**: 反方向更危险。`cleansing_eval_status` 收到一个导入任务的 id 时,
params 里没有 `sku_list` → `_batch = []` → 命中"全部分片完成"分支 →
**直接 `status='done'`**。一个只写了一半的导入会被标成"成功完成", 数据静默残缺。

修复(两层):
| 层 | 做法 |
|---|---|
| 前端 | `WatchKind` 四值(seed/cleansing/cleansing_eval/export), `_kindOf` 认不出的类型返回 `null` → **不接管**。宁可不推进, 不拿错端点推别人的任务 |
| 后端 | `common.type_ok(row, expect)` + 四个驱动端点入口校验, 不匹配返回 `status='not_found'` 且**不写任何东西**(`mark_driver` 从"SELECT 之前"挪到"校验之后") |

**关键取舍: probe 分支不校验。** 审计原话是"四个端点入口都校验", 但 App 层存在合法的
跨类型纯读 —— 例如用 `/seed/fill/status?probe=1` 读 `reset` 任务。若 probe 也校验,
这些读会永久 `not_found`, 前端轮询永不结束。纯读没有副作用, 不需要防误杀。

历史兼容: `task_type` 为空的行(2026-10 之前)一律放行, 不能因为加校验把在跑的老任务卡死。

#### P0-2 summary 漏传 mode —— 存在, 但"漏 channel"不成立

审计说三处 URL"没有 mode 也没有 channel", 结论是"非京东渠道按 BBCC 算"。
**核验**: `api/client.ts:144` 的请求拦截器会从 `localStorage.c_channel` **自动注入 channel** ——
所以 channel 没漏, 只有 mode 漏(拦截器不注入 mode)。真实影响范围是
"非 jd 渠道 / 切到传统模式时 summary 仍按 bbcc 算"。

修复:
1. `DashboardPage` 抽 `dashUrl()` 唯一构造点(首屏 load / 失败重试 / 30s 静默三处统一),
   并把 `_replMode` 加进两个 effect 的依赖(否则切模式后卡片停在旧口径);
2. 后端 `dashboard_summary/aux` 的 `mode` 缺省由硬编码 `"bbcc"` 改为 `ch_default_mode(channel)`。

#### P1-4 采购空库契约 —— 存在

`purchase_calc.py` 空商品库分支 `return ok({"suggestions": []})` 返回**已包装 dict**,
而其余路径 `return result`(list)。经 `cache_get` 后: `need_only=1` 迭代 dict 得到 key 字符串
→ `.get` 不存在 → AttributeError → 500; 坏值还被缓存 300s 反复复现。
修: 改回 `return []`, 并在 `list_page.shape()` 加契约护栏(非 list 按空列表 + 留痕)。

#### P1-6 新鲜度写入点已死 —— 存在, 但"兜底补 6 类"做不到

核验: `cleanse_write._finalize_import()` 全仓**零调用点**(2026-10-16 拆分后废弃),
其内的 `data_freshness` 写入是唯一写入点 → 表永远是空的。

**审计建议"兜底 SQL 补齐 6 类"在真实表结构上不成立**:
`inventory` / `inventory_archive` / `products` / `suppliers` **都没有 created_at / updated_at 列**,
inventory 更没有业务日期列 —— 硬写 `MAX(updated_at)` 就是每次请求一个 500。
实际可补的只有 `gmv_flow`(有 `arrived_time` + `created_at`)。

所以主路径修复放在**写入端**: `cleansing_status()` 的 done 分支补 `data_freshness` UPSERT,
覆盖全部 7 种 target; `rows_imported` 用**覆盖**不用累加(累加会让幂等重导变成双倍计数)。
兜底侧只加 `gmv_flow` 一类, 其余明确注释"无时间列, 依赖写入端"。

#### P1-3 档案类不幂等 —— 存在; 唯一键迁移暂不做

核验: `_write_batch` 只有 sum_mode / inv_upsert / ord_upsert 三个分支,
`products / suppliers / purchase_orders` 落进 `else: pass`(纯 INSERT) →
重导撞 `uq_products_sku` → 整批 1062 → 逐行降级 → 全失败 → "成功 0 条"。

已修: 加 `arch_upsert` 分支, `ON DUPLICATE KEY UPDATE` 覆盖业务列,
**排除 `id` / `deleted_at` / `channel`** —— channel 进覆盖列会把行"搬"到别的渠道,
deleted_at 进覆盖列会让重导旧文件复活用户删掉的商品。

**未做: 唯一键加 channel。** 线上实测两渠道各 1 万商品, SKU 靠 `-J`/`-O` 后缀刻意避开冲突,
说明业务侧尚未真正遇到"同 SKU 跨渠道"。DROP/ADD UNIQUE 是不可逆的破坏性 DDL,
且审计自己声明"未连真实 TiDB 验证" —— 这条需要先确认真实数据无重复再单独发布。

#### 四、这一轮踩到的坑（都值得记住）

1. **`INTERVAL %d` 不能进参数位**：PyMySQL 把 int 参数转成字符串 → `TypeError: %d format`。
   踩了两次（S4 收尾、S5 认领 SELECT），结论：天数一律 Python 级内联，SQL 提为模块常量。
2. **SQL 占位符错配 4 连击**：认领 UPDATE 少一个 `task_id`；完成标记与 stage 直读的 `IN (%s)`
   没插值。单 SKU 场景蒙对，多 SKU 必炸。→ 行构造器统一生成 + `db._guard_fmt` 前置守卫 +
   冒烟加"客户端格式化"检查（EXPLAIN 抓不到客户端 TypeError）。
3. **eval「领取即置位」是设计缺陷**：kick 线程认领后实例被冻结，兜底见未领行已空直接 done，
   **丢失的评估永远无法重放**。→ 改租约式认领（`claimed_at`/`claimed_token` 120s 可重认领），
   `applied` 退回"完成"语义，加 `waiting_claim` 防提前 done。
4. **归档区间 off-by-one**：`id > a` 永远漏掉 `MIN(id)` 那一行（实测 6 条只归档 5 条）→ `id >= a`。
5. **游标分页的 cursor 字段必须真在结果里**（今天新踩）：`INVENTORY_COLS` 不含 `id`，
   `_page[-1]["id"]` 恒 0 → 同一页被读 60 次，12 万行读成 30 万行。实测抓到的，加 `id,` 即修复。
   教训：**分页代码不跑大数据就不知道它没前进**。

#### 五、方案偏离（必须记录，否则后人以为漏做）

方案 S4-2 原定建 `eval_watermark(channel, scope, fp, cursor, updated_at)` 表做"水位"。
实际未建表，改用 **`eval_queue` 租约认领 + `import_stage` 物化** 表达同一件事：

- 水位表的作用是"知道上次算到哪、能不能续跑"。现在"待算的 SKU 清单"本身就落库（`eval_queue`），
  **清单即游标** —— 算完置 `applied=1`，认领超时 120s 可被别的实例重认领；
- 少一张表、少一处状态同步点，且天然支持"增量只算本批"（导入时就知道是哪些 SKU）；
- 代价：没有"渠道级指纹"用于跳过无变化的整轮评估。当前评估耗时 186~225s 可接受，暂不需要。

### 15.151 三条遗留收口：评估自愈、分批作业化、aux 剖析（2026-11-06 晚）

#### 一、评估被掐断后不再"永久跳过"（L1，真 bug）

**根因不在"没重跑"，在"跑之前就把结论写死了"**：`_daily_rules_guard` 在执行**之前**把当前
库存指纹写进 `maintenance_log.details`。实例被平台冻结时 `run_daily_rules()` 没跑完，但指纹
已经是"最新依据" → 之后每次请求都判定"今天已按此依据评估过"直接返回。

线上坐实：`maintenance_log` 里 2026-11-06 那行 `details=170200|165929|52852979`、
`created_at=11:37:51` —— 正是被冻结那次的**执行前**时间戳，且该指纹到 20:00 都没变过。

**改法**：`details` 三态 + 成功才落地。

| 取值 | 含义 |
|---|---|
| `''` | 待跑（从未跑 / 上次失败已回滚） |
| `#run#<fp>#<token>` | 某实例正持有；`created_at` 超 20 分钟未落地 = 被冻结，允许抢占重跑 |
| `<fp>` | 已完成（依据为该指纹） |

- CAS 抢占（`UPDATE ... WHERE details=<读到的旧值>`），令牌是随机的：`execute` 返回**改变行数**，
  同值 UPDATE 返 0 会被误判成"没抢到"（冻结遗留的标记本来就是同一个 `#run#<fp>`）。
- 结算也带令牌条件：跑的过程中若已被超时抢占者换掉，不许覆写 —— 否则会把"正在重跑"标成"已完成"。
- **cron 路由与看板兜底共用同一套**（`core.maintenance.claim_rules/settle_rules`）。原来两边各写
  一份：cron 用 `_claim` 只写空 details，于是 cron 跑完 details 仍为空 → 用户随后打开看板时
  兜底判定"依据已变"**又整跑一遍**（每天白跑一次全量评估）。

验证（独立日期 2099-01-01 隔离，10 个场景全过）：无行抢占 / 同指纹跳过 / 旧指纹重抢 /
新鲜令牌让路 / 超时令牌抢回 / 失败回滚 / 过期令牌不覆盖 / 兜底起线程 / 成功落指纹 /
失败可重跑。回归断言新增 8 条（含"cron 与兜底必须共用公共三态"的结构守门）。

#### 二、评估真分批（L2）：内存不再随行数线性增长

原来"游标分页读取"只是把大结果集拆成多趟，**读回来的行仍然全部堆在 `rows` 里**（17 万行），
再一次性建单元。现在还差最后一步。

| 改动 | 做法 |
|---|---|
| `metrics.units(acc=...)` | 增量累加器：同一个 dict 跨多批续写，语义与一次全量完全等价（插入顺序也一致） |
| 评估主循环 | 逐页读 → 直接喂给 `units(acc=)` → 页内行用完即弃；`rows` 只保留单元（远小于原始行） |
| `_agg`（超卖基准 SKU 汇总） | 原来遍历全部行逐条累加 → 改成库内 `GROUP BY sku`，只回 SKU 级结果 |
| `_PAGE` | 5000 → 20000 |

`_PAGE` 的依据（线上 other 8 万行实测，页数就是纯往返税）：
`5000→11.5s / 10000→6.3s / 20000→4.1s / 40000→2.9s`（一次全读 2.2s）。取 20000 是拐点。

**验证**：

- 线上真实数据逐单元比对（other 80,100 行 / 80,000 单元）：增量式与全量式**完全一致**；
  峰值内存 **138MB vs 300MB**。
- 端到端 A/B（worktree 跑旧实现、工作区跑新实现，同一份 `l2test` 数据 264 行 / 72 单元）：
  `hits=1`、**22 条告警逐条一致**（alert_type / 仓 / 69码 / SKU / 状态）。

#### 三、aux 剖析（L3）：先量，再决定改什么

**先纠正一个测量前提**：从沙箱访问线上，一个不存在的路径（`/api/nope-404`）都要 **1.7s** ——
那是网络 + 函数调用开销，不是业务。所以本地和跨区测出来的绝对值都不能直接当"aux 慢多少"。

线上 `other` 渠道冷算基线（等 60s 缓存过期后各打一次，5 轮）：**8.13 / 8.63 / 8.48 / 8.78
（中位数 8.63s）**，另有一次 30.77s 属 TiDB 侧抖动（同期无部署）。

剖析结论（`_build_aux` 内部 18 条 SQL、3 路并行）：

| 观察 | 数据 |
|---|---|
| 并行度不均衡 | 自有仓那一路 9 条 SQL（其余 3 / 6 条），决定整包时长 |
| 最大单条传输 | `sku_sales_stats` **20,093 行 × 14 列**，而调用方只用 ds7/ds14/ds28（3 列） |
| 次大 | `inventory` 90,100 行 × 8 列（判定必需，不动） |
| 连接开销 | 单连接固定 RTT 0.42s，3 路并行要 3 条连接 |

**已改**（零语义变更）：

1. `get_sku_sales_stats(fields=...)` 支持按需取列 —— 自有仓块只取 3 个指标列，
   少传 20,093 × 8 列 ≈ **2.5MB/次**。
2. `own_health` 的 products / 下游日销 / 自有仓批次三块**并行**（原来串行等三次往返）；
   峰值连接 6 条 < `DB_POOL_LIMIT=10`，不挤占其它请求。
3. 批次效期仍只取判定要用的 5 列。

**A/B 结果**：`_build_aux` 两个渠道（jd/bbcc、other/traditional）输出 JSON **逐字节一致**。

**部署后复测**（`f34764f` Success / Prod=yes，同法等 60s 缓存过期，5 轮）：
**7.43 / 7.73 / 7.73 / 8.38 / 10.79（中位 7.73s）**，基线中位 8.63s → **约 −10%**。
热态（缓存命中）1.57~2.46s —— 与部署前同量级，其中 1.7s 是"沙箱→线上"的网络地板（404 实测）。
另一轮出现过 76.17s / 33.78s，同期 `SELECT 1` 仍 0.42s、`COUNT(*) WHERE channel` 0.42s，
判定为 TiDB 侧瞬时抖动（非本改动引入，部署前后都出现过 30~76s 的孤立样本）。
**结论按"分布"看，不按单次看**：优化是真实的，但幅度被网络与数据库抖动掩住大半 —— 这也是
为什么这一条只做到"少传 + 并行"，再往下就得改判定架构。

**没做的**（记录判断，避免后人重复评估）：

- 把 `units` + `judge` 下推到 SQL —— 那是把 `core/metrics.py` 整套口径翻译成 SQL，等于养两份
  真源，风险远大于收益；`inventory` 9 万行的传输是判定本身的成本，砍不掉。
- 加长 `aux` 的 TTL（现 60s）—— 写操作已按域主动失效（`dash_aux` 登记了 orders/inventory/
  products/suppliers/rules/config），加长本可省一半冷算，但会让"关告警后多久消失"从 1 分钟
  变成 N 分钟，**感知不一致的代价高于省下的算力**，暂不做。

#### 四、这一轮新增的教训

1. **"写入时机"比"写什么"更容易出错**：占位/标记这类状态，写在动作**之前**还是**之后**，
   决定了中断时是"重跑"还是"永久跳过"。凡是"先占位再干活"的地方，都要问一句
   "占位失败/干活中断时，这个标记说的是真话吗"。
2. **`execute` 返回的是改变行数**：CAS 抢占若写回同一个值，会被当成"没抢到"。要么带令牌，
   要么比较其他会被改写的列。
3. **测量要先校准环境**：一个 404 都要 1.7s 的环境里，8s 与 9s 的差别说明不了任何事。
   先测"空请求"地板，再谈业务耗时。

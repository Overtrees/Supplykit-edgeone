### 15.152 判定结果物化：请求路径不再搬 15 万行算 10 个整数(2026-11-07)

#### 一、问题不是"慢", 是**结构性错配**

S3(11-06 16:16) 把判定从评估链路搬进了请求路径。之后每次打开看板, 服务端要搬
`inventory` 100,100 行 + 日销切片 63,186 行, 只为了算 **10 个整数**(健康分四档 + 低库存两数)。

线上 `perf_debug`(11-06 22:30):

```
查询 2.42s 组装 1.38s | stmt=6/5.22s max=2.07s | digest=2.41 inv=2.08 bundle=0.88 | jd
```

P0/P1 先做了同族的减少往返(6 条→1 条 bundle、合并两遍判定), 结果: `组装 3.14→1.2s`,
**总耗时 3.8s 一点没动** —— 因为两条大结果集挡着, 被"取最大值"的并行结构藏住了。
这印证了 §15.90 的那句: 常数项优化对"每请求 × 全量数据"的结构项无效。

#### 二、做法: 物化"算完的答案", 不是"把判定下推 SQL"

§15.151 拒绝过"units/judge 下推 SQL", 理由是"等于养两份真源"——那个判断是对的, 但**不是这件事**:

| | 下推 SQL(被拒) | `unit_state`(本次) |
|---|---|---|
| 判定公式 | SQL 条件表达式 **+** Python `classify()` | **只在 `metrics.judge()` 一处** |
| 真源数 | 2 | **1** |
| SQL 里 | 分档逻辑/安全线/在途口径 | 只有 `GROUP BY` / `WHERE state=...` |

新增三表(`SCHEMA_VERSION` 17→18):

| 表 | 内容 | 规模(jd) |
|---|---|---|
| `unit_state_head` | 每个 (channel, mode) 一行的**唯一切换点**: gen / fp / enabled / stale | 2 行 |
| `unit_summary` | 与 `metrics.tally()` 返回结构一一对应, 读回可直接喂 `_health_index(_tally=)` | 4 行 |
| `unit_alert` | 只存**非 ok** 单元(卡片读计数, 列表读明细, 同 gen 同源) | 7,365 行 |

外加 `data_version_dom`: 按**数据域**计数(不是全局 `data_version`)。全局计数粒度太粗——
改个供应商联系人也会 bump, 会把 17 万单元整体重建一遍。判定只依赖
`orders / inventory / products / rules / config`。

#### 三、四维保障(逐条可验, 不是口号)

| 维 | 机制 | 失效时的行为 |
|---|---|---|
| 一致性 | `fp` = 域计数器 + 粒度 + 模式的 md5; 每次读比对, 不等即不命中 | 不命中 → **退回现算**(慢但正确), 起后台重建 |
| 时效 | 写入 bump 域计数 → 下一次请求即重建; 读路径不阻塞 | 重建完成前一直走现算, 不会返回旧值 |
| 完整性 | **发布前自校验**: 单元总数 / 状态分布 / 独立 `tally()` 复核 / 异常行数; 任一不过**不切换 head** | 保留旧版本 + `stale=1` + 退避 10 分钟, 重复告警 |
| 可回滚 | `head.enabled` 一列(库内开关, UPDATE 即生效); env `UNIT_STATE_READ=0` 一刀关闭(优先) | 删变量/改一行, 秒级回到旧路径, 不用重新部署 |

**没有 TTL**。时间不参与"数据新不新"的判断 —— 这是 §15.120 否掉"拖 TTL"的同一条理由。
`stale` 退避用的 10 分钟是"重试间隔", 不是"数据保鲜期", 两件事不能混。

#### 四、实测(线上, 只读 `perf_debug`)

部署 `151a6bc`(Success/Prod=yes), `head.enabled=1` 之后, 等 60s 缓存过期逐轮测:

| 阶段 | 改前(11-06 22:30) | 改后(11-07 09:56~09:59) |
|---|---|---|
| 查询 | 2.42s | **0.90s** |
| 组装 | 1.38s | **0.03s** |
| 业务合计 | 3.80s | **0.93s** |
| 端到端(含 ~1.2s 平台地板) | 5.0~5.2s | **2.12 / 2.33 / 2.47s；other 2.60s** |
| 语句数 / 连接 | 6 条 / 6 次 | **7 条 / 3 次**(bundle 1 + 快照 3) |
| 最大单条 | 2.07s(`inv`) | **0.84s(`bundle`)** |

`inv` / `digest` 两条从 `perf_debug` 里**消失**了 —— 那是命中时压根不发这两条 SQL。

**等价性**: 同一份生产数据两条路径双跑, `jd/bbcc` 与 `other/traditional` 的 summary
**全字段 0 差异**(递归比对, 数值 1e-6); `health_index` 逐档相等;
低库存 `509 / 0 / 10000`(jd) 与 `2720 / 1998 / 70000`(other) 与现算完全一致。

#### 五、两个只有真跑才暴露的坑

1. **降级路径没接快照 → 4.6s 假象**。部署后先测到 4.3~5.2s, 比改前还慢。
   查日志发现 `summary agg 计时` **一条都没有** —— 说明走的是 `agg_dirty` 置位后的
   **直查降级分支**(60 天 orders 全扫 + 组装阶段串行查询), 而那条分支当时没拿快照。
   修: `_store_tally()` 两条路径共用。**教训: "加了快照"不等于"所有路径都吃到快照"**,
   降级分支恰恰是最需要它的时候(agg 脏 = 正在重建 = 本来就更慢)。
2. **`built_at` 时区让退避永久成立**。`NOW(6)` 是 DB 会话时区(+08), Python 侧 naive
   datetime 按本地(UTC)解释 → 差 8 小时 → `time.time() - built_at.timestamp()` 恒为负
   → 退避永远成立、重建永久停摆。修: 比较放进 SQL(`built_at > NOW(6) - INTERVAL n SECOND`)。

#### 六、回归

`local_test` **710 通过 / 0 失败**, 新增 11 条:

- 静态: `unit_store` 不得出现 `.classify(` / `CASE WHEN` / `safety_line(`(分档只走 `metrics.judge`); 状态常量必须引用 `M.ST_LOW/ST_OUT`
- 静态: `invalidate` 里按域 bump + 起后台重建; fp 依赖域**只含判定输入**
- 静态: schema 三表 + `data_version_dom` + 版本 ≥ 18
- 行为: 低库存(bbcc/traditional)两种口径的 `roll` 结果逐项相等
- 行为: 校验能抓到"单元总数不符"与"异常明细缺行"(不发布, 而不是发布后对账)
- 开关: `UNIT_STATE_READ=0` 一刀关闭; 未设置时不阻断(由 `head.enabled` 决定)

SQL 冒烟 **295 条 0 失败**; schema 对账 **53 表 / 514 列 / 15 索引**全在。

#### 七、已知边界(不吹)

- **评估本身没变快**: 导入后仍要真算 10 万单元, 只是不再抢读接口的连接。评估 142~225s 是业务成本。
- **明细类治不了**: 进销存 90,100 行本来就要展示, 只能分页 + 索引; 物化明细 = 复制一张 `inventory`。
- **网关地板 0.8~1.7s 抹不掉**: 端到端 2.1~2.6s 里约一半是平台调用开销(404 实测)。
- **`bundle` 0.84s 仍是最大单条**: 六合一里 `recent`(orders 直查) 与 `brands`(JOIN products) 是大头, 下一步可考虑把 `brands` 也物化。

## §15.153 全面退化排查: 不是分页失效, 是"切页全清缓存 + 不取消在途 + 重复全量取数"三层叠加(2026-11-07)

### 一、用户 8 点与结论(先给结论, 后给证据)

| # | 问题 | 结论 |
|---|---|---|
| 1 | 进销存懒加载/真分页是否失效 | **没失效**。后端 `page/page_size` LIMIT 生效(page1/page2 各 100 行), 前端滚动加载也在。慢的是"每页都要重做全维度 COUNT + 日销 + 批次 + 流水" |
| 2 | 是否所有页都退化、是否冗余优化叠加 | **是**。三个叠加层: ①切页 `clearCache()` 清**全站**缓存; ②`clearInflight()` 只清 Map **不 abort** 真请求; ③订单页翻页/搜索走 `loadAll()` 把看板+断货+告警全拉一遍 |
| 3 | 胶囊噪音 | 已改为**只按当前页真实在途**点亮; 后台任务全局显示"n 条任务运行中", 任务页不显示 |
| 4 | 快速切 tab 最新优先 | 已加 `abortScope` 于 tab 切换 + 页面卸载; 切页 `abortAll()` 真取消(旧实现只是清表) |
| 5 | 69 码组合优先 | **生效**。`grain_of()` 唯一决定处: bbcc→`(SKU,69码)`, traditional→`SKU`; 线上无覆盖配置 |
| 6 | 库存冗余表 | 无 b2test 残留(已清); 唯一可删的是 `b3test` 56 行快照与 `idx_snapshot_ch_date` 冗余索引, 见 §四 |
| 7 | 归档改滚动半年 | 已改 180 天, 且**写侧(cron)与读侧(history 切线)共用同一常量**, 不再各写 365 |
| 8 | 未完成项 | 见 §六 |

### 二、根因(按影响排序, 都有线上/代码证据)

**1. 切页把全站缓存清零(最大放大器)**
`App.navigateTo` 里 `clearCache()` 无参 = 清空 **所有** 键。用户每切一次页, 目标页要重发全部接口,
且刚离开的页面(30s 内本可命中)也一起失效。叠加每请求 0.8~1.2s 的 Makers 冷启动,
"切页=重算全站"就是"全面退化"的观感来源。
→ 改为: 只 `abortAll()` 真取消旧页在途; 缓存交给 30s TTL 与域级失效。

**2. `clearInflight()` 不取消请求**
它只 `inflight.clear()`, 底层 axios 请求继续跑完。旧页 4~6 个请求 × 1~8s 占着实例的
DB 连接与执行槽, 新页请求排队。这正是"切页后每个页面都等好几秒"。
→ 新增 `abortAll()`(逐个 `AbortController.abort()`), 切页调用。

**3. 订单页高频操作拉全站**
`setOrderPage` / `setOrderFilterLocal` 都调 `loadAll()`(summary main+charts、orders、
quality-logs、alerts、stock-risk)。翻一页 30 条订单 = 6~8 个接口重算。
→ 新增 `loadOrdersOnly()`: 只发 `/api/orders`; 分页/搜索/状态三处改用它。

**4. stock-risk 同一次数据读 5 遍(其中 2 遍参数完全相同)**
`_stock_risk` 连续调 `get_sku_sales_stats`: ①`wh=__C__` ②`wh=__C__`(与①逐字相同)
③全维度 ④全维度按码 ⑤`wh=__C__` 按码。合计约 25 万行传输, 只为算 100 个单元。
→ 合并为 1 次 `barcode="all"` + 4 列 `fields`, 内存按 (码是否为空 × 仓库是否聚合维) 分流。
线上 **7.71s → 0.75~1.04s(热)**。

**5. 滞销处置(disposal)的 CPU 热点**
每行库存(9 万行)都遍历品类配置并 `split` 字符串、`strptime` 解析日期。
冷实例实测该循环 26s(0.29ms/行), 是典型"数据翻倍→超线性恶化"。
→ 品类匹配按 `category` 记忆化、日期按 `ld` 记忆化。

**6. 多层物化/缓存各自为政**
`analysis_cache`(30~60s) / `unit_state`(指纹) / `sku_sales_stats`(90 天) /
`orders_day_agg` / `daily_sales_snapshot` 五层并存, 失效由 `invalidate(域)` 广播。
只要有一层 miss 就回退全量重算, 且互不感知 —— 表现为"时快时慢"。
本次先把"重复读同一层"的浪费消掉; 跨层合并见 §六。

## §15.154 断货三级改读物化：请求路径不再为基础 10 条明细搬 21 万行(2026-11-07)

### 一、为什么单独做，而不是跟着 aux 一起切

aux 的低库存卡读 `unit_summary`（金额级 6 个整数）就够了，`unit_alert` 存的 `state` 是
`ok/low/out` 五档。断货卡要的是**另一套东西**：

| | 低库存卡(`unit_alert`) | 断货卡(`risk_snapshot`) |
|---|---|---|
| 分档 | `ok/low/out/idle/paused` | `red/orange/yellow` 三级 |
| 安全线 | `period_of(kind)` | `b2c`(BC) / `lead`(C、own)，分维度取 |
| 分子 | `avail + transit` | `avail + 在途×OTIF + B→C 调拨在途` |
| 分母 | `ds` | `ds × 活动系数 × 当天小时加速` |
| own 维日销 | 下游需求 `__C__` | **该仓自己**的日销 |

塞一张表就是两条口径互相污染（红线 D：不叠加）。所以独立表、独立开关、独立指纹。

### 二、做了什么

| 改动 | 说明 |
|---|---|
| 新表 `risk_snapshot` | 存三个维度(BC/C/OWN)的**全部命中行**，与 `unit_summary` 同一个 gen 一起发布 |
| `unit_store._risk_rows()` | 重建时调 `_stock_risk(legacy=True)` —— **不复制算法**，只搬结果 |
| `unit_store.risk_of()` | 请求路径读几百~几千行，`None` 则调用方退回现算 |
| `?legacy=1` / `?compare=1` | 旧路径保留 + 两路逐字段对账（切换前的 0 差异证明） |
| `risk_sort_key()` | 排序唯一真源，现算与读回共用 |

`_stock_risk` 内部那份公式**一行没改**（除排序），只加了"先试试物化"的分支。

### 三、上线时自查出来的三个缺口（都是"不做就会静默错"）

1. **排序不确定**：原来 key 只有 `(level, days_to_empty)`，同值行顺序取决于 dict 插入序
   （inventory 物理返回序，TiDB 不保证稳定）。物化后读侧是 SQL 排序，与 Python 稳定排序对不上，
   双路对账实测报 **17616 条 diff，全是错位不是数值差**。
   修法：补 `(sku, barcode, warehouse)` 成全序，两路共用 `risk_sort_key`。
   （不交给 SQL 排：MySQL collation 与 Python 码位序不一致，SKU 格式不统一就会错位。）

2. **"没算成"与"真的 0 条"分不开**：`risk` 计算异常时该 gen 没有行，读侧会组装出
   "0 条断货"的合法 payload —— 用户以为今天没风险，比慢 5 秒严重得多。
   修法：`unit_state_head.risk_rows` 哨兵，`-1 = 本轮没算成` → 退回现算；`0` 是合法结果。

3. **供应商评分改了不生效**：判定模型不读 OTIF，所以 `JUDGE_DOMAINS` 里没有 suppliers；
   但断货卡的在途按 `suppliers.score/5` 打折。共用一个 fp 就会出现
   "评分改了、可撑天数还是旧的、且无人察觉"。
   修法：`RISK_DOMAINS = JUDGE_DOMAINS + ("suppliers",)` + 独立 `risk_fp` 列；
   `invalidate()` 的 bump 范围同步扩到 `RISK_DOMAINS`。

第 3 条已用真实写接口端到端验证：`PUT /api/suppliers/21`（**同值**，只触发失效）→
`data_version_dom.suppliers` 0→1 → `gen` 5→6 → `risk_rows` 重算 → 两个指纹均 match。

### 四、线上实测（复用 TLS 连接，同一时段）

### 15.134 预览页"标题行间距"的真因: 负 margin 压到了步骤条 (2026-11-03)

#### 一、现象与误判方向

反馈是"预览页的标题行间距有问题"。第一反应会去看标题内部的排版 ——
`清洗预览 · 前 50 行` 是 15px 加粗, 后面 `· 共 80 行, 仅展示前 50 行 · 3 列`
是 `.small` 12px, 同处一行靠 baseline 对齐。量下来两段都在 top=122 / bottom=136,
对齐正常, 不是这的问题。

真正的问题在标题**上方**: 标题 top=116, 而步骤条(`.step-indicator`)bottom=126
—— **两者重叠 10px**。所以视觉上是"标题贴在步骤条上", 而不是"标题内部行距不对"。

#### 二、根因

`.clean-preview-page { margin-top: -24px }`, 注释写得很明确: 想让预览区上移,
吃掉容器 70px 的 padding 顶部(等效 70→46), 把 24px 让给表格。

但负 margin 作用在**整个块**上, 它不是"只吃上方容器的 padding", 而是把块内所有
内容一起上移。上移路径上第一个遇到的是紧邻的步骤条:

| 量 | 值 |
|---|---|
| 步骤条占位 | 86 – 126 (高 40) |
| `.step-indicator` margin-bottom | 14 |
| 标题自然 top | 140 |
| margin-top:-24 后实际 top | 116 |
| 重叠 | 126 − 116 = **10px** |

桌面 1440×900 与移动 390×844 完全一致 —— 这是布局公式问题, 不是响应式问题。

#### 三、修法: 回退上移, 高度公式同步 +24

只删 `margin-top` 会让 page 整体下移 24px、底部按钮被推出视口, 必须同时把
`height: calc(100svh - 152px …)` 改成 `- 176px`。两者相加正好抵消:

| | top | height | bottom |
|---|---|---|---|
| 修复前 | 116 | 648 | 788 |
| 修复后 | 140 | 624 | 788 |

底部按钮位置不变, 代价是表格可视高度少 24px(527 → 503 的量级, 仍内部滚动)。
**要再省这 24px 只能从步骤条 padding 或 card padding 上取, 不能从标题上取。**

#### 四、验证

- 几何断言(不是看截图): 标题–步骤条 gap = 14(与映射页一致)、页面底距 = 56 不变、
  表格区高 ≥ 120、底部按钮完整在视口内; 390×844 / 1440×900 均过。
- 横屏 844×390 走 `height: auto` 分支(回文档流滚动), 行为未变 —— 它的溢出是设计使然,
  断言里要排除。
- 清洗页全流程冒烟 24 项全过(含订单类型的「表格列状态映射」弹窗)。

### 15.135 预览页两处口径对齐: 卡片高度 ×5px、标题 ×字号 (2026-11-03)

#### 一、卡片高度: 预览 = vh−110, 进销存 = vh−115

两页卡片都随视口线性变化, 但常数不同, 每页差 5px(底边 804 vs 799), 换页时底边跳。

| 页 | 高度构成 | 总高 |
|---|---|---|
| 预览 | pt16 + 步骤条40+mb14 + page(100svh−176−safe20) + pb16 | vh − 110 |
| 进销存 | pt16 + 标题21+mb12 + 滚动区(calc(100vh − 180px)) + pb16 | vh − 115 |

修法: 预览公式 176→181(改动一个常数), 两页同为 vh−115, 逐像素齐平(729/785)。
不动进销存的 `100vh−180`: 那是 1000+ 行表格的分页/虚拟滚动参数, 牵一发动全身。

#### 二、标题口径: 预览页弃用 .section-title

同位置的"标题行", 映射页与预览页原本两套口径(14/11 flex 居中 vs 15/12 baseline 混排,
mb 10 vs 12)。预览页改为映射页同构后, 标题行 140–160 逐像素一致。

> 细节: 映射页源码里 `marginTop: 2` 在块流里与步骤条的 margin-bottom **折叠**
> (实际间距 14); 预览页标题的父容器是 flex column, margin 不折叠, 照抄会变 16。
> "抄同一份代码"之前先确认它依赖的布局上下文是否相同。

#### 三、验证路径的一个坑

效果图脚本曾显示改动"没生效", 排查半天 CSS 缓存 —— 实际是脚本默认 HOST 是
**线上**(未部署, 当然是旧值)。验证改动是否生效, 先确认脚本连的是哪个环境。

### 15.142 库存批量删除/恢复: 借订单的交互, 不借订单的语义 (2026-11-04)

#### 一、先钉事实: 删除与恢复**前端都没有入口**

接手时以为只缺"恢复 UI"。实测 `grep -n "delInv\|confirmDel" InventoryPage.tsx`:

```
80:  const [confirmDel, setConfirmDel] = useState(null)   ← 定义
252: const delInv = async () => {...}                      ← 定义
1127: open={!!confirmDel}                                  ← 消费
```

`setConfirmDel` **全模块零调用点** —— 删除确认框的 `open` 恒为 false。也就是说
后端 `DELETE /inventory/{iid}`、`GET /inventory/archive`、`POST /inventory/{iid}/restore`
三个接口齐备且测试覆盖(S2-7), 但前端一个都没接, 删除按钮在页面上根本点不到。
"恢复 UI 未做"(`§15.121`)的前提, 其实是"连删除都没做"。

#### 二、照抄订单会错在哪(三条都不成立)

订单的批量操作是 `UPDATE orders SET deleted_at=NOW() WHERE id IN (...)`, 一次 SQL 结账。
库存照抄会出三处硬伤:

| 订单的做法 | 库存上为什么不成立 |
|---|---|
| `UPDATE deleted_at` 一把梭 | 库存是**整行归档快照**(`inventory_archive` 保留原 id + 删除时数量), 不存在"取消标记", 只能原样插回 |
| 一个 `ids` 数组、整批成功或整批失败 | 恢复会被 `uq_inventory_biz` 拦截(删完又导了同键) —— **必须允许部分成功**, 并说清哪条为什么不行 |
| 逐条 `Promise.all` 打单条接口 | 100 条 = 100 次往返(线上单次 ~57ms ≈ 5.7s), 逼近 120s wall clock |

所以只借**交互形状**(勾选列 + 锤子面板 + 事件联动), 语义全部重写。

#### 三、实现要点

**后端 `POST /inventory/batch`** —— 两个动作的路径完全不同:

- `delete`: 先 `SELECT id` 判存在 → 整批 `INSERT...SELECT` 归档 → 整批 `DELETE`。
  存在性必须**先查 inventory**, 不能回查归档表 —— 历史归档行会把"上次删过的 id"误判成本次删成功。
- `restore`: **预取 + 逐条判定**。先一次性取回归档行、一次取 `id` 占用、一次按候选 SKU 取现存业务键,
  在内存里判完再 `executemany` 写入、批量删归档。往返从 `3N` 压到 `≈5`, 且返回
  `{restored, failed:[{id, reason}]}` —— 部分成功是**正常结果**, 不是异常。
- `executemany` 整批失败时回退逐条, 不让一条脏数据把整批回滚。
- 上限 500 条且**超限报错**, 不静默截断("选了 800 只恢复 500" 是静默丢数据)。

**前端**: 库存页加勾选列(32px 最左, 与订单同款)+ 锤子"批量操作"面板;
回收站新增「已删除库存(归档快照)」分组, 复用 `ListItem` 勾选 + 锤子批量。
锤子计数拆两套: **恢复**吃三类(规则/订单/库存), **永久删除**只吃规则+订单 ——
库存归档没有"永久删除"语义, 混进同一个计数会让按钮点了必然失败。

顺手删掉 `delInv`/`confirmDel` 死代码(单条删除改走批量链路, 与订单一致)。

#### 四、实测(真实库, 不是 mock)

| 场景 | 结果 |
|---|---|
| 删 1 条 → 归档 → 列表命中 → 恢复 | `deleted:1 / restored:1`, **22 个字段逐一比对零差异**, 归档清零 |
| 删 1 条 → 同业务键重新导入 → 恢复 | `restored:0, failed:[{id:309030, reason:"同业务键…已重新导入"}]`; 原行未插回、新行 qty 完好、归档快照仍留 |
| 清理后再次恢复 | 成功, 字段零差异 |

回归 **403 通过 / 0 失败**(新增 11 条 S3-7); `--sql-smoke` 389 条唯一 SQL / 264 校验 0 失败;
preflight 七步全绿。

#### 五、教训

**"接口已备"不等于"功能可用"**。S2-7 把三个接口写完并测过, 文档记的是"恢复 UI 待接",
但实际是删除入口也没接 —— 死代码 `delInv` 一直安静地通过所有静态检查, 因为它**被定义了**。

**第一层**: SELECT 没有 i.id → 行里没这个字段。

### 15.144 两条代码红线 + S3-5 迁移框架落地(2026-11-04)

#### 一、红线: 以下两条从今天起是**准入条件**, 不是建议

**A 非内联优先。** 新增或调整功能时, 逻辑默认落独立文件; 页面/路由只做编排。
判据不是行数好看, 而是**一个文件只该有一件事**:

| 层 | 放哪 |
|---|---|
| 后端 | `routes/<域>.py`(HTTP) / `core/<域>.py`(纯逻辑) / `biz/<域>.py`(业务计算) / `migrations/steps/<域>.py`(迁移步骤) |
| 前端 | `pages/<页>/<块>.tsx`(页面私有) / `components/<域>/<块>.tsx`(跨页复用) |

触发即拆: `.py`>600 行 / `.tsx`>500 行 / 单函数或单组件>80 行 / **一个文件出现第二套职责**。
但**不许为拆而拆** —— 5 行的文件、只被引一次的包装层同样算噪音。按职责拆, 不按行数拆。

这条红线为什么现在才立: §15.139 拆了五大页(12482→4646 行), 但那是一次**还债**;
如果不把"新代码不许内联"钉死, 同样的债会在半年后再长回来。本轮 S3-5 就是活例 ——
`schema_create.create_all_tables()` 里塞了 7 段互不相关的数据迁移, 属于"一个文件两套职责"。

**B 不硬编码中文。** 界面文案一律 `t('key')`, 新增 key **必须 zh + en 双份**。
`t()` 的兜底是 `当前语言 → zh → key`, 所以**缺 en 不会报错, 只会静默显示中文** ——
这是"半中半英"长期收不了口的机制原因。本轮补了两条断言(zh/en 键集合相等 + 回退顺序),
把这件事变成门禁。

边界: 注释不受限(本仓库注释一律中文, 刻意的); 后端 `error` 字段是诊断文本可用中文,
但不能是唯一用户提示。

#### 二、S3-5: 把"改存量数据"的步骤从建表声明里分离

**动手前的事实核查**(用户要求"动前先读完整代码")。读完 `schema_create.py` 754 行后,
迁移框架的真实缺口不是"没有框架", 而是**框架的粒度错了**:

`ensure_schema()` 用 `SCHEMA_VERSION` 门禁把"全量路径"当原子操作 —— 版本一 bump,
`create_all_tables()` 里的**全部历史步骤重跑一遍**。这些步骤各自靠
`INSERT IGNORE INTO migration_log` 自守, 于是:

- 漏写一处守卫 = 改数据类步骤重复执行(金额翻倍级别);
- `oversell_wording` 那一步**根本没有守卫**, 每次冷启动都整表 UPDATE;
- 两个"守卫写法不一样"(`migration_log` 与 `schema_state`)并存, 谁也说不清哪些跑过。

所以 S3-5 要做的不是"上一个迁移工具", 而是**给每一步一个独立的应用状态**。

**落地**(`cloud-functions/api/migrations/`):

| 文件 | 职责 |
|---|---|
| `__init__.py` | 有序注册表 `_REGISTRY`(模块名延迟导入) + `validate()` 静态自检 |
| `runner.py` | 取已应用集合 → 只跑未应用的 → **单步事务** → 登记 |
| `steps/*.py` | 7 个步骤, 每个只导出一个 `run()` 返回影响描述 |

四个设计决定, 每个都有反例支撑:

1. **单步事务**: `run()` 的写与"登记已应用"同一事务提交。反例是"先执行后登记、各自
   autocommit" —— 崩在中间就是"改了数据但没登记", 下次重跑, 而 archive 那次已经证明
   逐条累加类逻辑重跑会把金额算两遍。
2. **失败不阻断后续**: 后续步骤大多不依赖它, 而阻断会让 schema 版本永远卡住、每次冷启动
   重跑全部步骤。失败步计入 `_errors` → 不写版本 → 下次冷启动重试。
3. **失败要留见证**(`status='failed'` + `attempts`): 一开始只记 applied, 结果失败步
   下次被当成"从没跑过"直接重跑; 加了 `MAX_ATTEMPTS=5` 上限后, 撞同一个错 5 次就跳过并告警,
   不再刷日志。
4. **旧标记归并**(`legacy_log_sync`): 线上 `migration_log` 里已有的标记直接登记为已应用、
   **不执行**。否则上线那一刻会把已跑过的步骤再跑一遍。

**实测**(真实 TiDB, 非 mock):

```
schema_state.version = 5
schema_migrations: 7 行, 全部 applied / attempts=0
  20261029_rules_field_path      | days_since_last=0 stock=0
  20261030_lowstock_sellable     | 0 条
  20261030_channel_name          | 0 条
  20261030_lowstock_wording      | 0 条
  20261029_oversell_wording      | 0 条
  20261101_products_expiry_managed | 0 个 SKU 标 yes
  20261104_legacy_log_sync       | 归并 5 条        ← 5 条旧标记被认领, 未重跑
```

影响行数全为 0 是**预期**: 这 5 步线上早跑过, 数据已是目标态。归并 5 条证明防重跑生效 ——
如果没生效, `oversell_wording` 会整表 UPDATE(它原本无守卫)。

### 15.145 i18n 全量对齐 + 4 视口验证(2026-11-04)

#### 一、这一轮的边界: 先把"文案"和"数据"分开

前序几轮已经把残留压到 0, 但那只证明**代码里没有中文了**, 不证明**界面上没有中文**。
本轮先用 4 视口 × 双语的实机快照把"界面上还剩什么中文"摊开, 再逐条判定它是哪种:

| 类别 | 例子 | 处理 |
|---|---|---|
| 界面文案 | 列头、按钮、提示、图表轴标签 | 必须 `t()`, 这是本轮主体 |
| **数据值** | 订单状态「已完成」、渠道名「京东渠道」、仓库名「上海仓」、商品名 | 不翻。翻了下游匹配就断 |

#### 二、快照跑出来的 6 类问题(全部已修)

**1. 列头直接显示词条键(`col.brand`)** —— 最典型的一类。
`colLabel(id)` 是 `t('col.' + id)` 动态拼键, 审计的"t() 引用"检查是按字面量做的,
拼出来的键它看不见。而 `configs.ts` 里 66 个列 id 有 24 个压根没写词条。
→ 补 24 条双语, 并让审计直接比对 **列 id 集合 ⊆ `col.*` 键集合**。

**2. 数字消失, 只剩单位(`万单`)** —— 柱状图每根柱子都标"万单"。
`'dash.unit_wan_orders': '万单'` 丢了 `{n}`。这个错**不会报任何错**, 值直接被抛弃。
→ 修正文案; 审计新增"传参却无占位符"检查。这是本轮性价比最高的一条。

**3. 英文界面冒出「单 / 件」** —— `t()` 的回落是 `当前语言 → zh → key`,
en 写成 `''` 不报错, 安静地掉回中文。**空串是假翻译**。
→ 补 `'orders'` / `'units'`; 审计把空串一律当缺陷, 只有 `rfm.then`
(英文语法上不该有对应词) 逐条登记进 `EMPTY_OK`。

**4. 图表轴标签仍是中文** —— 订单阶段分布的「已完成/已发货/待发货/待确认/总订单」
是后端 funnel 的 `name`(状态原值), 前端 `xAxis.data` 直接吃了。
→ 走 `orderStageLabel()`(与 `orderStatusLabel()` 同源映射), tooltip 同样。

**5. 英文被裁掉(`Replenish 1…`)** —— 待处理卡片是 `aspect-ratio:1` + `overflow:hidden`,
第二行 `nowrap`, 英文比中文长约 60%, 放不下就是硬裁, **且不产生横向溢出**
(所以只查 `scrollWidth` 会漏)。→ 英文词条取短写(Buy / Replen / Low), 保持 nowrap。

**6. 洞察表格一屏只显示 1~2 行(行高 244px, 中英都有)** —— 这条和 i18n 无关, 但危害最大。
两个因素叠加:
- 备注列是上百字的分析句, `.col-name` 只给了 `min-width:100px`, 逐字折行 → 十几行;
- `td.mono { word-break: break-all }` 把 `SKU-0462-J`、13 位条码也拆成多行。

→ 新增 `.col-note`(220~320px、限 3 行、`title` 悬浮全文), `td.mono` 改 `nowrap`。
**行高 244 → 58px, 一屏从 1~2 行变成 10+ 行。**

> 这里有个教训: `word-break: break-all` 对"码值"(SKU/条码/单号)是错的 ——
> 它不是自然语言, 断在任意字符处既难读也没有省下空间。码值要么 `nowrap`,
> 要么按分隔符(`-`/`_`)断, 不要 `break-all`。

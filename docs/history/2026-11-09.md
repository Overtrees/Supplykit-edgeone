### 二、失败形态链（容易被 401 误导）

```
POST /api/auth/login (admin) → HTTP 200 + {"ok":false,"error":"服务处理失败…",
                                "detail":"OperationalError","request_id":...}
  · admin 分支要查 users 表 → 1105 → 被 @traced 包成 200 错误体
  · demo/demo123 是内置硬编码分支，不查库 → 仍能拿到 token
→ 拿不到 token → 所有业务接口级联 401「未登录，请先登录」
→ health 中间件独立放行 → 200 + degraded + 1105 全文
```

**别把 401 当鉴权故障**：那是登录失败的级联。做冒烟必须用 `demo` 拿 token，
否则看到的全是 401，接口本身是什么形态根本测不到。

### 四、这轮最有价值的发现：`200 + 全 0` 的静默空壳

初版冒烟按「HTTP 200 且 `data` 非空」判可用，结果 8 个「可用」里 5 个是假阳性。
逐条看原始响应体后才发现：

| 接口 | 返回 | 实际含义 |
|---|---|---|
| `boot` | `ok:true`，但 `data.orders/summary` 是 `OperationalError`，另两块全 0 | 首屏四块全废 |
| `aux` | `alerts:[]`、`alertCounts.total:0`、`stockOverview` 全 0 | 空壳 |
| `stock_risk` | `items:[]`、`total:0`、三级全 0 | 空壳 |
| `unit_state` | `gen:0 / units:0`，但 `cold_guard.started=15` 等进程累计计数非 0 | 空壳（诊断计数不是业务数据） |
| `hist_coverage` | `archive:null / orders:null`，`note:"暂无归档：订单自 - 起…"` | **DB 查不到被包装成「没有数据」** |

`hist_coverage` 那条最危险：用户会以为归档数据丢了，实际是查不到。
历史文档早有同类教训（"静默吞异常曾让 version 恒 0 而无人知"），这次是同一模式在
读路径上重演。

判定因此收紧成三条：① 响应体含 `OperationalError`/`1105`/`quota`（**含嵌套**）→ C；
② 递归找有效业务数据，排除配置常量（cutoff/archive_day/*_days/channel/mode）与
含「暂无」的兜底文案 → 无则 E；③ `unit_state` 只看 `gen/units`。

**`tasks` 的 500 是另一个形态**：`routes/tasks.py:123` 的 `list_tasks` **没有**
`@traced` 装饰器，异常直接冒泡到平台 → EdgeOne 返回 HTML 错误页，与其他接口的

### 15.186 新集群 `supplykit-1109` 迁移 + 空库自举修复 + 两缺口（2026-11-09 第二批）

**触发**：用户补了一份可用的 TiDB Cloud API 凭据（新附件只改了 `TIDB_PUBLIC_KEY` /
`TIDB_PRIVATE_KEY`，其余 18 项逐字相同 —— 旧 key 已失效）。要求「新增集群当成新库把
现有业务逻辑和全链路联动建表那些」+「修复上一批提到的两个缺口」。红线依旧：
**不导业务数据、不重跑 seed、不改判据、中文思考**。

#### 一、认证踩坑（先排掉工具问题）

- `serverless.tidbapi.com/v1beta1` 用 **HTTP Digest**（public=用户名 / private=密码）。
  旧 key 下 curl / requests / 手写 RFC 2617 三种实现、27 种 realm/算法变体全 401
  （`stale=false`、Kong 层空 body）→ 结论是凭据失效，不是实现问题。
- 新 key 下 **`curl --digest` 第二次请求 200**；但 Python `requests.HTTPDigestAuth`
  在 HTTP/2 下报 403 —— 「403 Forbidden」是第一次请求就被网关挡了，不是授权失败。
  **本项目一律用 `curl --digest` 调 TiDB Cloud API**，别用 requests 的 digest。
- `GET /v1beta1/projects` 是 `404 no Route matched`（v1beta1 无此路由）；
  `projectId` 从**已有集群对象**的 `labels."tidb.cloud/project"` 取
  （`1372813089454817708`），不必另找端点。
- `POST /clusters` 参数沿用 §15.63：`displayName`(≥6 字符) +
  `region.name` 完整形态 `regions/alicloud-ap-southeast-1` + `clusterType=DEVELOPER` +
  `rootPassword`(24 位随机，仅本地临时文件，不进 git/对话) + `projectId`。
  结果：`supplykit-1109` / `10406157977958137320`，state=ACTIVE，
  userPrefix `ef9qsFFUPZajwgh`，host 同区 gateway01。

#### 二、空库自举暴露的 2 个结构性 bug（存量库永远测不出）

`db.py` 首连 `Unknown database` 自动 `CREATE DATABASE` 成功；`ensure_schema()`
第一次跑建出 61 张表，但 `schema_state` / `channels` / `data_version_dom` 全空 ——
说明内部有失败项，按设计「不写版本」。查 `quality_logs` 留痕定位：

| # | 现象 | 根因 |
|---|---|---|
| 1 | `补索引 idx_batches_sku_bc: (1072, 'column does not exist: barcode')` | 顺序是「建表 → 建索引 → **补列**」，而 `idx_batches_sku_bc(sku,barcode)` 引用的 `batches.barcode` 只在 `_COLUMN_ADDS` 补列里。存量库早有该列 → 从没暴露；空库首建时列还没补 → 记进 `_errors` → 版本永不写 → **每次冷启动重跑全量 DDL（实测 86s）** |
| 2 | `channels` 0 行（连留痕都没有） | 渠道种子 `INSERT INTO channels` 写在 `create_all_tables()` **最前面**、建表循环之前。空库里 `channels` 表不存在 → INSERT 失败；`try_err` 想写的 `quality_logs` 也还没建 → **双重静默**。只能靠 `common.ch_list` 的硬编码兜底，用户在渠道页改配置无法持久化 |

修法（都只影响「版本未写/新库」路径，存量库 `schema_state=v26` 走热路径零 DDL）：
① `ensure_schema()` 把**补列整块前移到建索引之前**；② `_TABLES.batches` DDL 直接写上
`barcode`（与 `_COLUMN_ADDS` 注释「新库 DDL 已含同名列」对齐，声明自洽）；
③ 渠道种子移到建表循环之后；④ 补 `INSERT IGNORE INTO data_version(id,v) VALUES(1,0)`
（空表时写路径 `UPDATE ... WHERE id=1` 影响 0 行 → 版本永不递增 → 失效机制瘫痪）。
**没有 bump `SCHEMA_VERSION`**：改的是建表脚本逻辑不是表结构，存量库无需重跑 86s DDL。
沉淀为 [DEVELOPMENT.md 红线 18](../DEVELOPMENT.md)。

修复后重跑 `ensure_schema()` 55.9s，验证全绿：`schema_state=v26`、`channels` 2 行
（jd/other）、`data_version` 初始行、`data_version_dom('schema')=1`、
`schema_migrations` 7 条、61 张表、`idx_batches_sku_bc` 已建、无新增 schema 错误。

#### 三、两个缺口

**缺口一（统一 degraded 态）**：DB 挂掉时业务接口仍 200 + 全 0「静默空壳」，
用户误判成「没数据」。实现刻意选了**响应头**而非改响应体 ——
`@app.middleware("http")` 是 Starlette `BaseHTTPMiddleware`，`call_next` 返回
`_StreamingResponse`（实测 `media_type=None` / 无 `body` 属性），响应体不可写；
头可写且不碰 content-length。

- `db.py`：`mark_db_fail()` 只认**连接/配额类** `OperationalError`
  （1105/1040/2003/2006/2013… 或含 quota/restricted/connection/timeout），
  业务 SQL 错误（列不存在/重复键）不算降级，避免误报横幅；进程内时间戳 TTL 120s，
  `conn()` / `query()` / `execute()` 三处异常路径打点，**零额外查询、零额外 RU**。
- `index.py`：中间件统一给响应加 `X-App-Degraded: 1`，不回传异常正文（防泄漏表名）。
- 前端 `client.ts`：axios 响应拦截器 + `apiJson` 裸 fetch 通道都读头 →
  派发 `app:degraded` / `app:degraded-clear`；空壳**不写 30s 缓存**；
  `apiJson` 把 `__degraded` 注入解析对象，供 LoginPage 判定。
- `App.tsx` 常驻横幅（在 `ToastProvider` 外，登录页也能看到）、`styles.css` 样式、
  zh/en 文案；登录页把 `detail:"OperationalError"` 换成「服务暂时不可用」。
- 对照验证：旧库（1105）`/auth/login` + `/health` 均带 `X-App-Degraded: 1`；
  新库（正常）均不带。`scripts/perf/smoke.py` 加 `[DEGRADED]` 展示标注，**不改分类判据**。

**缺口二**：`routes/tasks.py` 的 `list_tasks` 补 `@traced`，
异常不再冒泡成 EdgeOne HTML 500，与其他接口 200 + `request_id` 形态一致。

#### 五、空库自我失效循环（第三个修复，额度止血必需）

部署后线上 `health` 已 `db:ok`，但冒烟里 `boot`/`summary` 是 `B:降级(SWR)`，连查 3 轮
仍是 `serving_previous / fp_changed:True / built_at` 每次刷新。直查新库发现
`data_version` 从 0 涨到 **22**（部署后 3 分钟）、`data_version_dom('orders')=22`、
`list_head` gen 到 14/9/7、`own_health_head` 到 19/17；再做一次前后快照：
**4 个只读 GET 让 dv 22→26**，物化 `built_at` 全部刷新 —— 持续的自我失效循环。

定位（本地 TestClient + patch `db.execute` 抓 `INSERT INTO data_version` 的调用栈）：

```
GET /insights/replenishment → list_store.serve → _build_repl
  → biz/sales.get_sku_sales_stats → 表空 → _rebuild_sku_sales_stats
  → invalidate("orders")                      # sales.py:762
  → data_version_dom.orders +1 → 读侧 fp 必变 → 下个请求又进同一分支
```

`/dashboard/aux` 同源。**有数据的库上重建一次就有行，分支不再进，所以从没暴露；
空库上永远建不出 0 行以外的结果 → 无限循环**，刚换的新集群额度会被白烧。

修法（`biz/sales.py`，只影响空库路径，有数据时行为逐字不变）：表空时先用一条索引点查
确认 `orders` 有底料；无底料 → 直接返回空结果，**不重建、不 invalidate**；有底料 →
重建后**再查一次确实产出行**才 `invalidate("orders")`（有底料却建不出的异常态也不循环）。
`_ensure_stats_table` 本来就有进程内 DDL 门闩，不新增开销。

验证：本地 5 个接口请求 + 等后台线程 4s，`data_version` **32→32 稳定**
（修复前同样请求 +2）；`local_test.py` 860/0。线上部署后第二轮 10 个只读 GET 的
`data_version` 全程 **40→40 零触发**（部署切换期首轮 +8 属多实例冷启动首建的一次性
现象，不是循环）。沉淀为 [红线 19](../DEVELOPMENT.md)。

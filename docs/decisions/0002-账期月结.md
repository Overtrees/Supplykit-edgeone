# 0002: 账期(月结) — 期初结转、批次月初余额、自动结账

- 日期: 2026-11-04
- 状态: **已定案（用户拍板：甲方案 + B + 自动结账）**

## 决策

自有仓库存从「**快照当基线 + 滚动窗口流水**」改为「**按月一本账、期末结转下月**」：

```
本月期初 = 上月期末(月末 23:59:59 结存)
可用     = 期初 + 本月入库 − 本月出库        （仍按计算来，不是导入即权威）
批次池   = 月初余额(带生产/到期日) + 本月入库流水
周转     = 平均库存 × 天数 ÷ 当月出库       （完整月用 28~31；当月未满用已过天数）
```

平台仓 / B 仓**不进这套**，维持「后台导出即权威」。

## 背景：为什么必须改

改之前的口径是：

```
可用 = beginning_stock(某次库存导入的值) + Σ近90天/全期(入库 − 出库)
```

而库存导入进来的本来就是**当时的可用量**（`cleanse_write` 在缺 `beginning_stock` 时拿
`available_qty` 顶上）。于是快照本身已经扣过那段流水，再叠加一遍 = 结构性双算。

更糟的是：**每次导入都刷新基线，流水窗口却不动**，偏差每月累加一次、单调增长、永不回落。
这不是"某个公式写错了"，是数据流没有同一个时间边界 —— 所以洗一次数（原 B 方案）下个月又会脏。

顺带暴露的第二个问题：周转一律乘整月天数。今天 11-04，分母只有 4 天的出库量，分子却乘 30 天，
**周转虚高约 7 倍**，月初尤其离谱。

## 被否掉的方案

| 方案 | 为什么不采用 |
|---|---|
| 一次性洗期初（原 B 方案） | 只治当期。下个月导入又把基线抬高，脏回去；且要 2~3 万 RU |
| 期初冻结 + 全期重放 | 依赖"建账日"这个干净分界点。生产第一次导流水常带几个月历史 → 直接被污染 |
| 结账后冻结历史批次 | 用户明确否掉：上月入库没卖完，本月要继续优先出。批次必须跨月连续 |
| 当月不算周转，只看已结账月 | 用户明确要"看当月"，改为按已过天数折算 |

## 关键设计点

1. **期初只有一个来源**：上月期末。首期（未建账）才用导入值当基线。不做任何反推。
2. **`beginning_stock` 冻结为"建账基线"**，导入不再覆盖它（已建账后只把导入值存进
   `snapshot_qty` 做对账）。这一条是根治双算的那一行。
3. **批次月初余额必须带日期**（`batch_opening`）。少了它，上月批次到本月就变成"无日期期初批次"，
   指定批次出库全部命中不了、只能降级 FIFO —— 用户"以导入指定批次为准"的口径当场失效。
4. **漏结不会算错，只会窗口变长**：可用 = 最近已结账月末余额 + 其后全部流水。账期断档时
   自动退化成更长窗口，结果仍是真值，不是兜底。
5. **自动结账，但数据不齐拒绝结**：1~3 号尝试，体检（上期流水最后一天距期末 ≤2 天）不过就
   `blocked` 留痕，**一个数都不改**。补导后走 `POST /ledger/reclose` 补结。
6. **不允许跳月结账**：只能结"当前生效账期的下一期"，否则期初会静默取到更早的基线。

## 新增表

| 表 | 作用 | 量级 |
|---|---|---|
| `inventory_month` | 每账期每行：期初/入/出/期末 | 2000 SKU × 12 ≈ 2.4 万行/年 ≈ 3MB |
| `batch_opening` | 批次月初余额（带日期） | ≈ 1.2 万行/月 ≈ 15MB/年 |
| `ledger_state` | 每(渠道×仓型)一行：当前账期 + 起算日 | 常数 |

## 接口

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/ledger/status` | 当前账期、状态、上期是否可结（含原因） |
| GET | `/ledger/preview?period=` | dry-run：只算不写，看结出来多少、与当前可用差多少 |
| POST | `/ledger/close` | 结账（幂等覆盖，永不累加） |
| POST | `/ledger/reclose` | 补导后从某期补结到上月 |
| GET/POST | `/cron/ledger-close` | 手动/CI 触发结账（窗口 00:30–03:00，函数内再限 1~3 号） |

### 定时调度怎么挂的（重要）

`edgeone.json` 的 `schedules` 有 **maxItems 10** 的硬上限，本项目 10 条已占满
（archive / cleanup / freshness / snapshot / daily-rules / reconcile / recycle /
push-alerts / ping / continue-tasks）。**加第 11 条会让整组定时任务丢路由**（历史已有
"结构变更导致 health 返回 HTML"的实证），所以不新增调度条数，改为：

- 月结嵌入 **`cleanup-logs`（每日 03:05 CST）** 这条最轻的凌晨任务执行；
- 调用点在 `_claim` **之前**：即使当天日志已清理过，结账照常进行；
- `run_ledger_close()` 在每月 4 号之后第一行就返回，**一条 SQL 都不发**，日均成本为零；
- 1~3 号共三次机会自动结账，4 号后停（再往后走 `POST /ledger/reclose` 明确补结）；
- 结账只对 **真有自有仓库存**的渠道跑，避免给平台仓渠道白写一条 `blocked`。

回归用例锁死了这条绑定（`local_test.py`「月结挂在 cleanup-logs 调度内」），
防止重构时把这句挪走 —— 挪走不会报错，只会让账期永远不结。

## 代价与已知限制

- **重结历史超过一期不支持**：期初已被后续结账覆盖，需要整链重建，本版不做，照实报错。
- **`snapshot_qty` 目前只存不比**：导入快照与计算值的差异还没有做成看板，属于下一步。
- **`cleanse_write.py` 已 1500 行**，超出 600 行红线（改造前就超）。账期逻辑已外置到
  `core/ledger.py`，本次只在该文件加了日期窗口与批次池起点的判断，未再堆业务。
- 月结已随 `cleanup-logs` 调度自动执行，无需在 Makers 后台另配；`/cron/ledger-close` 保留给手动补结。

## 验证

- `core/ledger.py` 纯函数有回归：跨年平移、真实月末（2 月 28/29）、已过天数、断档天数。
- 静态断言：批次池读 `batch_opening`、重算有账期下界、无 `max(0, available)` 兜底。
- 结账前先跑 `GET /ledger/preview`，确认 `diff`（与当前可用之差）符合预期再 `close`。
